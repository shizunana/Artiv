# 上传文件存储审计

> 审计日期：2026-08-18  
> 审计范围：`backend/uploads` 与 Git 历史

## 1. 结论

- `backend/uploads/` 已被 `.gitignore` 忽略，当前 `git ls-files` 中上传文件数量为 **0**。
- Git 对象库约 **4.34 MiB**，当前没有“上传文件被重复提交导致仓库持续膨胀”的证据。
- 本地上传目录共 **181** 个文件，约 **139.8 MB**。
- 按 SHA-256 内容摘要统计，共 **44** 组重复内容，涉及 **130** 个文件；若只保留每组一份，理论可节省约 **113.1 MB**。

## 2. 为什么暂不直接清理历史重复文件

数据库可能让不同业务记录引用不同文件名。即使文件内容相同，直接按哈希删除也可能造成作品、企划、橱窗、聊天附件或订单原图加载失败。因此本次不对已有上传文件做破坏性删除。

## 3. 已采取的防增长措施

- 新上传文件改为内容寻址：以 `SHA-256 + 规范扩展名` 作为文件名。
- 相同内容再次上传时复用已有文件并返回同一路径，不再生成时间戳副本。
- 并发上传相同内容时使用原子创建；其中一个请求成功写入，其余请求复用结果。
- 历史路径保持不变，不影响现有数据库记录和页面。

## 4. 后续安全清理方案

1. 汇总数据库全部图片字段和 JSON 内 `/uploads/` 引用。
2. 建立“路径 → 内容摘要 → 引用记录”清单。
3. 对重复组选择主文件，先在事务内替换所有引用，再做页面回归。
4. 仅删除零引用副本；操作前备份数据库与上传目录。
5. 增加定期孤儿文件审计，禁止依据文件名或时间直接批量删除。
