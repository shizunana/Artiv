# 上传文件存储审计

> 审计日期：2026-08-18  
> 审计范围：`backend/uploads` 与 Git 历史
> 2026-09-05 补充：按 `fec304f` 静态核对上传实现和忽略规则；未重新统计磁盘文件、重复摘要或对象库体积，也未清理文件。

## 1. 2026-08-18 历史审计结论

- `backend/uploads/` 已被 `.gitignore` 忽略，当前 `git ls-files` 中上传文件数量为 **0**。
- Git 对象库约 **4.34 MiB**，当前没有“上传文件被重复提交导致仓库持续膨胀”的证据。
- 本地上传目录共 **181** 个文件，约 **139.8 MB**。
- 按 SHA-256 内容摘要统计，共 **44** 组重复内容，涉及 **130** 个文件；若只保留每组一份，理论可节省约 **113.1 MB**。

## 2. 为什么暂不直接清理历史重复文件

数据库可能让不同业务记录引用不同文件名。即使文件内容相同，直接按哈希删除也可能造成作品、企划、橱窗、聊天附件或订单原图加载失败。因此本次不对已有上传文件做破坏性删除。

## 3. 当前策略与防增长边界

- 上传目录继续由 `.gitignore` 忽略，避免上传媒体进入 Git 历史；这是当前唯一启用的防 Git 膨胀措施。
- 新上传采用 UUID 独立文件名：相同内容也保留不同路径，便于未来独立管理；目前没有上传者/业务归属台账或引用计数，UUID 本身不提供授权，也不能保证某路径未被多个业务记录复用。
- 2026-08-18 曾短暂采用 SHA-256 内容寻址去重，评估后已撤回；原因是当前数据模型尚无引用计数和安全垃圾回收机制，不适合共享物理文件。
- 已有历史路径保持不变，不影响数据库记录和页面。

## 4. 后续安全清理方案

1. 汇总数据库全部图片字段和 JSON 内 `/uploads/` 引用。
2. 建立“路径 → 内容摘要 → 引用记录”清单；先识别重复内容与孤儿文件，不直接删除。
3. 若未来仍需去重，先实现引用计数、文件权限边界和事务化的引用迁移，再决定是否改用共享物理文件。
4. 仅删除确认零引用的文件；操作前备份数据库与上传目录。
5. 增加定期孤儿文件审计，禁止依据文件名、内容摘要或时间直接批量删除。

## 5. 2026-09-05 当前源码边界

- 本轮 `git ls-files backend/uploads` 仍无输出，且 `.gitignore` 保留 `backend/uploads/`；这不能证明 Git 历史从未出现媒体，也不包含前端展示资产。
- `UploadController` 通过 `artiv.upload.dir` 和 `artiv.upload.url-prefix` 定位文件；默认目录 `uploads/` 随后端工作目录解析，容器配置则为 `/app/uploads`。不得固定假设所有环境都使用 `backend/uploads/`。
- 单文件上限 5 MB，扩展名允许 png/jpg/jpeg/gif/webp；上传入口未验证实际图片内容、尺寸及上传者后续引用归属。
- `WebMvcConfig` 将上传目录作为公共静态资源暴露，登录拦截器仅覆盖 `/api/**`。订单详情隐藏原图地址不等于禁止直链下载，相关风险见 [未解决问题](未解决问题.md)。
- 订单交稿会派生水印预览，历史订单详情 GET 也可能补生成预览并回写数据库；审计时必须把原图、预览及所有版本引用纳入清单。
- 数据库基线脚本不备份上传文件；执行后续恢复或清理前，应停业务写入并保留同一时点的数据库和实际上传目录备份。
