# 上传文件存储审计

> 审计日期：2026-08-18  
> 审计范围：`backend/uploads` 与 Git 历史

## 1. 结论

- `backend/uploads/` 已被 `.gitignore` 忽略，当前 `git ls-files` 中上传文件数量为 **0**。
- Git 对象库约 **4.34 MiB**，当前没有“上传文件被重复提交导致仓库持续膨胀”的证据。
- 本地上传目录共 **181** 个文件，约 **139.8 MB**。
- 按 SHA-256 内容摘要统计，共 **44** 组重复内容，涉及 **130** 个文件；若只保留每组一份，理论可节省约 **113.1 MB**。

## 2. 为什么暂不直接清理历史重复文件

数据库可能让不同业务记录引用不同文件名。即使文件内容相同，直接按哈希删除也可能造成作品、企划、橱窗、聊天附件或订单原图加载失败。因此本次不对已有上传文件做破坏性删除。

## 3. 当前策略与防增长边界

- 上传目录继续由 `.gitignore` 忽略，避免上传媒体进入 Git 历史；这是当前唯一启用的防 Git 膨胀措施。
- 新上传采用 UUID 独立文件名：即使内容相同，也会保留不同路径，保证一条业务记录可独立替换、授权或删除，不与其他记录互相影响。
- 2026-08-18 曾短暂采用 SHA-256 内容寻址去重，评估后已撤回；原因是当前数据模型尚无引用计数和安全垃圾回收机制，不适合共享物理文件。
- 已有历史路径保持不变，不影响数据库记录和页面。

## 4. 后续安全清理方案

1. 汇总数据库全部图片字段和 JSON 内 `/uploads/` 引用。
2. 建立“路径 → 内容摘要 → 引用记录”清单；先识别重复内容与孤儿文件，不直接删除。
3. 若未来仍需去重，先实现引用计数、文件权限边界和事务化的引用迁移，再决定是否改用共享物理文件。
4. 仅删除确认零引用的文件；操作前备份数据库与上传目录。
5. 增加定期孤儿文件审计，禁止依据文件名、内容摘要或时间直接批量删除。
