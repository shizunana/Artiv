### 1.1 定向邀请系统交接结论

定向邀请现定义为“核心流程已实现，本轮优化已通过自动化、构建和关键页面验收”。现有接口、实体和前端页面都是继续开发的有效基线，不需要整体重写。

稳定规则：

- `mode=0` 为公开企划，`mode=1` 为单画师定向企划；定向企划不进入公开列表。
- 发布时选择唯一已认证画师，创建后不能撤回、追加或更换邀请对象。
- 待回应画师显示在应征画师区域并计数，但没有可下单 `application`。
- 接受只填写报价，创建有效应征并自动建立或复用合并私聊；会话系统提示与独立系统消息分别落库，正文相同。
- 拒绝必须填写原因，只发送系统消息，不建立会话；画师从应征区域移除，企划自动下架。
- 被拒绝企划可通过 `PUT /projects/{id}/publish-public?deadline=YYYY-MM-DD` 改为公开招募，不带入原拒绝画师；新日期至少为当前日期 +2 天。
- 接受后仍由企划方选定并按现有应征报价发单，不自动创建订单。
- “收到的邀请”支持全部/待处理/已接受/已拒绝/已失效筛选；包含定向邀请、邀请报价和带价邀请。
- 业务状态 `2` 与提醒页文案统一为“已拒绝”。
- 四种业务状态都可删除提醒；删除只设置当前画师的 `painter_hidden=1`，不影响邀请、有效应征、会话、系统消息、订单或履约。待处理提醒被隐藏也不等于拒绝。
- 定向邀请遵循企划截稿日期：日期当天仍可接受，过期后不能接受但仍可拒绝或隐藏；已接受形成的应征、会话和订单不受后续过期影响。

邀请相关迁移包括 `backend/sql/migrations/20260825_invitation_optimization.sql`（补齐历史接受通知和拒绝企划下架）以及 `backend/sql/migrations/20260825_invitation_reminder_inbox.sql`（提醒隐藏字段和索引），均可重复执行。完整文案、状态和验收证据见《邀请系统优化与验收》。

后续使用专用测试数据补做一次“新建邀请 → 实时首次通知 → 接受/拒绝 → 未读与跳转 → 转公开 → 后续发单”的双账号演示即可；这是发布前回归，不是整体重构任务。

### 1.2 公开企划主动邀请交接结论

- 已认证画师公开主页的“邀请”按钮打开邀请弹窗；只列出当前企划方本人正常上架、未过期的公开企划。
- `invitation_type=1` 为邀请报价：企划方不填价格，画师接受时只填写报价；`invitation_type=2` 为带价邀请：企划方发送至少 ¥50 的价格，画师接受时只确认该锁定价格。定向邀请也只填写报价；三类邀请均不要求画师输入应征说明，普通大厅应征表单不受影响。
- 两类公开邀请创建时只产生邀请记录和首次系统通知；接受后形成有效应征并自动建立或复用会话，同时写入会话系统提示与独立系统通知；任何一步都不直接创建订单。
- `application.quote_source=1` 表示带价邀请形成的锁价应征，服务端禁止画师更改报价；普通、邀请报价和大厅自主应征均为 `0`。
- 一个公开企划可以邀请多名画师，也可以保留同一画师的多条历史邀请；但目标画师已有当前有效应征时禁止继续邀请。
- 画师从大厅自主应征时，同企划、同画师全部待处理公开邀请同步为已接受并关联该应征，同时自动建立或复用会话。
- 公开邀请拒绝不下架企划。企划过期、主动下架、管理员下架或逻辑删除时，待处理公开邀请变为 `status=3 已失效`；旧邀请不会因后续延长日期而恢复。
- “收到的邀请”新增三类蓝色类型标签和“已失效”筛选；右侧小标题统一为“预算”，邀请报价显示固定文字，带价邀请显示邀请价格。
- 迁移 `backend/sql/migrations/20260826_public_project_invitations.sql` 会新增类型、价格、报价来源，删除阻止多邀请的唯一索引并建立普通查询索引；脚本可重复执行。
- 黑名单已开发并在邀请创建/接受时执行服务端双向校验；画师个人最低带价金额尚未开发，当前固定最低 ¥50。

完整产品口径与实现证据见《公开企划主动邀请画师开发计划》和《邀请系统优化与验收》；接口以《接口文档》第 8 节为准。

### 1.3 企划时间规则交接结论

- `project` 只保留 `deadline`；迁移 `20260825_project_deadline_unification.sql` 会回填空值、设为非空、删除 `recruit_deadline` 并补大厅索引，脚本可重复执行。
- 发布、编辑、主动下架后重新上架、被拒绝定向企划转公开，所选日期均必须至少为操作当日 +2 天，前后端都要校验。
- 截稿日期是日期语义：当天仍有效，只有 `deadline < 当前日期` 才算过期。
- 公开大厅由后端动态要求 `mode=0 / status=0 / deadline>=today`，不通过定时任务写“过期”状态。
- “我的企划”中自然过期显示“已过期”，用户主动下架显示“已下架”；重新上架必须重新选择日期，不能静默沿用或自动加 10 天。
- 过期只禁止新增应征和待处理邀请接受。已有应征仍可沟通和发单，已有会话及全部订单流程不受影响。
- 创建企划订单时将当时的 `deadline` 写入 `projectSnapshot`，供准时交稿率使用；之后编辑企划日期不得改变历史订单统计基准。

### 1.4 企划面板交接结论

- `/projects/{id}` 是统一浏览详情，继续展示公开应征画师；企划方管理入口统一为 `/dashboard/projects/{id}/panel`，只有发布者可以读取。
- 公开企划默认进入“应征画师”，定向企划默认进入唯一“邀请画师”；定向企划不允许追加邀请目标。
- “参与画师”不维护独立成员表，以当前企划产生的全部订单为事实来源，按画师分组并逐笔展示订单。终态订单同样属于参与历史。
- 参与订单查询必须同时限定 `employer_id=当前用户`、`source=project` 和 `project_id`，不能只相信前端路由 ID。
- 完整内容编辑使用 `PUT /projects/{id}/content`，只允许标题、描述、预算、标签/题材、类型、图片、稿件要求与创作阶段；有效应征、待处理/已接受邀请或任何历史订单都会锁定。
- 截稿日期、上下架和转公开使用专门接口：面板标题区提供日期弹窗，摘要区开关控制上下架/拒绝后转公开；删除入口在“我的企划”的 `ProjectDeleteDialog`。当前面板未使用 `ProjectManageDialog`，不能根据旧组件名推断入口。
- 共享组件为 `ProjectApplicantList.vue` 和 `OrderListItem.vue`；新增面板功能应继续复用，避免详情、面板和订单管理出现第三套卡片逻辑。

### 1.5 艺绘向导管理员测试版交接结论

- 当前入口只向正常管理员开放，复用 `/api/v1/admin/**` 的数据库角色与账号状态复验；不能仅靠前端隐藏按钮保护。
- 前端是右侧 `position: fixed` 非模态窗口，不锁定滚动、不拦截原页面点击、不因点击外部关闭；切页保持展开，收起或刷新后可恢复当前后端进程中的会话。

## 2. 管理员后台已完成范围（P0–P4）

### 2.1 第一阶段：管理员安全底座（P0，必须最先完成）

目标是先让后台“安全且可追溯”，再增加业务按钮。

- 后端统一保护 `/api/v1/admin/**`，普通用户手工请求也必须返回无权限。
- 管理员仅由初始化 SQL 或受控数据库操作创建，注册接口不得创建管理员。
- 新增管理员操作日志表和统一记录服务。
- 记录管理员、操作类型、目标、变更前后状态、原因、时间、请求标识等信息。
- 后台所有状态变更要求填写原因。
- 清除后台页面的静态假数据；请求失败时显示真实错误，不回退为模拟数据。
- 完成后台基础布局、菜单、加载态、空态、错误态和无权限页。

验收重点：普通用户访问管理员接口被后端拒绝；管理员状态变更能在只读审计日志中查询。

### 2.2 第二阶段：认证审核与用户管理（P1）

- 新增画师认证申请历史，不能只依赖 `user.cert_status`。
- 认证申请要求个人简介完整并至少有 4 件公开作品。
- 管理员可查看笔名、必填常用站、公开主页、作品、历史申请，以及认证资料修改前后的差异。
- 支持认证通过、带原因驳回和驳回后重新申请。
- 支持用户查询、永久封禁、限时封禁和带原因解封。
- 被封禁用户仍可登录、浏览公开页和历史记录，但不能创建新的交易关系。
- 封禁时取消该用户参与的全部未完成订单，全额退款下单方；橱窗订单按规则恢复库存。
- 封禁、退款、库存恢复、订单事件、系统通知和审计日志必须事务化或具备可恢复的幂等处理。
- 禁止管理员封禁自己；不得提供修改用户密码或角色的入口。
- 管理员用户详情已提供受控的测试资金工具：“发放资金”只能追加 `0.01～10000000.00`，“余额调整”把最终余额设为 `0.00～9999999999.99`。两者都必须由后端管理员鉴权、事务和用户行锁保护，要求操作原因并写入变更前后审计；只修改 `user.balance`，不得同步篡改订单、托管金额或伪造充值流水。

验收重点：认证不能被重复终结；重复封禁或任务重试不能重复退款、重复恢复库存。

### 2.3 第三阶段：订单争议与管理员仲裁（P2）

- 企划方和画师都可对企划订单或橱窗订单发起争议。
- 争议说明必填，可上传 1–9 张图片证据。
- 管理员详情展示来源快照、订单事件、全部阶段交付、水印预览、修改意见和双方争议材料。
- 不允许管理员浏览与争议订单无关的完整私聊。
- 首期仅实现两种仲裁：全额退款企划方、全额结算画师。
- 部分退款只预留枚举和接口扩展位，当前请求必须明确拒绝。
- 仲裁必须同时更新订单、托管金额、余额、事件、双方通知和审计日志。
- 所有资金操作必须使用数据库事务和幂等保护。

验收重点：同一争议只能终结一次；重复提交不会重复退款或重复给画师结算。

### 2.4 第四阶段：企划内容治理（P3）

- 首期只治理企划，不扩展作品和橱窗审核。
- 管理员可带原因强制违规下架和恢复企划。
- 平台治理状态与发布者自己的上架/下架状态分开保存。
- 违规下架后不在大厅展示、不接受新应征，发布者不能自行重新上架绕过治理。
- 既有应征仍可沟通和发单，已经建立的订单及来源详情不受影响。
- 下架和恢复都要通知发布者并记录审计日志。

### 2.5 第五阶段：概览与真实数据统计（P4）

- 后台概览首先展示待认证、待仲裁、封禁用户、违规下架企划和进行中订单。
- 展示今日新增用户、今日新增订单、今日完成订单和今日成交额。
- 展示最近 10 条管理员操作。
- 数据统计包含“用户需求洞察”和“平台运营”两个标签。
- 管理端页面默认统计 `2026-08-10` 至今天，支持近 7 天、近 30 天、全部历史和最长 366 天的自定义范围；前后端都禁止早于平台数据起始日、晚于今天或超过 1 年的查询。
- 日期按 `Asia/Hong_Kong` 计算，缺失日期由后端补 0。
- 统计由后端聚合查询完成，禁止前端拉取全部数据自行统计。
- 需求洞察覆盖类型、题材、预算、截稿周期、应征反馈、企划转化漏斗和供需缺口。
- 成交额只统计已经完成的订单，不做画师收入排行，不做 Excel/CSV 导出。
- 使用 MySQL `EXPLAIN` 验证聚合查询，并按实际结果补索引。

### 2.6 管理后台之后的收尾工作

按优先级继续处理：

1. 处理 CR-001–CR-005：用户实体读取边界、私有文件授权、默认凭据/密钥、橱窗购买幂等、普通私信准入。私信规则先结合产品意图确认；不要把已有页面入口视为服务端限制。
2. 处理应征更新、删除/屏蔽与建单竞争、封禁锁顺序并补真实数据库并发测试（CR-006、CR-007、CR-017）；其他业务口径类问题依报告第 5 节逐项确认。
3. 完成三类邀请双账号和企划治理演示、窄屏可用性、长列表、部署配置、备份、日志与上传目录持久化验收；管理员资金、评价终态和认证 E2E 已有记录，相关整改后按影响重跑。

## 3. 每次开发必须执行的基本操作

### 3.1 开始开发前

1. 确认工作目录是 Artiv 仓库根目录（当前 `D:\ProjectForGraduation\Artiv`），不要误改外层空 Git 仓库、`ArtivDemo` 或旧备份。
2. 执行 `git status --short`，识别并保留用户已有修改。
3. 查看 `git branch --show-current` 和最近提交，确认开发基线。
4. 阅读本次模块对应的设计文档、接口文档和未解决问题。
5. 涉及订单、余额、库存、认证或治理状态时，先写清状态流转、权限、事务和幂等规则，再编码。
6. 涉及删除、批量清理、重置数据库或历史重写时，必须先备份并取得用户明确授权。

当前仓库可能存在未提交文档和本机构建缓存；不得用 `git reset --hard`、`git checkout -- .` 等方式清除。

### 3.2 启动开发环境

1. 检查实际 MySQL 8 服务；`启动Artiv.cmd` 固定使用 `MySQL80-Artiv`，工具路径固定为 `D:\CodeTool\…`，使用前核对本机环境。
2. 仅在首次建库或明确需要重建为“三个初始用户、其余业务表为空”的环境时执行 `backend/sql/init.sql`；普通启动不要重复初始化数据库。
3. 后端：

```powershell
cd D:\ProjectForGraduation\Artiv\backend
mvn.cmd spring-boot:run
```

4. 前端：

```powershell
cd D:\ProjectForGraduation\Artiv\frontend
npm.cmd install
npm.cmd run dev
```

5. 默认地址：前端 `http://127.0.0.1:5173`，后端 `http://127.0.0.1:8080`。

PowerShell 下优先使用 `npm.cmd`。出现全部接口 500 时，先检查 MySQL 和后端是否启动，不要先改业务代码。

### 3.3 数据库开发规则

- 修改现有库时新增带日期的迁移 SQL，不依赖手工记忆执行步骤。
- 同步更新 `backend/sql/init.sql`，保证全新建库得到同一结构。
- 迁移必须考虑已有数据、默认值、唯一约束、索引和重复执行风险。
- 订单金额、余额、库存、认证和治理状态不能只在前端控制。
- 资金、库存和订单状态变更使用事务；重复请求使用状态条件、唯一业务记录或幂等键保护。
- 删除用户、订单、消息、交易和审计记录原则上使用逻辑删除或状态关闭，不物理破坏历史。
- `backend/uploads/` 为运行数据且已被 Git 忽略；不得直接清理可能仍被数据库引用的文件。

### 3.4 后端开发规则

- 接口统一使用 `/api/v1` 前缀和 `{ code, message, data }` 响应结构。
- Controller 只负责参数与身份入口，复杂业务放入 Service。
- 新接口使用 DTO，不直接接收可由用户伪造身份、金额、状态的实体。
- 权限必须在后端校验：当前用户身份、资源归属、管理员角色、订单参与方等。
- 状态流转必须显式校验，不能通过任意数字直接更新状态。
- 管理员关键操作、订单事件和系统通知必须与业务结果保持一致。
- 对异常分支返回明确业务错误，禁止吞掉异常或只在前端隐藏按钮。

### 3.5 前端开发规则

- 先在 `frontend/src/api/` 封装接口，再由页面调用；不要在页面散落 Axios 请求。
- 页面不保存伪造业务真相，金额、权限、状态和统计以服务端结果为准。
- 管理后台使用表格、筛选、详情抽屉/对话框，不复用消费者端瀑布流。
- 每个接口区域提供加载、空数据、失败重试和无权限状态。
- 状态文本优先复用 `utils/status.js`，类型和题材复用共享常量。
- 前端路由守卫只改善体验，不能替代后端鉴权。

### 3.6 验证顺序

业务代码变更至少执行以下检查；纯文档同步以逐份源码比对、链接/路径检查和 `git diff --check` 验证，不新增测试通过记录：

```powershell
cd D:\ProjectForGraduation\Artiv\backend
mvn.cmd test

cd D:\ProjectForGraduation\Artiv\frontend
npm.cmd run build
```

然后按风险补充人工或接口测试：

- 正常流程、参数非法、未登录、普通用户越权、资源不属于本人。
- 重复点击、重复请求、刷新页面、服务重启后的幂等性。
- 涉及余额时核对双方余额、订单金额、事件记录和重复请求前后差值。
- 涉及库存时核对下单扣减、取消/拒单恢复、重复操作不重复恢复。
- 涉及消息时使用两个账号验证实时到达、未读、系统通知和跳转。
- 涉及管理员时同时使用管理员和普通账号验证后端权限。
- 涉及日期统计时验证空日期补 0、跨日边界和自定义范围。

高风险功能不能只以“前端按钮可点击”作为通过标准。

### 3.7 文档和 Git 收尾

每次功能完成后按以下顺序收尾：

1. 先完成代码测试，并提交一次清晰的本地 Git 代码提交。
2. 更新 `docs/接口文档.md`：写明请求、响应、权限、业务规则，以及“已实现/未实现、已测试/未测试”。
3. 更新 `docs/项目进度.md`：追加本次功能、验证结果和真实提交哈希，不能删除旧记录。
4. 更新 `docs/测试.md`：记录测试环境、步骤、结果、遗留问题和测试数据。
5. 更新 `docs/未解决问题.md`：完成项勾选并写提交号；新问题按优先级追加，不能因暂时不做而删除。
6. 若改变订单、消息、主页或后台业务规则，同步更新相应设计文档。
7. 再检查 `git diff`、`git status`，确保未提交 `.m2/`、`uploads/`、日志、构建产物和敏感配置。
8. 文档修改可单独使用 `docs:` 提交，便于追溯。

默认只提交本地 Git。只有用户明确要求“推送远端”时，才执行远端推送；不得把每次本地提交自动上传 GitHub。

## 4. 管理后台实施时的文件落点建议

后端建议按现有分层新增或扩展：

- `controller/admin/`：管理员接口。
- `service/` 与 `service/impl/`：认证、封禁、仲裁、治理、统计和审计服务。
- `dto/admin/`：筛选、审核、封禁、仲裁、治理请求。
- `entity/`、`mapper/`：认证历史、争议、证据、管理员日志等实体和查询。
- `security/`：统一管理员鉴权与业务可用性校验。
- `backend/sql/`：迁移 SQL 与同步后的 `init.sql`。

前端建议落点：

- `frontend/src/api/admin.js`：后台接口封装；用户黑名单与举报封装在 `governance.js`。
- `frontend/src/views/admin/`：概览、认证、用户、仲裁、内容、统计和日志页面。
- `frontend/src/router/`：管理员路由与守卫。
- `frontend/src/utils/`：状态映射、日期和金额展示工具。

实际目录以现有项目结构为准，不为追求目录形式进行无意义的大范围重构。

## 5. 禁止事项与高风险边界

- 不允许普通注册创建管理员。
- 不允许仅依赖前端隐藏按钮保护管理员能力。
- 不允许绕过“发放资金 / 余额调整”专用接口直接在页面或通用用户更新接口修改余额；不允许管理员修改用户密码或角色。
- 不允许把管理员测试资金工具描述为真实充值、提现、扣款或支付，也不允许它反向改写既有订单、托管金额和结算历史。
- 不允许后台默认读取全部私聊。
- 不允许物理删除订单、资金、消息和审计历史。
- 不允许在没有事务与幂等保护时修改余额或退款。
- 不允许下架企划破坏既有应征、订单或订单来源详情。
- 不允许使用前端假数据冒充后台统计结果。
- 不允许未验证接口在文档中标记为“已测试”。
- 不允许只修改 `invitation.status` 就把邀请视为已接受或已拒绝。
- 不允许在邀请接受链路中留下“邀请已接受但无有效应征、无会话或无可追溯消息”的半完成状态。
- 不允许一个定向企划追加或更换第二名受邀画师，也不允许企划方撤回待处理邀请。
- 不允许接受邀请时只写会话提示或只写独立系统消息；两处必须使用同一固定文案分别落库并可追溯。
- 不允许拒绝邀请后建立邀请会话、保留有效应征或继续把该画师计入应征人数；企划必须自动下架，后续只能由企划方编辑为公开企划。
- 不允许沿用已归档文档中的“邀请整体重构”结论覆盖当前已验证实现；新增需求应先复现并记录真实差异。
- 不允许清理异常定向企划或历史邀请数据而不先备份、统计关联数据并给出修复方案。
- 不允许把“收到的邀请”删除实现成 `invitation.deleted=1`、拒绝邀请、取消会话或取消订单；只能隐藏当前画师提醒。
- 不允许未获用户明确指示就推送远端、改写 Git 历史或清理数据库。
