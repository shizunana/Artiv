### 1.1 定向邀请系统交接结论

定向邀请现定义为“核心流程已实现，本轮优化已通过自动化、构建和关键页面验收”。现有接口、实体和前端页面都是继续开发的有效基线，不需要整体重写。

稳定规则：

- `mode=0` 为公开企划，`mode=1` 为单画师定向企划；定向企划不进入公开列表。
- 发布时选择唯一已认证画师，创建后不能撤回、追加或更换邀请对象。
- 待回应画师显示在应征画师区域并计数，但没有可下单 `application`。
- 接受只填写报价，创建有效应征并自动建立或复用合并私聊；会话系统提示与独立系统消息分别落库，正文相同。
- 拒绝必须填写原因，只发送系统消息，不建立会话；画师从应征区域移除，企划自动下架。
- 被拒绝企划可通过 `PUT /projects/{id}/publish-public` 改为公开招募，不带入原拒绝画师。
- 接受后仍由企划方选定并按现有应征报价发单，不自动创建订单。

本轮迁移为 `backend/sql/migrations/20260825_invitation_optimization.sql`，用于补齐历史接受通知和历史拒绝企划下架状态，可重复执行。完整文案、状态和验收证据见《邀请系统优化与验收》。

后续使用专用测试数据补做一次“新建邀请 → 实时首次通知 → 接受/拒绝 → 未读与跳转 → 转公开 → 后续发单”的双账号演示即可；这是发布前回归，不是整体重构任务。

## 2. 管理员后台已完成范围（P0–P4）

### 2.1 第一阶段：管理员安全底座（P0，必须最先完成）

目标是先让后台“安全且可追溯”，再增加业务按钮。

- 后端统一保护 `/api/v1/admin/**`，普通用户手工请求也必须返回无权限。
- 管理员仅由初始化 SQL 或受控数据库操作创建，注册接口不得创建管理员。
- 新增管理员操作日志表和统一记录服务。
- 记录管理员、操作类型、目标、变更前后状态、原因、时间、请求标识等信息。
- 后台所有状态变更要求填写原因。
- 清除后台页面的静态假数据；请求失败时显示真实错误，不回退为模拟数据。
- 完成后台基础布局、菜单、加载态、空态、错误态和无权限页。

验收重点：普通用户访问管理员接口被后端拒绝；管理员状态变更能在只读审计日志中查询。

### 2.2 第二阶段：认证审核与用户管理（P1）

- 新增画师认证申请历史，不能只依赖 `user.cert_status`。
- 认证申请要求个人简介完整并至少有 4 件公开作品。
- 管理员可查看笔名、必填常用站、公开主页、作品、历史申请，以及认证资料修改前后的差异。
- 支持认证通过、带原因驳回和驳回后重新申请。
- 支持用户查询、永久封禁、限时封禁和带原因解封。
- 被封禁用户仍可登录、浏览公开页和历史记录，但不能创建新的交易关系。
- 封禁时取消该用户参与的全部未完成订单，全额退款下单方；橱窗订单按规则恢复库存。
- 封禁、退款、库存恢复、订单事件、系统通知和审计日志必须事务化或具备可恢复的幂等处理。
- 禁止管理员封禁自己；不得提供任意改余额、密码或角色的入口。

验收重点：认证不能被重复终结；重复封禁或任务重试不能重复退款、重复恢复库存。

### 2.3 第三阶段：订单争议与管理员仲裁（P2）

- 企划方和画师都可对企划订单或橱窗订单发起争议。
- 争议说明必填，可上传 1–9 张图片证据。
- 管理员详情展示来源快照、订单事件、全部阶段交付、水印预览、修改意见和双方争议材料。
- 不允许管理员浏览与争议订单无关的完整私聊。
- 首期仅实现两种仲裁：全额退款企划方、全额结算画师。
- 部分退款只预留枚举和接口扩展位，当前请求必须明确拒绝。
- 仲裁必须同时更新订单、托管金额、余额、事件、双方通知和审计日志。
- 所有资金操作必须使用数据库事务和幂等保护。

验收重点：同一争议只能终结一次；重复提交不会重复退款或重复给画师结算。

### 2.4 第四阶段：企划内容治理（P3）

- 首期只治理企划，不扩展作品和橱窗审核。
- 管理员可带原因强制违规下架和恢复企划。
- 平台治理状态与发布者自己的上架/下架状态分开保存。
- 违规下架后不在大厅展示、不接受新应征，发布者不能自行重新上架绕过治理。
- 既有应征仍可沟通和发单，已经建立的订单及来源详情不受影响。
- 下架和恢复都要通知发布者并记录审计日志。

### 2.5 第五阶段：概览与真实数据统计（P4）

- 后台概览首先展示待认证、待仲裁、封禁用户、违规下架企划和进行中订单。
- 展示今日新增用户、今日新增订单、今日完成订单和今日成交额。
- 展示最近 10 条管理员操作。
- 数据统计包含“用户需求洞察”和“平台运营”两个标签。
- 默认近 7 天，支持近 30 天和最长 366 天的自定义范围。
- 日期按 `Asia/Hong_Kong` 计算，缺失日期由后端补 0。
- 统计由后端聚合查询完成，禁止前端拉取全部数据自行统计。
- 需求洞察覆盖类型、题材、预算、截稿周期、应征反馈、企划转化漏斗和供需缺口。
- 成交额只统计已经完成的订单，不做画师收入排行，不做 Excel/CSV 导出。
- 使用 MySQL `EXPLAIN` 验证聚合查询，并按实际结果补索引。

### 2.6 管理后台之后的收尾工作

按优先级继续处理：

1. 补齐企划招募截止的列表过滤和自动状态处理。
2. 使用专用数据完成定向邀请完整双账号演示，重点观察首次通知、两个消息分区未读、转公开和后续发单。
3. 按《测试.md》完成管理员认证、仲裁、封禁退款、企划治理，以及评价双方提交和申诉批准/驳回 E2E。
4. 完成移动端适配及 Demo 上线前配置、备份、日志和上传目录持久化检查。

## 3. 每次开发必须执行的基本操作

### 3.1 开始开发前

1. 确认工作目录是 `G:\ProjectForGraduation\Artiv`，不要误改 `ArtivDemo` 或旧备份。
2. 执行 `git status --short`，识别并保留用户已有修改。
3. 查看 `git branch --show-current` 和最近提交，确认开发基线。
4. 阅读本次模块对应的设计文档、接口文档和未解决问题。
5. 涉及订单、余额、库存、认证或治理状态时，先写清状态流转、权限、事务和幂等规则，再编码。
6. 涉及删除、批量清理、重置数据库或历史重写时，必须先备份并取得用户明确授权。

当前仓库可能存在未提交文档和本机构建缓存；不得用 `git reset --hard`、`git checkout -- .` 等方式清除。

### 3.2 启动开发环境

1. 检查并启动 MySQL 8 的 `MySQL80` 服务。
2. 仅在需要重建演示数据时执行 `backend/sql/init.sql`；普通启动不要重复初始化数据库。
3. 后端：

```powershell
cd G:\ProjectForGraduation\Artiv\backend
mvn.cmd spring-boot:run
```

4. 前端：

```powershell
cd G:\ProjectForGraduation\Artiv\frontend
npm.cmd install
npm.cmd run dev
```

5. 默认地址：前端 `http://127.0.0.1:5173`，后端 `http://127.0.0.1:8080`。

PowerShell 下优先使用 `npm.cmd`。出现全部接口 500 时，先检查 MySQL 和后端是否启动，不要先改业务代码。

### 3.3 数据库开发规则

- 修改现有库时新增带日期的迁移 SQL，不依赖手工记忆执行步骤。
- 同步更新 `backend/sql/init.sql`，保证全新建库得到同一结构。
- 迁移必须考虑已有数据、默认值、唯一约束、索引和重复执行风险。
- 订单金额、余额、库存、认证和治理状态不能只在前端控制。
- 资金、库存和订单状态变更使用事务；重复请求使用状态条件、唯一业务记录或幂等键保护。
- 删除用户、订单、消息、交易和审计记录原则上使用逻辑删除或状态关闭，不物理破坏历史。
- `backend/uploads/` 为运行数据且已被 Git 忽略；不得直接清理可能仍被数据库引用的文件。

### 3.4 后端开发规则

- 接口统一使用 `/api/v1` 前缀和 `{ code, message, data }` 响应结构。
- Controller 只负责参数与身份入口，复杂业务放入 Service。
- 新接口使用 DTO，不直接接收可由用户伪造身份、金额、状态的实体。
- 权限必须在后端校验：当前用户身份、资源归属、管理员角色、订单参与方等。
- 状态流转必须显式校验，不能通过任意数字直接更新状态。
- 管理员关键操作、订单事件和系统通知必须与业务结果保持一致。
- 对异常分支返回明确业务错误，禁止吞掉异常或只在前端隐藏按钮。

### 3.5 前端开发规则

- 先在 `frontend/src/api/` 封装接口，再由页面调用；不要在页面散落 Axios 请求。
- 页面不保存伪造业务真相，金额、权限、状态和统计以服务端结果为准。
- 管理后台使用表格、筛选、详情抽屉/对话框，不复用消费者端瀑布流。
- 每个接口区域提供加载、空数据、失败重试和无权限状态。
- 状态文本优先复用 `utils/status.js`，类型和题材复用共享常量。
- 前端路由守卫只改善体验，不能替代后端鉴权。

- 重复点击、重复请求、刷新页面、服务重启后的幂等性。

- 涉及库存时核对下单扣减、取消/拒单恢复、重复操作不重复恢复。
- 涉及消息时使用两个账号验证实时到达、未读、系统通知和跳转。
- 涉及管理员时同时使用管理员和普通账号验证后端权限。

## 4. 管理后台实施时的文件落点建议

后端建议按现有分层新增或扩展：

- `controller/admin/`：管理员接口。
- `service/` 与 `service/impl/`：认证、封禁、仲裁、治理、统计和审计服务。
- `dto/admin/`：筛选、审核、封禁、仲裁、治理请求。
- `entity/`、`mapper/`：认证历史、争议、证据、管理员日志等实体和查询。
- `security/`：统一管理员鉴权与业务可用性校验。
- `backend/sql/`：迁移 SQL 与同步后的 `init.sql`。

前端建议落点：

- `frontend/src/api/admin/`：后台接口封装。
- `frontend/src/views/admin/`：概览、认证、用户、仲裁、内容、统计和日志页面。
- `frontend/src/router/`：管理员路由与守卫。
- `frontend/src/utils/`：状态映射、日期和金额展示工具。

实际目录以现有项目结构为准，不为追求目录形式进行无意义的大范围重构。

## 5. 禁止事项与高风险边界

- 不允许普通注册创建管理员。
- 不允许仅依赖前端隐藏按钮保护管理员能力。
- 不允许管理员任意修改余额、密码或角色。
- 不允许后台默认读取全部私聊。
- 不允许物理删除订单、资金、消息和审计历史。
- 不允许在没有事务与幂等保护时修改余额或退款。
- 不允许下架企划破坏既有应征、订单或订单来源详情。
- 不允许使用前端假数据冒充后台统计结果。
- 不允许未验证接口在文档中标记为“已测试”。
- 不允许只修改 `invitation.status` 就把邀请视为已接受或已拒绝。
- 不允许在邀请接受链路中留下“邀请已接受但无有效应征、无会话或无可追溯消息”的半完成状态。
- 不允许一个定向企划追加或更换第二名受邀画师，也不允许企划方撤回待处理邀请。
- 不允许接受邀请时只写会话提示或只写独立系统消息；两处必须使用同一固定文案分别落库并可追溯。
- 不允许拒绝邀请后建立邀请会话、保留有效应征或继续把该画师计入应征人数；企划必须自动下架，后续只能由企划方编辑为公开企划。
- 不允许沿用已归档文档中的“邀请整体重构”结论覆盖当前已验证实现；新增需求应先复现并记录真实差异。
- 不允许清理异常定向企划或历史邀请数据而不先备份、统计关联数据并给出修复方案。
- 不允许未获用户明确指示就推送远端、改写 Git 历史或清理数据库。

## 6. 交接验收清单

下一位开发者开始编码前，应能回答：

- [ ] 当前工作目录、分支和未提交修改是什么？
- [ ] 本次功能对应哪份设计文档和哪条未解决问题？
- [ ] 谁能操作该功能，后端如何校验权限？
- [ ] 会改变哪些状态、余额、库存、消息和审计记录？
- [ ] 是否需要事务、幂等保护和数据库迁移？
- [ ] 正常、越权、重复请求和异常恢复如何测试？
- [ ] 完成后需要更新哪些接口、进度、测试和业务文档？
- [ ] 本次只做本地 Git，还是用户已经明确要求推送远端？
- [ ] 若涉及邀请，是否证明“邀请、应征、会话、系统通知、未读”在成功、失败和重复请求下保持一致？
- [ ] 若涉及定向企划，是否验证非创建者、非受邀者无法通过数字 ID 或关联接口读取内容？

如果这些问题无法回答，应先补设计或向项目负责人确认，不要直接修改核心状态机。

## 7. 建议立即开始的第一项工作

下一项功能工作优先处理企划招募截止的列表过滤和自动状态。定向邀请不再安排整体重构，只在使用专用数据完成完整双账号演示时修复能够稳定复现的差异；验收脚本见《邀请系统优化与验收》。之后继续管理员、评价和上线前高风险回归。创建橱窗的后端认证门槛属于已完成功能，不应在这些收尾任务中顺带改写。
