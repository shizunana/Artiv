# 艺绘（Artiv）黑名单与举报开发计划

> 状态：已开发并完成自动化与关键页面验收  
> 最近更新：2026-08-26  
> 当前入口：公开用户主页“更多操作”提供“加入黑名单 / 解除屏蔽 / 举报用户”；账户设置提供黑名单管理；管理员后台提供用户举报治理  
> 实施版本：`v0.8.13-beta`

## 1. 功能目标

黑名单用于阻止两个用户继续建立新的关注、应征、邀请、下单和私信关系；举报用于把违规用户或内容提交给管理员处理。

两项能力必须分开：

- 加入黑名单不等于举报，不会自动生成举报记录；
- 举报不等于加入黑名单，不会自动阻断双方关系；
- 黑名单是用户自己的关系设置，举报是平台治理流程；
- 黑名单不能破坏已经成立的订单、结算、评价或争议记录。

按两个阶段设计并在本版本一并落地：

1. **第一阶段：用户黑名单**——公开主页加入/解除、账户设置管理、核心互动服务端拦截；
2. **第二阶段：举报治理**——举报表单、证据、管理员审核、通知和审计。

## 2. 黑名单产品口径

### 2.1 关系模型

黑名单按“用户”建立，而不是按企划方/画师身份分别建立。

例如用户 A 在画师主页屏蔽用户 B 后，B 的企划方身份和画师身份都属于同一个被屏蔽账号，不允许通过切换工作台绕过限制。

数据库保存有方向的关系：

```text
blocker_id  屏蔽发起人
blocked_id  被屏蔽用户
```

虽然关系有方向，但核心互动采用**双向阻断**：只要 A 屏蔽 B 或 B 屏蔽 A，双方都不能新建合作或普通私信。

### 2.2 影响范围

| 场景 | 加入黑名单后的规则 |
| --- | --- |
| 查看公开主页 | 仍可查看；账户设置黑名单中的“查看主页”因此始终有明确用途 |
| 查看公开作品、企划和橱窗 | 首期不从公共大厅隐藏，避免把屏蔽关系变成内容权限系统 |
| 关注 | 双方不能重新关注；加入黑名单时删除双方已有关注关系 |
| 公开企划邀请 | 双方任一方向存在黑名单关系时禁止邀请报价和带价邀请 |
| 定向邀请 | 双方任一方向存在黑名单关系时禁止创建和接受 |
| 公开企划应征 | 被屏蔽画师不能应征对方企划，屏蔽对方的画师也不能应征其企划 |
| 橱窗下单 | 双方任一方向存在黑名单关系时禁止新下单 |
| 主动建立会话 | 禁止发起新的应征沟通、邀请会话和普通私聊 |
| 已有会话 | 历史消息继续可见；不存在进行中订单时，普通文字和图片输入区禁用 |
| 已完成订单与评价 | 永久保留，不删除、不隐藏、不改分 |
| 解除屏蔽 | 只恢复未来互动能力，不自动恢复关注、邀请、应征或会话状态 |

### 2.3 进行中订单保护

双方存在以下任意非终态订单时，禁止加入黑名单：

- 待接单；
- 进行中；
- 待验收；
- 争议中。

提示文案：

> 您与该用户仍有未结束的订单，请先完成交易或售后处理后再加入黑名单。

原因是 Artiv 的消息会话按双方用户合并。如果允许合作中途屏蔽并禁止消息，会妨碍接单、交付、验收和争议举证；如果允许消息继续发送，又会让黑名单语义不一致。禁止在非终态订单期间屏蔽是首期最稳定的规则。

### 2.4 待处理业务关系

加入黑名单成功时，由同一事务执行：

1. 删除双方关注关系；
2. 将双方之间尚未响应的邀请改为“已失效”；
3. 将尚未形成订单的有效应征关系结束，`ended_reason` 记录为 `BLOCKED`；
4. 保留邀请、应征和会话历史，不物理删除业务记录；
5. 不向被屏蔽用户发送“您已被加入黑名单”的系统消息。

解除屏蔽后不自动恢复上述关系，需要双方重新关注、应征或邀请。

## 3. 用户页面设计

### 3.1 公开主页“更多操作”

当前占位菜单改为真实状态菜单：

| 当前状态 | 菜单项 |
| --- | --- |
| 未屏蔽 | 加入黑名单、举报 |
| 已由本人屏蔽 | 解除屏蔽、举报 |
| 对方屏蔽了本人 | 不泄露对方操作，只在发起受限互动时提示“当前无法与该用户互动” |

“加入黑名单”二次确认：

> 加入黑名单后，双方将无法关注、发送普通消息或建立新的应征、邀请和订单。历史消息与已经完成的交易记录不会删除。确定继续吗？

操作成功只向当前用户显示提示，不通知对方。

### 3.2 账户设置新增“黑名单”

在 `/settings` 左侧菜单“身份认证”下方新增第三项：

```text
黑名单
管理已屏蔽的用户
```

继续复用同一页面和查询参数：

```text
/settings?section=blocks
```

不新增脱离账户设置的新路由。

### 3.3 黑名单管理页面

页面标题：**黑名单**  
页面说明：**管理您已屏蔽的用户。解除后，双方可以重新发起关注和合作。**

每条记录展示：

- 头像；
- 用户昵称；
- 认证画师/企划方等可用公开标识；
- 加入黑名单时间；
- **查看主页**；
- **解除屏蔽**。

按钮规则：

- “查看主页”使用普通蓝色文字按钮，进入 `/profiles/{userId}`；认证画师默认打开画师视角，否则打开企划方视角；
- “解除屏蔽”使用危险色文字按钮；
- 解除前二次确认：`解除后，双方可以重新关注、发送消息并发起新的合作。确定解除屏蔽吗？`；
- 解除成功后当前记录立即从列表移除；
- 不自动恢复此前被删除的关注或已失效的邀请/应征。

列表按加入时间倒序，每页 10 条；只有超过一页时显示分页。

空状态：

> 暂无已屏蔽用户

如果目标账号已经注销或删除，记录显示“已注销用户”，禁用“查看主页”，仍允许“解除屏蔽”。

## 4. 黑名单数据设计

计划新增 `user_block`：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `blocker_id` | BIGINT | 屏蔽发起用户 |
| `blocked_id` | BIGINT | 被屏蔽用户 |
| `created_at` | DATETIME | 加入黑名单时间 |

约束与索引：

```text
UNIQUE KEY uk_user_block (blocker_id, blocked_id)
KEY idx_user_block_blocker_created (blocker_id, created_at)
KEY idx_user_block_blocked (blocked_id)
```

黑名单关系解除时物理删除关系记录。业务幂等规则：

- 重复加入返回当前 `blocked=true`，不生成重复记录；
- 重复解除返回当前 `blocked=false`，不报服务器错误；
- 数据库唯一键兜底并发重复加入。

## 5. 黑名单接口设计

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| GET | `/api/v1/blocks/users?page=1&size=10` | 查询本人黑名单 |
| GET | `/api/v1/blocks/users/{userId}/status` | 查询本人是否已屏蔽目标用户 |
| PUT | `/api/v1/blocks/users/{userId}` | 加入黑名单 |
| DELETE | `/api/v1/blocks/users/{userId}` | 解除屏蔽 |

列表接口返回摘要 DTO，不直接返回关系实体或目标用户私密资料。

建议状态响应：

```json
{
  "blocked": true
}
```

服务端统一提供：

```java
boolean isEitherBlocked(Long firstUserId, Long secondUserId)
```

关注、邀请、应征、橱窗下单和消息服务必须调用该方法，不能只依靠前端隐藏按钮。

## 6. 举报功能设计

### 6.1 举报目标

原预留范围包括：

- 用户；
- 作品；
- 企划；
- 橱窗。

第一期只开放**举报用户**，入口为公开主页“更多操作 → 举报”。作品、企划和橱窗留到相应治理能力完善后再开放，不能只收集举报却没有处置手段。

### 6.2 用户举报表单

表单字段：

- 举报类型：骚扰辱骂、欺诈风险、冒充他人、违规内容、其他；
- 详细说明：必填，10–500 字；
- 图片证据：选填，最多 6 张，复用现有上传接口；
- 被举报用户、举报人和提交时间由服务端确定。

提交成功文案：

> 举报已提交，平台会根据您提供的信息进行核查。

举报后不自动加入黑名单，表单底部可提示用户按需单独执行屏蔽。

### 6.3 举报聚合与计数规则

举报不按每次提交生成一条独立后台案件，而是按“被举报用户”聚合为一条案件：

```text
用户 B 被用户 A 举报 → B 的案件显示 1 人举报
用户 B 又被用户 C 举报 → 同一案件显示 2 人举报
用户 A 重复举报用户 B → 仍显示 2 人举报，不重复计数
```

第一期同一举报人对同一目标账号永久只计一次。重复提交返回当前案件已记录，不新增举报人数，也不重复保存相同提交。管理员列表按聚合案件展示，并明确显示不同举报人数。

已处理或已驳回的案件收到新的不同举报人提交时，案件重新进入“待处理”，原处理结论保留在管理员审计记录中，不能覆盖历史结论。

计划新增三张表：

#### `report_case`：聚合案件

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `target_type` | 第一期固定为 `USER`，为后续扩展保留类型 |
| `target_id` | 被举报用户 ID |
| `target_snapshot` | 首次提交时目标昵称等 JSON 快照 |
| `status` | `0 待处理 / 1 已处理 / 2 已驳回` |
| `admin_id` | 最近处理管理员 |
| `decision_reason` | 最近处理结论 |
| `handled_at` | 最近处理时间 |
| `created_at / updated_at` | 创建与更新时间 |

约束：`UNIQUE KEY uk_report_case_target (target_type, target_id)`。

举报人数优先通过 `report_submission` 中不同举报人记录实时统计，不单独维护容易失真的可写计数字段。

#### `report_submission`：举报人提交

| 字段 | 说明 |
| --- | --- |
| `id` | 主键 |
| `case_id` | 所属聚合案件 |
| `reporter_id` | 举报人 |
| `category` | 举报分类 |
| `reason` | 举报说明 |
| `created_at` | 首次举报时间 |

约束：`UNIQUE KEY uk_report_submission_reporter (case_id, reporter_id)`，确保同一举报人只计一次。

#### `report_evidence`：举报证据

证据图片保存为 `report_evidence(submission_id, image_url, sort_order, created_at)`，与具体举报人的说明绑定，管理员可以分别查看每名举报人的理由和证据。

### 6.4 举报接口与后台

| 方法 | 路径 | 用途 |
| --- | --- | --- |
| POST | `/api/v1/reports` | 提交用户举报；同一举报人重复提交不增加人数 |
| GET | `/api/v1/admin/reports` | 管理员分页查询聚合案件和举报人数 |
| GET | `/api/v1/admin/reports/{id}` | 管理员查看全部举报人说明和证据 |
| PUT | `/api/v1/admin/reports/{id}/resolve` | 处理或驳回 |

管理员后台新增“举报管理”，第一期支持状态、时间、被举报用户和关键词筛选。列表每个被举报用户只显示一条聚合案件，并展示“1 人举报 / 2 人举报 / N 人举报”。处理必须填写说明并写入 `admin_action_log`；没有新增举报人的终态案件不得重复处理。

用户侧第一期不提供“我的举报”列表，也不发送处理结果系统消息。提交成功只显示当前页面成功提示；被举报用户不会因为收到举报而获得通知。

管理员处理举报时只记录处理结论和审计，不自动封禁用户，也不自动下架企划或内容。确需处罚时，由管理员继续手动使用现有用户封禁、企划治理等真实治理功能；这些治理操作沿用各自已有通知和审计规则。

## 7. 安全与权限边界

1. 不能屏蔽自己、举报自己；
2. 被屏蔽用户不能查询是谁屏蔽了自己；
3. 黑名单列表只能读取当前登录人的关系；
4. 所有互动限制必须由服务端按两个用户 ID 双向校验；
5. 管理员不能借普通黑名单接口绕过后台权限模型；
6. 举报目标必须真实存在，目标 ID、举报人和处理人不能由前端伪造；
7. 举报证据继续使用上传格式、数量和路径安全校验；
8. 黑名单和举报都不能删除历史订单、余额流水、评价、争议、消息或管理员审计。

## 9. 测试与验收

### 9.1 黑名单自动化

1. 不能屏蔽自己；
2. 重复加入和重复解除幂等；
3. 数据库并发下只有一条关系；
4. 任一方向存在关系时，关注、邀请、应征、下单和普通私信均被拒绝；
5. 加入后双方关注删除，待处理邀请失效，有效未下单应征结束；
6. 存在非终态订单时拒绝加入黑名单；
7. 已完成订单、评价、争议和历史消息不变化；
8. 解除后不恢复关注、邀请或应征；
9. 黑名单分页只返回本人数据，不泄露他人关系；
10. 已注销目标仍可从列表解除。

### 9.2 页面 E2E

使用两个专用账号验证：

```text
A 查看 B 主页
→ 加入黑名单
→ A 的账户设置出现 B
→ 双方关注、邀请、应征、下单和普通消息均被服务端拒绝
→ 历史主页、消息和完成订单仍可查看
→ A 在黑名单点击“查看主页”正常
→ A 点击“解除屏蔽”
→ 记录消失，双方可重新建立关系
```

举报功能自动化验收覆盖：

1. 举报功能第一期只允许举报用户，不能伪造作品、企划或橱窗目标类型；
2. 不同举报人对同一用户只生成一条聚合案件，人数按不同举报人正确累计；
3. 同一举报人重复提交不增加人数、不生成重复记录；
4. 管理员可以查看每名举报人的说明与证据；
5. 已处理案件收到新的不同举报人提交后重新进入待处理，历史处理审计不丢失；

7. 用户侧不存在“我的举报”入口，处理完成后不发送结果通知；
8. 证据上传数量、格式、路径权限与管理员审计符合安全要求。

## 10. 已确认产品口径

1. 双方存在非终态订单时禁止加入黑名单；
2. 加入黑名单后，双方待处理邀请统一变为“已失效”；
3. 尚未形成订单的有效应征统一结束，`ended_reason=BLOCKED`；
4. 公共大厅内容和公开主页仍可查看，只禁止双方继续互动；
5. 黑名单按整个用户账号生效，不能通过切换企划方/画师身份绕过；
6. 举报第一期只支持举报用户，作品、企划和橱窗延后；
7. 举报按被举报账号聚合，不同举报人累计人数，同一举报人只计一次；
8. 用户侧不提供“我的举报”，也不反馈管理员处理结果；
9. 管理员只记录举报结论，处罚继续手动使用现有用户封禁和企划治理功能。
