# 收藏关注设计

> 文档状态：已实现，已完成自动化、接口与浏览器回归
> 制定日期：2026-08-24
> 适用范围：画师公开主页、作品广场、橱窗详情、企划方与画师工作台共用侧栏
> 相关文档：《主页功能设计计划》《项目开发计划书》《后续开发交接说明》

## 1. 目标

本次功能补齐三类用户关系：

1. 关注画师：在其他用户的画师主页关注或取消关注。
2. 收藏作品：在作品详情弹窗收藏或取消收藏作品。
3. 收藏橱窗：在橱窗详情收藏或取消收藏橱窗。

企划方与画师工作台共用“画师收藏、作品收藏、橱窗收藏”三个入口。入口不放进某一方的工作台首页主内容，而是在两种工作台左侧主菜单卡片下方显示一张独立快捷卡，切换工作台后仍然存在。

公开画师主页同时完成“邀请、关注、更多操作”的按钮设计。邀请复用现有定向邀请业务；黑名单和举报只保留后续扩展契约，本期不实现实际业务。

## 2. 产品边界

### 2.1 本期实现

- 关注、取消关注画师，并查询当前关注状态。
- 收藏、取消收藏作品和橱窗，并查询当前收藏状态。
- 分页查看自己的关注与收藏内容。
- 企划方与画师工作台的共用侧栏显示三个收藏入口，并进入同一套收藏数据。
- 画师主页的邀请按钮打开企划选择对话框，选择企划后复用现有定向邀请接口。
- 未登录用户点击关系按钮时跳转登录，并保留原页面返回地址。
- 目标下架、隐藏、删除或失效后，不在用户收藏列表中继续公开展示。

### 2.2 本期不实现

- 不做关注动态、关注推荐、粉丝排行或关注数量公开展示。
- 不做作品点赞；收藏是用户自己的私密整理行为，不等同于点赞。
- 不做企划收藏。
- 不向被关注者发送系统通知，避免本期引入新的通知噪音和隐私口径。
- 不做收藏分组、收藏备注、批量转移和导出。
- 不实现黑名单和举报的数据库、后台处置页及实际请求接口。
- 不因收藏或关注关系改变作品、橱窗、画师大厅的公开排序。

## 3. 核心业务规则

### 3.1 身份与权限

- `user.role` 只决定默认工作台入口，不作为关注、收藏或邀请的能力判断。
- “关注画师”的目标必须是正常、未删除且 `cert_status = 2` 的认证画师。
- 发送邀请的目标也必须是正常、未删除且 `cert_status = 2` 的认证画师，继续由现有邀请服务做最终校验。
- 正常登录账号均可关注画师、收藏作品和收藏橱窗，不要求注册时选择画师身份。
- 被封禁账号仍可登录和浏览，但不得创建新的关注、收藏或邀请关系；允许取消自己已有的关注和收藏。
- 不允许关注自己；本人画师主页不显示“关注、邀请、更多操作”。
- 本人作品和本人橱窗不显示收藏按钮，避免产生无意义的自收藏数据。

### 3.2 幂等和并发

- 同一用户对同一目标最多只有一条有效关系。
- 关注或收藏接口重复调用返回当前已生效状态，不重复插入数据。
- 取消接口重复调用仍返回未关注或未收藏，不抛出不存在异常。
- 数据库唯一约束是防止并发重复数据的最终边界，不能只依赖前端按钮禁用。
- 前端请求期间禁用当前按钮；响应后以服务端返回状态为准，不使用仅本地保存的伪状态。

### 3.3 目标失效

- 作品仅在 `visibility = 1`、`deleted = 0` 时可被收藏和显示。
- 橱窗仅在 `status = 1`、`deleted = 0` 时可被收藏和显示。
- 画师仅在账号正常、未删除且 `cert_status = 2` 时可被关注和显示。
- 目标失效时不强制删除历史关系；列表查询通过目标状态过滤，避免泄露隐藏或删除内容。
- 目标重新恢复公开后，原关系可以重新显示。用户仍可通过取消接口移除自己的关系。

## 4. 页面与按钮设计

### 4.1 画师公开主页

位置：`/profiles/{userId}?role=painter` 顶部身份信息右侧。

从左到右排列：

1. `+ 关注`：蓝色主按钮；关注后变为浅色或描边状态的 `已关注`，再次点击取消关注。
2. `邀请`：中性描边按钮，视觉层级低于关注；替代参考页面中的“发消息”。
3. `···`：无文字的更多按钮；菜单预留“加入黑名单”和“举报”。

显示规则：

- 本人主页隐藏三个按钮。
- 未认证画师主页不显示关注和邀请，避免对不具备画师交易资格的账号建立画师关系。
- 未登录时按钮可见；点击后进入登录页，登录成功返回原主页。
- 关注请求失败时保持原状态，并显示服务端错误，不先永久改变按钮状态。
- 本期更多菜单可展示两个禁用项并标注“暂未开放”，不得弹出成功提示或伪造结果。

### 4.2 邀请画师

邀请不是私信，也不能脱离企划单独存在。

点击“邀请”后：

1. 打开“选择邀请企划”对话框。
2. 展示当前账号拥有、仍在招募、未违规下架、未过招募截止时间且 `mode = 1` 的定向企划。
3. 用户选择一个企划，可填写最多 500 字邀请说明。
4. 提交时复用现有 `POST /api/v1/invitations`，请求仍为 `projectId + painterId + message`。
5. 若没有可邀请企划，显示空态并提供“发布定向企划”入口。
6. 已存在同企划、同画师的待处理邀请时，显示后端返回的重复邀请提示。

首期可用现有 `GET /api/v1/projects/mine` 加载本人企划并在对话框筛选；是否新增“可邀请企划”专用查询接口，应在实现时根据分页和字段完整性决定。无论前端如何筛选，最终资格必须继续由后端邀请服务校验。

### 4.3 作品详情弹窗

位置：`/works` 作品详情弹窗头部操作区，靠近“进入主页”按钮。

- 使用线框爱心图标加“收藏”文本，不只依赖颜色表达状态。
- 未收藏：线框爱心 + `收藏`。
- 已收藏：实心爱心 + `已收藏`，使用项目蓝色强调。
- 点击只切换收藏状态，不关闭弹窗、不重新加载作品大图。
- 作品所有者查看自己的作品时隐藏收藏按钮。
- 当前禁用的“举报作品”仍保持预留，不与本次收藏接口混用。

### 4.4 橱窗详情

位置：`/stalls/{id}` 右侧操作区，“立即下单”下方。

- 新增与“立即下单”相同宽度和高度的 `收藏橱窗` 按钮。
- 为避免出现两个同层级主按钮，采用白底、橘黄色边框与文字；已收藏时使用浅橘底并显示 `已收藏`。
- 收藏按钮与订单库存、价格、能否下单相互独立；无库存但仍上架的橱窗仍可收藏。
- 已下架或不存在的橱窗不显示公开详情，也不能新建收藏。
- 橱窗所有者进入编辑视图时隐藏收藏按钮。

### 4.5 两种工作台共用收藏快捷卡

位置：`/dashboard/**` 和 `/painter/**` 左侧主菜单白色卡片下方。快捷卡与主菜单是上下分开的两张白色卡片，样式参考现有工作台圆角、边框和阴影，不塞进菜单列表内部。管理员工作台不显示该卡片。

快捷卡内部横向等分三个图标按钮：

| 入口文案 | 显示内容 | 点击目标 |
| --- | --- | --- |
| 画师收藏 | 线条人物/关注图标和文字 | 当前工作台的收藏中心 `type=painters` |
| 作品收藏 | 线条图片图标和文字 | 当前工作台的收藏中心 `type=works` |
| 橱窗收藏 | 线条橱窗图标和文字 | 当前工作台的收藏中心 `type=stalls` |

设计要求：

- 三个按钮均为整块可点击区域，图标使用项目现有黑白线条风格，不使用 Emoji。
- 三列之间使用浅色竖向分隔线；悬停时仅改变图标、文字和浅色背景，不改变整张卡片尺寸。
- 快捷卡不展示预览图和虚构数量，因此不需要为侧栏额外请求汇总接口。
- 切换企划方/画师工作台只改变当前页面外壳，收藏关系和三个入口不随 `role` 分开。
- 窄屏时保持三列横排；空间不足时缩小间距和字号，不让标签换成两行。

### 4.6 收藏管理页

收藏中心复用一个页面组件，但保留当前工作台外壳：

- 企划方工作台入口：`/dashboard/favorites?type=...`。
- 画师工作台入口：`/painter/favorites?type=...`。

两个路由展示相同数据和相同页面组件，通过查询参数切换三个标签：

- `type=painters`：关注的画师。
- `type=works`：收藏的作品。
- `type=stalls`：收藏的橱窗。

页面复用现有公开卡片的视觉信息，但操作只保留“查看详情”和“取消关注/取消收藏”。每个标签独立分页；取消成功后从当前列表移除并同步总数，当前页变空时自动回到上一有效页或显示空态。

收藏中心不加入主菜单列表，而是由主菜单下方的共用快捷卡进入。两个路由的数据完全相同，`role` 只决定保留哪一种工作台侧栏，不得生成两份收藏关系。

## 5. 数据库设计

为保持目标类型清晰并便于后续建立索引，使用三张关系表，不使用无法建立明确目标约束的多态收藏表。

### 5.1 `user_follow`

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | BIGINT | 主键 |
| `user_id` | BIGINT | 发起关注的用户 ID |
| `painter_id` | BIGINT | 被关注的认证画师 ID |
| `created_at` | DATETIME | 关注时间 |

约束与索引：

- 唯一键 `uk_user_painter (user_id, painter_id)`。
- 索引 `idx_painter_created (painter_id, created_at)`，为后续画师关注数统计预留。
- 索引 `idx_user_created (user_id, created_at)`，用于我的关注按时间倒序分页。

### 5.2 `work_favorite`

字段：`id`、`user_id`、`work_id`、`created_at`。

- 唯一键 `uk_user_work (user_id, work_id)`。
- 索引 `idx_user_created (user_id, created_at)`。
- 索引 `idx_work_created (work_id, created_at)`。

### 5.3 `stall_favorite`

字段：`id`、`user_id`、`stall_id`、`created_at`。

- 唯一键 `uk_user_stall (user_id, stall_id)`。
- 索引 `idx_user_created (user_id, created_at)`。
- 索引 `idx_stall_created (stall_id, created_at)`。

关注与收藏属于可随时撤销、且不影响交易审计的个人关系，取消时可以物理删除关系行；不得物理删除用户、作品、橱窗或交易记录。实现时必须新增日期迁移 SQL，并同步更新 `backend/sql/init.sql`。

## 6. 接口设计

接口继续使用统一 `{ code, message, data }` 响应结构。改变关系的接口要求登录；分页接口默认 `page=1`，并限制 `size` 最大值。

### 6.1 画师关注

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| PUT | `/api/v1/follows/painters/{painterId}` | 幂等关注画师 |
| DELETE | `/api/v1/follows/painters/{painterId}` | 幂等取消关注 |
| GET | `/api/v1/follows/painters/{painterId}/status` | 查询当前用户是否关注 |
| GET | `/api/v1/follows/painters?page=1&size=20` | 分页查询我的关注画师 |

关注与取消响应：

```json
{
  "followed": true,
  "painterId": 14
}
```

### 6.2 作品收藏

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| PUT | `/api/v1/favorites/works/{workId}` | 幂等收藏作品 |
| DELETE | `/api/v1/favorites/works/{workId}` | 幂等取消收藏 |
| GET | `/api/v1/favorites/works/{workId}/status` | 查询收藏状态 |
| GET | `/api/v1/favorites/works?page=1&size=20` | 分页查询收藏作品 |

### 6.3 橱窗收藏

| 方法 | 路径 | 说明 |
| --- | --- | --- |
| PUT | `/api/v1/favorites/stalls/{stallId}` | 幂等收藏橱窗 |
| DELETE | `/api/v1/favorites/stalls/{stallId}` | 幂等取消收藏 |
| GET | `/api/v1/favorites/stalls/{stallId}/status` | 查询收藏状态 |
| GET | `/api/v1/favorites/stalls?page=1&size=20` | 分页查询收藏橱窗 |

### 6.4 邀请复用

- 已有：`GET /api/v1/projects/mine`。
- 已有：`POST /api/v1/invitations`。
- 请求继续使用 `{ projectId, painterId, message }`。
- 不新增脱离企划的 `/users/{id}/invitations`，并在后续同步修正《主页功能设计计划》中旧的预留写法。

### 6.5 黑名单与举报预留

以下仅为后期接口命名保留，本期不得创建空 Controller 或返回伪成功：

| 方法 | 预留路径 | 后期用途 |
| --- | --- | --- |
| PUT | `/api/v1/blocks/users/{userId}` | 加入黑名单 |
| DELETE | `/api/v1/blocks/users/{userId}` | 移出黑名单 |
| POST | `/api/v1/reports` | 举报用户、作品、企划或橱窗 |

后期举报至少需要 `targetType`、`targetId`、`reason`、证据图片和处理状态，并需要管理员治理页面、审计日志及重复举报规则；未完成这些设计前不提前开放。
