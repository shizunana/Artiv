> 日期：2026-09-07。实施前本地 Git 基线：df62197；本轮实现尚未提交、未推送。
> 状态：B 路线结构已实施，本机 artiv 已受控迁移；原十类保留给橱窗/作品，企划独立六类，数据库 project_category、接口 projectCategory。第 5 节页面优化尚未开发，等待单独决定。

## 1. 要解决的问题与结论

企划方发布时面对十个细类型，容易不知道应该选哪个；画师能够承接多个相近类型，却需要在大厅反复切换，可能漏看合适企划。目标是减少分类决策，而非减少必要的需求说明。

最终期望：发布只需选择一个企划大类；题材风格可选、默认不限，不再出现“大类 → 细类型 → 题材风格”三层选择。大厅主要面向找稿的画师，默认展示全部符合公开条件的企划。

本轮数据库核对确认企划、订单及主要关联表为空，用户随后确认采用“企划独立六类”的 B 路线，按小步骤实现并在依赖准备齐后统一启用。现阶段无需旧企划归类或历史订单数据改写，但已确认的列重命名需要执行受控数据库结构迁移，流程见第 9.1 节。

本方案只保留已确认的 B 路线：用新的六个“企划类型”替代企划原来使用的十类，不是给旧十类加分组，也不是额外增加一级选择。发布、编辑、存储、大厅筛选和企划统计统一使用新六类；原十类仅在橱窗、作品及其供给查询中继续使用。
题材风格
结构阶段包含前端现有控件的六类选项、提交、回显与查询参数适配；不包含六张卡片、布局重排、题材折叠、取消默认头像等体验调整。第 5 节样式建议在结构验收完成后单独决定是否开发。

### 已确定的产品边界

- 六个名称：头像、立绘、角色设计、插画、平面设计、自设/OC。没有“其他”分类。
- “全部”是清除大厅类型限制的入口，不是第七个可发布类型。
- 原十类仍供橱窗和作品使用：头像、Q版全身、半身像、立绘、组合页、服设、壁纸、表情包、Live2d、平面设计。
- 35 个题材风格选项及各模块已有数据规则保留。“类型”和题材中的“立绘”仍是不同字段，不借本方案合并或删除。
- 发布的题材风格可多选且可为空；大厅当前是单选题材筛选，维持现状。这里“最多两组选择”指类型与题材两个维度，不是题材最多选两项。
- 橱窗、作品发布与筛选不变；订单履约、余额、邀请接受和各模块删除规则不在重构范围。
- B 路线及六类名称已实施；统计按第 7 节适配，页面优化明确后置。本轮没有清理主库业务数据。

### 数据库调整决定：重命名企划字段，不新建分类表

迁移前三种资源各自有独立字段：project.category、stall.category、work.category，并非共同引用分类表。迁移后仅企划字段变为 project.project_category，另两者不变。

- project.category → project.project_category：执行列重命名，保持 VARCHAR(50)、现有可空性和默认值，更新列注释为“企划类型（六类）”；保存六个中文名称之一，例如“角色设计”。本次不顺带新增 NOT NULL、索引或外键，必填及六类限制由服务端统一校验。
- stall.category / work.category：继续保存原十类，现有作品数据不动。
- 英文名用于代码和文档，不意味着必须把数据库存储值改成英文编码。
- 企划 Entity / DTO、创建/编辑 JSON、列表筛选参数及相关响应统一 projectCategory；MyBatis-Plus 映射到 project_category。已有 MyApplicationItem.projectCategory 沿用，修改它的数据来源；不保留两个可独立写入的同义字段。
- 新订单在现有 project_snapshot JSON 中使用 projectCategory 键；统计等读取者同步修改。为兼容可能导入的旧快照，可在新键缺失时只读回退旧 category 键，但不据此自动迁移旧分类值，也不批量重写订单快照。订单表本身不新增列，履约规则保持原实现。

这里确实涉及数据库结构变更：重命名 project 表中的一列，需要独立迁移脚本、备份与部署协调。六项固定选项仍由代码白名单管理，无需增加企划类型字典表；管理员统计读取六类，不意味着开放后台动态新增分类。

仅当未来明确需要管理员随时新增、停用、排序企划类型，或维护多语言名称时，再评估独立分类字典表及外键。这些动态管理能力不属于当前需求。

订单表没有独立 category 列。企划建单会在 [OrderServiceImpl.projectSnapshot](../../backend/src/main/java/com/artiv/service/impl/OrderServiceImpl.java) 中写入类型与题材；橱窗建单没有独立橱窗类型快照，主要保存标题、封面、阶段及金额。

这支持“保留订单履约实现”的设计，但不构成零 bug 保证。第 10 节必须用新六类订单进行回归。

## 3. 六类名称、交互含义与供给映射

以下关联集合仅用于管理员供需对比中匹配橱窗、作品的原十类，不用于企划发布存储或大厅筛选。关联范围按用户最后调整的版本保留：

| 六类名称 | 原十类关联集合 | 面向用户的简短说明（建议文案） |
| --- | --- | --- |
| 头像 | 头像、表情包 | 头像与表情形象 |
| 立绘 | 立绘、Q版全身 | 角色全身展示，包含 Q 版 |
| 角色设计 | 服设、组合页、立绘、Live2d | 角色外观、服装与形象设计 |
| 插画 | 半身像、壁纸 | 人物画面与壁纸插画 |
| 平面设计 | 平面设计、表情包 | 标识、文字与图形设计 |
| 自设/OC | Q版全身、半身像、立绘、组合页、服设 | 围绕自己的原创角色约稿 |

十个原类型均被覆盖，允许跨组重复。Live2d 只在角色设计；自设/OC 不含头像和 Live2d；插画不含立绘。

映射仅是供给关联，不是保存时随机选一个旧类型的规则，也不是作品能力保证。“自设/OC”和其他五类存在语义重叠；发布者选择最主要的需求方向，以描述和参考图补充，不强制追加细类。

选择“自设/OC”的新企划会保存为自设/OC，不保存原十类的关联集合；它不会自动出现在所有其他新分类下。六类不能同时被当作互斥统计分类和可重复计数的推荐分组。

## 4. 路线 B：以独立六类替代企划原十类（唯一实施方案）

- 将 project.category 重命名为 project_category，仍保存六类中的一个字符串；采用独立受控迁移，不新建类型表，不改订单表列结构。
- 前端新增企划专用常量，保留 subjects.js 内原 CATEGORY_OPTIONS 与 SUBJECT_OPTIONS 给橱窗、作品及题材使用；不全局替换原列表。
- 后端新增企划专用分类规则（拟议 ProjectCategoryRules），统一六类白名单和原十类供给映射，供发布、编辑、查询及统计调用。
- 创建和允许的内容编辑以 projectCategory 校验非空及六类白名单；拒绝任意字符串、“全部”及旧细类型。当前 DTO 中 category 缺少这样的完整校验，不能只限制页面。
- 大厅直接按新六类精确查询，参数改为 projectCategory；旧 category 参数需明确报错，不能被 Spring 忽略后静默查询全部。新旧参数同时出现也明确拒绝。题材为空表示不限，不把字符串“不限”写入 subject。
- 六类精确条件与题材、预算、日期及原有可见性条件取交集，保留未删除、公开模式、招募中、审核正常、未过期等限制；不通过原十类并集扩大查询范围，不新增分组查询参数。
- 页面回显、向导、统计同时识别六类后，再开放新的发布选择。旧页面缓存提交细类型时返回明确提示并要求刷新，不自动猜测改写。
- 当前相关业务表为空，不设计批量数据 UPDATE。同步 init.sql 的 project_category 列定义用于全新安装；现有库只执行专用重命名迁移，不重新执行 init.sql。
- 数据库列名、Java 映射、请求字段与快照读取必须同批切换；旧服务在列重命名后会查询不存在的 category，不能新旧服务混跑。回退必须协调数据库列名、接口和数据兼容。

旧写入字段 category 不静默转为新字段，也不自动映射旧细类；返回明确参数错误并要求刷新。实施时补显式检测与契约测试，因为默认 JSON/查询绑定可能忽略未知字段。兼容旧快照读取不等于兼容旧版发布客户端。

发布和大厅都使用六类，管理员按第 7 节拆分企划与橱窗/作品统计。原十类映射仅保留在供需对比中，不参与新企划类型的存储与大厅筛选。

## 5. 页面与样式优化建议

> 后置候选：本节不属于结构阶段的必做内容，结构完成后由用户决定是否开发。现有页面只先适配六类选项、接口、回显与必要校验，保持布局、默认选择和题材交互。下文的新增选择组件、卡片、折叠、排序区域等不得自动进入结构改动。

### 5.1 发布企划与编辑企划

复用当前白色工作台卡片、品牌蓝和圆角按钮，不新增风格不同的大弹窗或图标墙。现有发布流程仍为“稿件用途 → 需求详情 → 高级选项 → 预览企划”，分类改造不同时重写整套发布向导。

- “想约什么”区域只显示六张紧凑单选卡：桌面 3 列 × 2 行，窄屏 2 列 × 3 行。每张显示名称及一行说明；说明不变成二级可点击类型。
- 选中以蓝色边框、浅蓝背景与明确选中标识共同表达，未选为白底浅灰边框；使用原生 radio 或具备完整键盘支持的单选组件。
- 控件点击高度建议至少 44px，卡片约 64～76px；名称 14～16px，说明 12～13px，具体值以真实页面验收调整。
- 建议取消目前默认“头像”，初始未选择；在第一步“下一步”时提示选择大方向，避免无意发布为头像。这是待审阅的产品选择。
- 编辑页使用同一企划类型选择组件回显。仍受 contentEditable 和后端 canEditContent 约束，有应征、有效邀请或历史订单时不借此次 UI 开放编辑。
- 题材风格保持高级选项中的可选能力。建议默认折叠为“题材风格：不限／设置”，展开后从原 35 项中多选，可搜索；已选用标签展示并可清空。
- “不限”与具体题材互斥；清空恢复空数组，预览显示不限。此处最多两个分类维度，不限制用户填写必要预算、日期、文字或参考图。
- 切换类型不清空用户已有描述、图片、创作阶段和用途；不要根据映射自动勾选题材。
- 预览页展示新类型和实际题材；不显示映射表、内部参数或统计术语。

### 5.2 企划大厅

- 第一行只保留“全部 + 六类”。“全部”默认选中，不默认选头像，不增加“其他”入口；未知旧值若意外存在仍在全部列表可见，并进入数据核对，不静默丢弃。
- 使用紧凑文字胶囊按钮，选中状态与发布页一致。桌面优先单行，窄屏自动换行，避免把末尾类别藏到必须横向拖动才能发现的位置。
- 第二行优先展示“题材风格：不限”“预算：不限”和搜索；排序、截稿日期等可以放次级区域。保留可用功能，不擅自改变对应含义。
- 当前大厅题材为单选，下拉保留全部 35 项、支持搜索。不要照搬画师大厅的多题材 AND 规则，造成此次隐藏的查询语义变化。
- 只要任一筛选有效，展示“已选条件”与“清除筛选”。无结果时说明“暂无符合条件的企划”，提供手动清除；不自动放宽条件。
- 卡片优先层级：标题与预算 → 需求摘要和参考图 → 类型、题材、截稿日期与应征数。题材最多露出少量标签，其余通过详情查看，避免标签占满卡片。
- 保留卡片进入详情及键盘操作，不把类型标签点击意外触发成详情跳转。刷新、快速切换和返回大厅的状态策略需一致，至少保证旧请求不能覆盖新条件结果。
- 类型、题材、预算、日期变化统一回到第一页；请求失败有提示，不把失败当作真实空列表或零应征。

以上能减少选择与阅读负担，但“曝光增加”仍是待验证的产品效果；不把分类减少等同于已经提升接稿率。先默认全部和清晰摘要，不增加推荐算法、自动排名或行为埋点。

## 7. 管理员统计的具体处理

必须同时完成以下口径，不能用同一个分类数组替换所有图表：

1. 企划类型分布：按实际保存的六类计数，一条企划只占一类；六类合计应等于对应范围的分类有效企划总数。
2. 在售橱窗类型分布：继续原十类；不会因为企划六类而修改橱窗记录。
3. 企划订单成交价格分层：原卡片“完成订单成交价格分层”统一改用此名称，明确只统计已完成的企划来源订单。按订单快照 projectCategory 中的六类过滤，缺新键时可只读兼容旧 category，值未知时显式记录兼容缺口；保持完成时间范围、金额、分位数和样本不足规则，不由当前企划类型覆盖已有快照。两键均有值时以新键为准，矛盾不静默合并。
4. 供需对比：每行是一个企划大类，需求计该大类企划；供给按第 3 节原十类集合匹配在售橱窗和公开作品。画师在同一组内按 userId 去重，橱窗按 ID 计数。同一供给可出现在多组，各组供给不能相加冒充全站总量，也不把映射命中称为已确认接稿能力。
5. 平台运营的类型排名：当前 operationCategories 混合企划与橱窗的原类型。独立六类后建议拆成“企划成交类型”“橱窗成交类型”两个统计口径，保留平台总订单数和 GMV 原算法，避免同名“立绘”跨体系误合并。返回字段变更与前端必须同批启用。
6. 数据为空时显示真实空态，不用虚构数据填图；未来出现无法识别的值，后台提示异常数据数量并核对，不静默排除。

供需映射会重复覆盖，但分类饼图和订单总数不得重复计数。这是本方案最重要的统计验收点。

### 9.1 数据库迁移安全流程（本机已执行，其他部署仍须遵循）

这是表结构变更，不依赖“数据库为空所以随便改”。实施必须留下执行前后证据，步骤如下：

1. **确认目标。** 核对后端实际生效 profile、环境变量和数据源，明确 host / port / database；本文件的 127.0.0.1 / artiv 只是本次核对基线。读取 SHOW CREATE TABLE 和 information_schema，确认原列类型、默认值、可空性、索引以及相关视图/触发器等依赖。数据库凭据不出现在文档、日志或 Git 中。
2. **再次核对数据。** 停止写入后，检查企划、订单、应征、邀请及阶段等表（包含软删除）的数量，记录现有作品、用户余额及其他表的基线。若出现非空旧类型数据，先补兼容和归类方案，不自动清理，不继续套用空库计划。
3. **备份并验证恢复。** 在迁移前备份完整数据库的结构和数据，以及实际上传目录；停写窗口内记录时间、备份路径与完整性校验。备份保存在受保护且不入 Git 的位置。在隔离数据库验证能够恢复，不能只凭“导出文件存在”判定可回退。现有数据库基线脚本不备份上传文件，也不自动证明可恢复。
4. **先隔离演练。** 使用备份/等价结构建立测试库，验证旧列 → 新列、列属性保留、重复执行、异常状态拦截，以及新后端读写。不能在主库直接边写迁移边试。
5. **停旧服务后迁移。** 停止 Artiv 后端及可能写库的定时/测试进程，防止其他页面继续发请求。使用独立脚本对 project.category 做 RENAME COLUMN 到 project_category，不采用删除旧列再添加新列的方式。需要改注释时保留原列属性并将其作为可单独核验步骤；不重跑 init.sql，不改 work/stall/order_info 的列。
6. **核验后启动配套版本。** 新列必须存在、旧列必须不存在；类型、默认值、可空性及无关表数据应与基线一致，仅预期名称/注释改变。启动已完成 DTO、Mapper、接口、统计、向导适配的新后端和前端；检查不存在 Unknown column、空字段或静默失效筛选。通过回归前不开放正常写入。
7. **记录结果。** 保存实际脚本版本、应用提交、目标库、执行时间、变更前后结构和验收结果；后续导入旧备份时必须先识别列版本，不直接用新后端连接旧结构。

迁移脚本或配套执行器应基于列存在性识别状态：

| 原 category | 新 project_category | 处理 |
| --- | --- | --- |
| 存在 | 不存在 | 核验前置条件后执行改名 |
| 不存在 | 存在 | 检查属性与注释，正确时视为已迁移；缺注释只补对应步骤 |
| 存在 | 存在 | 异常状态，停止；不自动删任一列或合并值 |
| 不存在 | 不存在 | 目标库或结构异常，停止 |

MySQL DDL 不能依赖普通业务事务 ROLLBACK 恢复；列改名与后续注释修改等多个步骤也不能假定整体可回滚。任一步失败先读取实际结构，再决定补做或撤回，不盲目重跑整套脚本。

回退分两种：未开放写入且确认无新增记录时，在停服务状态下校验后逆向改名、恢复注释并部署配套旧版本；已经产生新六类企划或新键订单快照时，仅逆向列改名并不能解决语义兼容，需先保留新增数据并完成兼容评估，优先向前修复。整库恢复会覆盖备份后的变更，不作为自动回退动作。

未借这次改名收紧数据库约束、重命名橱窗/作品字段或重设计订单表。专用 SQL 和带状态检查的 PowerShell 执行器已创建并在隔离库和本机验证，具体路径见第 13 节。
