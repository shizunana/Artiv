## 1. 结论与适配重点

这个方向适合 Artiv，现有 Vue 和 Spring Boot 项目可以承载，不需要另建微服务或重构交易流程。原稿的产品边界基本合理，但不能直接按原稿的工具清单和目录结构开工。

| 原稿中的设想 | 当前项目事实 | 本版调整 |
| --- | --- | --- |
| 调用现有 Service 就等于只读、安全 | 部分查询 Service 有写入副作用，部分允许管理员查看非公开数据 | 逐个审查方法、增加受限数据投影；有副作用的方法暂不注册为工具 |
| 管理员可在企划、订单页面测试全部能力 | 管理员工作台守卫会重定向普通工作台路由；订单详情只允许订单双方 | 首先验收公共数据能力；私人业务使用隔离样例或后续经授权的本人数据 |
| `get_project_invitations` 可直接复用 | 现有邀请查询面向收到邀请的画师，没有通用“发布者全部邀请列表”接口 | 不虚构已有接口，也不拿画师查询接口冒充发布者接口 |
| 上传参考图后用图片 ID 做锚点 | 现有上传返回 `/uploads/...` 字符串，没有通用文件实体、归属表或图片 ID | 视觉阶段新增向导私有参考图资源，不能把任意路径当作授权凭据 |
| `project_id` 直接绑定需求锚点 | 需求头脑风暴通常发生在企划创建前 | 锚点先属于向导会话草案；人工复制后走原发布流程 |
| 使用新的 `assistant/controller/service/model/vo` 全套结构 | 当前项目按 `com.artiv.controller/service/service.impl/dto/entity/mapper` 分层 | 遵循现有分层；只为模型客户端和工具新增局部包 |
| 第一版同时完成全部八个阶段 | 流式、工具、权限、视觉和存储都有独立工作量 | 分成可单独验收的三个增量，保留完整目标，避免一次性打包验收 |

本文中带“新增”“建议”的接口、类、表和配置原为设计；第 7 节记录原有业务入口，第 24.7～24.10 节记录各阶段实际交付。历史记录保留当时配置，当前能力和限制以最新交付记录为准。本文件已纳入项目 Git，下载目录的同名适配版为同步副本。

## 2. 产品定位与范围

前台统一显示“艺绘向导”，入口不与“消息”“发布需求”混淆。说明页应明确它使用模型辅助理解信息，回答和图片识别可能出错；不以更换名称隐瞒模型处理。

允许：规则解释、公开候选检索与比较、授权业务状态摘要、需求草案、参考图可见元素描述和候选锚点。

禁止：图片生成、补图、扩图、改画、上色、线稿生成、画师风格模仿、绘图模型提示词转换，以及任何由模型执行的业务写操作。禁止调用创建、删除、上下架、应征、邀请、接单、交付、验收、退款、结算、仲裁、封禁、举报、评价和消息发送等业务接口。

“业务只读”与“模块自己需要保存数据”应区分：用户主动发送对话、上传参考图、确认或删除草案、提交反馈可以写向导自己的会话、日志和临时文件；这些入口不作为模型工具，不修改企划、订单或其他交易数据。

## 3. 已核实的技术基线（向导开发前）

| 项目项 | 当前事实与实现约束 |
| --- | --- |

| 数据访问 | MyBatis-Plus 3.5.7、MySQL；不是 JPA/Repository 架构 |
| 鉴权 | `AuthInterceptor` + JWT Bearer + `UserContext` ThreadLocal；不是完整的 Spring Security 过滤器链 |
| 管理员入口 | `/api/v1/admin/**` 检查数据库中的 `role=3`、`status=0` 和未删除 |
| JSON 协议 | `Result<T>`：`code / message / data`；分页使用 MyBatis-Plus `Page` |
| 前端 | Vue 3、JavaScript、Element Plus、Pinia、Vue Router、Vite |
| 普通 HTTP 请求 | `frontend/src/utils/request.js`，Axios 默认超时 15 秒，自动携带 Bearer Token |

新增模块先沿用现有运行环境。是否选择模型 SDK，取决于最终供应商的真实协议；不先升级 Spring Boot，不默认引入 Spring AI、LangChain、Redis、向量数据库或新 Node 服务。

## 4. 管理员开放与数据范围

### 4.1 入口权限

新增接口统一放在 `/api/v1/admin/guide/...`，这样可复用当前管理员拦截逻辑。前端入口依据 `userStore.isAdmin`，后端仍逐请求鉴权；功能关闭时不调用模型。

当前错误协议需要按源码验收：

- 有效普通账号访问管理员接口：HTTP 403，业务码 `2003`。
- 未登录或无效 Token：当前全局异常处理一般返回 HTTP 200、业务码 `401`；不能把验收条件写成“必须 HTTP 401”，除非另立任务统一修改协议。
- 流式请求建立前同样可能收到上述 JSON 错误，客户端必须先检查状态和 Content-Type，不能把所有响应当事件流解析。

### 4.2 管理员身份不扩展向导的数据范围

默认开放：平台规则、公开招募企划、正常认证画师的公开资料、公开作品的文字信息与公开评价、管理员自己在向导输入的测试需求。

默认关闭：其他用户的私人订单、私聊、定向企划、非公开作品、认证材料、后台案件证据和管理员全站查询数据。不得为了演示而允许前端或模型传入任意 `userId / actorId / role` 来假扮企划方或画师。

特别注意：`ProjectServiceImpl.getById(id, viewerId)` 内部存在管理员读取非公开企划的分支。向导公共查询应使用固定的公共读取策略，例如以匿名查看者调用既有公开权限分支，并投影允许字段；不能直接把当前管理员 ID 传进去就称为“公共数据”。

### 4.3 私人业务能力如何测试

管理员路由守卫无法直接承载普通工作台的完整体验；`OrderServiceImpl.getDetail` 也不因为角色是管理员而跳过订单参与者校验。

第一增量只测公共数据。后续私人业务阶段分开验收：

1. 用无真实身份信息的固定样例验证摘要和下一步解释，页面明确标注“模拟测试数据”。
2. 通过服务层测试验证订单双方、企划发布者、无关账号的访问边界，不改变向导 HTTP 接口仅管理员开放的约束。
3. 如果当前管理员确有本人业务记录，可以在新增的纯读取方法中按本人关系查询；没有就显示无记录，不冒用他人身份。
4. 真正面向普通用户的端到端工作台测试，放到后续小范围开放阶段，不将管理员模拟测试标记为已通过。

## 5. 三个开发增量

| 增量 | 交付内容 | 明确的完成边界 |
| --- | --- | --- |
| A：文本与公共数据闭环 | 管理员入口、多轮对话、流式、规则工具、公开企划/画师检索、需求草案、基础日志和限额 | 可独立演示、可关闭；不依赖图片和私人订单 |
| B：参考图与候选锚点 | 私有上传、视觉分析、结构化结果、用户确认、会话内缓存、临时资源清理 | 锚点属于草案；用户手动使用，不回写企划 |
| C：授权业务解释 | 审查并补齐纯读取摘要方法、本人企划/订单解释、有限待办摘要 | 权限与零业务副作用验证通过后才注册对应工具 |

上述顺序是建议的实现顺序，完整产品目标仍包含三个增量。局部框选、多参考图比较、长期历史、自动填入发布表单和普通账号开放属于后续扩展，不作为 A 的验收前置。

实际执行按第 24 节拆成逐次验收的小任务，每轮只开发用户选定的任务。鉴于多模态是明确要求，在完整图片功能开发前，任务 02 就用少量授权图片验证模型能力；该验证不等于 B 阶段已经完成。

## 6. 总体架构和工具调用边界

```text
管理员 → GuideHost / 右侧抽屉
       → AdminGuideController（入口鉴权、功能开关、限额）
       → GuideService（会话、流式、调用次数和时间预算）
       → GuideModelClient（供应商协议适配）
       ↔ 固定 GuideToolRegistry
       → GuideReadService（工具参数验证、字段最小化）
       → 已审查的业务 Service 读取方法
       → Mapper / MySQL
```

工具注册表只包含明确列出的函数，不开放任意 URL 请求、任意 SQL、任意 Java 方法反射、Shell、文件路径读取或通用后台 API。模型只能提出工具调用，服务端决定是否执行。

身份从鉴权后的服务端上下文取得，不能来自模型参数。所有资源 ID、分页、筛选值、查询长度和返回条数都有服务器上限。返回只包含回答所需字段，不直接序列化完整实体。

新增向导 Service 可以管理自己的会话和临时资源；业务 Mapper 仍由对应业务服务封装。现有查询不能安全复用时，给原业务模块补一个有权限校验的纯读取方法，不复制删除、付款、邀请等状态流转逻辑。

## 7. 现有接口与建议工具的准确对应

以下 HTTP 路径用于核对现有能力。工具在同一后端进程内调用 Service，不需要携带管理员 Token 回环请求 HTTP。

| 建议工具名 | 已有 HTTP / Service | 接入决策 |
| --- | --- | --- |
| `get_current_user_context` | `GET /api/v1/auth/me`；管理员请求的 `UserContext` 已含身份 | A：仅输出最小身份与启用能力，不传完整账户对象 |
| `get_platform_rules` | 没有已有规则查询 API | A：新增读取审核后的版本化规则文件 |
| `search_projects` | `GET /api/v1/projects` → `ProjectService.listProjects(...)` | A：复用公共招募筛选，限制条数并做字段投影 |
| `get_public_project` | `GET /api/v1/projects/{id}` → `ProjectService.getById(id, viewerId)` | A：公共权限策略；不启用管理员非公开读取分支 |
| `search_painters` | `GET /api/v1/users/artists` → `ArtistService.listArtists(...)` | A：正常认证画师公开摘要；参数叫 `subjects`，不是企划查询中的 `subject` |
| `get_painter_profile` | `GET /api/v1/users/{id}/public-profile?role=painter` → `PublicProfileService.getProfile(id, role)` | A：公开主页 DTO；推荐候选仍需满足画师大厅资格 |
| `get_public_works` | `GET /api/v1/users/{id}/works` → `PublicProfileService.listWorks(id, page, size)` | A：先提供标题、分类等文字和站内展示引用，不自动把所有作品图发送给视觉模型 |
| `get_painter_reviews` | `GET /api/v1/users/{id}/reviews?role=painter` → `ReviewService.listPublic(...)` | A：只投影公开评价文本与统计，不附带订单内部 ID 等无关字段 |
| `get_my_projects` | `GET /api/v1/projects/mine` → `ProjectService.listMine(..., currentUserId, mode)` | C：仅本人；可复用 `deletable / deleteBlockReason` 等当前计算结果 |
| `get_my_project_panel` | `GET /api/v1/projects/{id}/panel` → `ProjectService.getPanel(id, currentUserId)` | C：发布者专属，不能用管理员通用查看代替 |
| `get_project_applicants` | `GET /api/v1/projects/{id}/applications` → `ApplicationService.listApplicantDetails(...)` | C：既有访问校验也含管理员分支；先限制为公共或本人发布企划，再裁剪应征及关联订单标识等字段，不能直接传管理员 ID 放行非公开数据 |
| `get_my_orders` | `GET /api/v1/orders` → `OrderService.listMine(...)` | C：始终叠加当前用户参与关系；`projectId` 只是额外筛选 |
| `get_order_summary` | 当前详情为 `GET /api/v1/orders/{id}` → `OrderService.getDetail(...)` | C：现有详情有副作用，不直接注册；新增纯读取状态摘要方法 |
| `get_my_invitation_summary` | `GET /api/v1/invitations`、`GET /api/v1/invitations/project/{projectId}` | C：现有查询有副作用；需先提供纯读取摘要方法 |
| `get_project_invitations` | 没有与该名称直接对应的发布者完整邀请列表接口 | 暂不注册；不能把收到邀请接口当作已发邀请列表 |
| `analyze_reference_image` | 没有现成视觉服务 | B：新增；只接受当前会话所属且已同意分析的 `referenceId` |

不要用 `GET /api/v1/users/{id}` 作为画师工具的数据源。它目前返回仅清空密码的 `User` 对象；适配时应使用已存在的 `PublicProfileResponse`，并继续做向导字段白名单。

## 8. “GET / Service”不等于没有副作用

已定位两处会直接影响原稿“只读”承诺的代码：

1. `InvitationServiceImpl.listMine` 和 `getMineByProject` 调用 `convergeInvalidPublicInvitations`，可能把待处理公开邀请更新为失效，并写回应与更新时间。
2. `OrderServiceImpl.getDetail` 调用 `repairLegacyPreview`，可能生成水印文件并更新 `order_stage.attachments`。

仅隐藏写工具、只允许 GET、或者加上 `@Transactional(readOnly=true)` 都不能替代上述调用链审查。

C 阶段建议在原业务 Service 中增加明确命名的纯读取摘要方法，复用或抽取既有资源归属检查，仅读取必要状态字段；不执行历史附件修复、过期状态更新、消息发送或任何交易行为。原有页面接口保持原有行为。

如果数据库中的邀请状态尚未完成既有失效处理，摘要可以区分“存储状态”与“根据企划日期/可见性推导的当前有效性”，不能为让回答看起来实时而由向导触发更新。向导也不得从这一推导声称某项写操作必定成功。

只读验收要覆盖业务表、文件写入和消息事件；向导自身会话与日志写入单独计入允许范围。

## 9. 规则知识与回答依据

建议新增 `backend/src/main/resources/guide/platform-rules.json`，随代码发布。每条包含 `ruleId`、主题、经审核的规则正文、对应源码路径、验证日期和规则版本。模型读取规则正文；页面引用用规则标题和版本，不向普通用户显示内部源码或运维说明。

当前 `docs/功能说明.md`、`docs/接口文档.md` 和测试记录可作为整理材料，但不能把整个文档目录或历史设计直接放入系统提示。源码与测试是核对依据；尤其不能把“开发计划”和“未解决问题”当成已上线规则。

首批规则应覆盖以下 Artiv 特有事实，并在真正开发时再次与源码核对：

- 普通账号 `role=1/2` 用于默认工作台选择，不能当成唯一交易权限；画师大厅目前以 `certStatus=2`、正常状态和未删除筛选。
- `ProjectTimeRules` 规定截稿日期当天仍未过期，修改截稿日期至少选择当前日期 2 天后。公开大厅还会检查招募状态、审核状态和未删除。
- 项目数据库存在多个历史 `status` 值，解释当前企划是否可操作需要结合合作方式、日期、审核状态和关联关系，不能只翻译一个数字。
- 邀请接受后形成应征关系和沟通，不等于已经创建订单；带价邀请报价使用既有锁价规则。
- 企划有任何关联订单或待回应定向邀请时不能删除；橱窗有未完成订单时不能删除；删除邀请只是隐藏提醒；作品隐藏、逻辑删除都应退出公开作品列表。
- 订单状态为待接单、进行中、待验收、已完成、已取消、争议中；创作阶段名称来自实际订单/企划快照，不能假定固定三阶段或按阶段百分比结算。

回答的数据来源分成“本次查询结果”“平台规则”“一般建议”。业务结果包含查询时间；分页不完整时明确“本页/已检索候选”，不得把有限查询当作全平台或全部待办。

工具失败、数据不足、未授权或规则库未覆盖时说明无法确认。引用 ID 必须来自本次工具结果或规则库，后端验证；模型不得编造数据、已执行操作或不存在的页面。

## 10. 推荐如何复用现有筛选

### 10.1 画师候选

复用 `ArtistService.listArtists(page, size, category, subjects, keyword)`：当前类型条件依据画师的公开作品分类；多个 `subjects` 逐项叠加标签条件；当前默认按用户 ID 排序。不能把这份结果直接宣传为“智能最佳排名”。

建议先取最多 15 个满足筛选的候选，返回公开简介、类型、题材标签、公开作品文字摘要、评分与评价数量，让模型解释匹配点和不确定项。无候选时提示条件过窄，若放宽条件必须明确告诉用户。

目前没有统一画师报价区间或实时档期字段。不能根据作品或评分臆测价格、接单意愿、商业授权范围。若使用公开橱窗价格，只能说明该项具体服务标价，不推断该画师所有服务都适用。

### 10.2 企划候选

复用 `ProjectService.listProjects`：当前固定检索公开、招募中、审核正常、未删除且截止日期未过期的企划。预算上下限按区间相交筛选；`keyword` 当前主要匹配标题，不等于对需求全文进行语义搜索。

第一版是“筛选后由模型比较已取回的候选”，不是全库语义检索。推荐基于用户本轮主动提供的类型、预算、题材和需求，不读取私人认证材料，不输出无算法依据的精确匹配百分比。

现有分类来自 `frontend/src/constants/subjects.js`：类型与题材必须分开处理。开发向导时将允许值同步到服务端可校验配置，并校验一致性，不能仅信任前端枚举。未知分类可保留在草案备注，但不作为有效筛选值提交。

## 11. 需求草案与现有企划字段

第一版“生成需求”意味着生成可编辑、可复制的草案，不调用 `POST /api/v1/projects`。管理员可用测试需求演示，无需进入普通账号发布工作台。

| 草案内容 | 当前表单/请求的对应方式 |
| --- | --- |
| 标题 | `title`，最多 20 字 |
| 需求正文 | `description`，建议遵守现有表单 1000 字上限；创建请求的后端校验与完整编辑 DTO 的限制并不完全一致，不能声称当前所有入口已有同等后端限制 |
| 类型、题材 | `category`、`subject: string[]`，使用现有选项 |
| 预算 | `budgetMin / budgetMax`；现有发布请求还发送兼容字段 `budget=budgetMax`，金额需合理且上下限有序 |
| 截稿时间 | `deadline`，日期语义由当前服务端规则校验，不由模型保证 |
| 文件要求 | `requirements.size / colorMode / formats / publishPermission` |
| 创作阶段 | `phases` 最终为 `[{"name":"..."}]` 的 JSON 字符串，不添加已废弃的百分比语义 |
| 参考图 | 当前 `images` 是逗号分隔地址；向导私有 `referenceId` 不是可直接提交的作品或企划图片路径 |
| 用途、商用、人物数量、背景复杂度等 | 第一版先整理进草案说明；当前 `ProjectRequirements` 不含 `usage` 或 `commercial` 字段 |

`ProjectNew.vue` 虽然有用途选择 UI，当前提交对象没有独立 `usage` 字段。适配版不能把它描述为已有数据库能力。

对已有企划也不自动回填：`ProjectContentUpdateRequest` 不接收合作方式、邀请目标、日期和状态；完整内容能否修改由既有有效应征、邀请和历史订单条件决定。未来若增加“填入表单”，仍需用户显式点击、原表单校验和原 Service 校验，不给模型发布工具。

## 12. 参考图与候选锚点

### 12.1 当前上传不能直接当成私有素材服务

当前 `UploadController` 接收单个 `file`，以扩展名和 5 MB 大小作基础检查，返回 `/uploads/...` 地址；`WebMvcConfig` 将上传目录静态公开。当前全局 multipart 上限为单文件 5 MB、单请求 10 MB，也没有持久化文件归属表。

B 阶段新增向导专属上传入口，保存在没有静态 URL 映射的私有目录，返回随机 `referenceId`。读取或分析时同时检查当前管理员、会话归属、有效期和分析授权。

建议初版每轮最多 3 张、逐张上传，每张不超过 5 MB，服务端再检查会话累计容量。第一版只接受经真实解码验证的 PNG/JPEG；不能因为原上传允许 GIF/WEBP，就假定当前 Java 解码器和选定视觉服务都支持。校验像素总量、尺寸、真实格式，清除不必要的元数据，并限制解码和模型输入尺寸。

不接受任意公网 URL、内网 URL、本地绝对路径或任意 `/uploads/...` 字符串作为视觉工具参数。只有当前会话已授权引用可解析为文件，阻断路径遍历和服务端任意地址请求。

管理员选择图片后，明确提示图片将发给配置的模型服务进行分析，点击“分析参考图”才开始；公开画师作品不因为能在网页看到就自动批量发送到外部视觉服务。

### 12.2 数据结构

需求锚点先绑定会话，不要求 `projectId`。下面是新增 DTO 示例，并非已有数据库字段：

```json
{
  "draftId": "server-generated-id",
  "sessionId": "server-generated-id",
  "schemaVersion": 1,
  "anchors": [
    {
      "id": "server-generated-anchor-id",
      "category": "composition",
      "content": "半身构图",
      "sourceType": "vision",
      "referenceId": "owned-reference-id",
      "sourceRegion": null,
      "confidence": "medium",
      "confirmation": "pending"
    }
  ],
  "uncertain": ["无法确认用户是否只参考服装"],
  "questions": ["你想保留构图，还是只参考服装？"]
}
```

类别沿用原稿的构图、角色、外观、服装、道具、场景、氛围、色彩、必须保留、明确不要和其他，使用固定枚举。服务端校验 JSON、数组长度和文本长度，不合格结果提示重试，不作为正式要求。

模型只返回候选内容、疑问和自身不确定性。草案 ID、资源引用校验、来源标记及确认状态由服务端管理；用户手动接受/修改后才将对应项标记为已确认。模型输出 `confirmed` 也不能改变确认状态；重新生成不能覆盖用户已确认的内容。

第一版不建立 `project_requirement_anchor` 表，不改 `ProjectRequirements` 的既有格式。即便用户确认，锚点也只是“已确认的草案”，还没有成为已发布企划要求。

### 12.3 缓存和生命周期

缓存按所有者、图片摘要、模型 ID、分析版本和裁剪区域隔离；相同文件属于不同用户时不得串读结果。已分析的结构化描述可用于后续对话，原图不在每一轮重复提交。

建议测试阶段会话/图片闲置 24 小时到期，同时设置会话总数和总容量上限。用户清空会话、账号退出或资源到期时清理相应缓存与临时文件；已有在途调用取消并释放资源。向导资源的清理属于模块自身生命周期，不是模型自主后台业务操作。

这不能替代供应商端的数据保留控制；开发前需核实所选服务的留存设置，不能承诺本地清理等于供应商即时删除。

### 12.4 局部框选

放在多图和基础锚点稳定之后。后续区域用相对坐标表示，例如 `x/y/width/height` 均位于 0～1，服务端验证边界后裁剪已授权图片；`sourceRegion` 当前保持空。裁剪仅用于参考理解，不保存为新作品、不提供绘画编辑功能。

## 14. 流式方案与现有鉴权兼容

后端使用 Spring MVC 的 `SseEmitter`，前端用独立 `fetch` 读取事件流。`SseEmitter` 提供事件发送及超时等能力，适合现有 MVC 服务；不要求改成 WebFlux。[Spring SseEmitter 文档](https://docs.spring.io/spring-framework/docs/6.1.0-M4/javadoc-api/org/springframework/web/servlet/mvc/method/annotation/SseEmitter.html)

前端显式携带 `Authorization: Bearer ...`，基址仍读取 `VITE_API_BASE_URL` 或 `/api/v1`，Token 获取复用 `utils/auth.js`。原 Axios 包装按完整 JSON 解析且默认 15 秒超时，不直接拿来承载长流式回答。

浏览器原生 `EventSource` 构造方式不能满足本方案的自定义 Bearer 请求头和 POST 消息体，因此采用 `fetch` + ReadableStream。解析 `text/event-stream` 时按空行识别完整事件，保留跨网络分块的缓冲，用流式 UTF-8 解码处理中文，并支持取消。[MDN Fetch](https://developer.mozilla.org/en-US/docs/Web/API/Fetch_API/Using_Fetch)、[MDN SSE 格式](https://developer.mozilla.org/en-US/docs/Web/API/Server-sent_events/Using_server-sent_events)

建议统一事件名：`meta`、`delta`、`tool_status`、`references`、`usage`、`done`、`error`。工具事件仅显示“正在检索公开企划”等状态，不把内部参数、密钥或完整工具输出推到页面。

流建立前的鉴权、参数和额度错误走现有 JSON 协议；流建立后的错误发送结构化 `error` 再结束。不能在已经提交的 SSE 响应上继续写 `Result` JSON。页面支持停止输出，超时、断网、账号退出和组件卸载会取消请求。

`UserContext` 使用 ThreadLocal，不能假定后台线程、模型回调或异步线程池自动拥有请求身份。请求鉴权完成后创建不可变的调用上下文，显式传递 userId、sessionId 和运行 ID；不得读取到空身份后退化成无权限限制的查询。

配置有界执行器、心跳、连接与整体超时、完成/错误/超时清理回调。取消后尽力终止上游请求并阻止后续工具执行；已被供应商处理的请求可能已经计费。开发环境复用 Vite `/api` 代理；部署时实测代理缓冲和空闲超时，不能只凭本机成功认定线上流式正常。

## 18. 会话、日志与成本控制

### 18.1 A 阶段可以不迁移数据库

单机管理员测试可使用带容量上限、会话归属和闲置 TTL 的内存会话存储，明确重启后会话丢失。对话历史由服务端维护，前端不使用长期 localStorage 保存业务文本或图片。

日志用结构化事件记录 `runId / sessionId / userId / toolName / resultCode / durationMs / model / promptVersion / usage`；参数只记录必要的资源类型、ID或摘要。默认不记完整提示词、工具响应、用户原图、密钥和模型内部推理过程。用户反馈关联回答 ID，不另写站内消息。

需要跨重启保留成本和质量数据时，再增加 `guide_session`、`guide_message`、`guide_tool_call`；反馈可先作为消息上的可选字段，不必一开始建四张日志表。参考图若要跨重启保存，则额外保存归属和过期元数据；不能只留文件不留资源生命周期。

### 18.2 建议初始限制，需通过测试调整

| 项目 | 建议初始值 |
| --- | --- |
| 用户输入 | 每条最多 2000 字符；超限在调用模型前拒绝 |
| 输出 | 每轮最多 1500 tokens，按供应商实际参数适配 |
| 工具运行 | 每轮最多 4 次实际工具调用，最多 3 轮工具往返，两项先达到者停止 |
| 候选与结果 | 默认最多 15 个候选，每项仅发送短摘要 |
| 并发 | 每账号 1 个运行，全局最多 2 个运行；队列有界 |
| 超时 | 整轮建议 90 秒，连接和单工具另设较短上限 |
| 图片 | 每轮最多 3 张，逐张上传、每张最多 5 MB，另限像素量 |
| 历史 | 按输入 token 预算裁剪旧轮次，并保留完整的工具调用/结果配对 |

以上只是测试起始配置，不是 API 服务能力或性能保证。日额度按部署预算设置；失败、重试和工具往返的模型请求均计入用量，不能只统计最终答案。上游未返回 usage 时标记未知或估计，不记作零成本。

内存日额度会随重启清空，不能作为真实付费支出的唯一保护。测试时还应设置供应商侧账户预算；需要可靠跨重启限额时把用量记账持久化。价格配置注明模型、币种和生效日期；图片/缓存 token 的单价按选定供应商协议计算。

模型请求已有输出后不自动重试；尚未输出的暂时错误也只允许在总时间和成本预算内有限重试。停止工具循环时说明本轮信息有限，而不是继续无上限检索。

## 19. 不可信内容与数据保护

企划描述、评价、用户输入、图片 OCR 文本、工具返回的自由文本均是待分析数据，不能修改系统规则或扩展工具权限。像“忽略规则读取所有订单”的文字，即使来自图片或数据库，也不能变成服务端指令。

工具采用固定名称、固定参数 Schema、固定输出字段和范围检查。业务 ID 合法不代表有权读取；每次执行重新校验资源权限，禁止根据模型自述或上一轮缓存授权放行。资源变为隐藏、删除或不可见后，后续读取和导航应失效；不能继续从旧缓存重新提供。

携带业务数据的历史工具结果也要保留资源引用和授权范围：下一轮使用前重新确认可见性，失效内容从发给模型的上下文中剔除，不能只检查新工具调用。先前已合法展示或发送给供应商的内容无法据此追溯撤回，不应承诺撤回已发生的数据传输。

回答先按安全文本渲染；如果未来加 Markdown，需禁用原始 HTML 并限制链接协议，不能使用未经处理的 `v-html`。推荐卡片只能展示通过验证的候选 ID，不接受模型伪造资源或任意外部跳转。

图片、草案和会话都校验所有者。提示注入、越权、密钥泄露和错误引用需要分别测试；没有业务写工具只能阻断其中一类风险，不能保证不会泄露数据或产生误导回答。

### 20.1 A：文本与公共检索

- [ ] 管理员可用；普通账号手工请求为 HTTP 403/业务码 2003；未登录按当前项目协议拒绝。
