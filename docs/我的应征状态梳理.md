# 我的应征状态梳理

> 文档状态：现状分析与待确认方案，尚未修改应征状态机。
> 最近检查：2026-08-25。

## 1. 当前数据结构

`application.status` 当前定义为：

| 值 | 当前文案 | 实际写入位置 |
| --- | --- | --- |
| `0` | 待处理 | 普通应征、接受定向邀请、重新应征 |
| `1` | 已通过 | 企划方点击选定应征 |
| `2` | 已拒绝 | 仅保留在表注释和前端映射中，当前没有业务接口写入 |
| `3` | 已撤销 | 画师主动撤销；企划订单完成结算时也写入同一个值 |

`GET /api/v1/applications/mine` 目前只返回应征 ID、企划 ID、标题、图片、报价、`application.status` 和应征时间。接口不返回关联订单 ID 或订单状态，因此前端只能直接把上述数字翻译成“待处理 / 已通过 / 已拒绝 / 已撤销”。

## 2. 当前状态变化

1. 发布普通应征或接受邀请后，应征状态为 `0`。
2. 企划方可以把 `0` 改为 `1`，但发企划订单同时允许 `0` 或 `1`，因此“已通过”不是创建订单的必要前置状态。
3. 画师只能撤销 `0`，撤销后改为 `3`。
4. 创建、接单、拒单、取消订单不会同步改变应征状态。
5. 企划订单完成结算时，对应应征也被改为 `3`，目的是退出有效应征列表并要求画师下次重新应征。
6. 状态 `2` 当前没有可到达的正式业务入口。

## 3. 已确认的问题

- `3` 同时表示“主动撤销”和“合作已完成后关闭”，但页面统一显示“已撤销”，语义错误。
- 页面无法显示订单的待接单、进行中、待验收、已完成、已取消或争议中状态。
- 当前画师撤销应征和修改报价只检查 `application.status=0`，没有检查是否已有非终态订单；理论上可能出现应征显示已撤销，但关联订单仍待接单或履约中的冲突。
- 本地主库现有 8 条有效应征：状态 `0` 为 3 条，状态 `3` 为 5 条，状态 `1/2` 均为 0。应征 `#2` 当前为 `3`，但仍关联待接单订单 `#28`，已经证明单看应征状态不能表达真实合作阶段。
- 重新应征会复用原记录并覆盖应征内容和创建时间，适合维持唯一关系，但无法单独保存每次应征的历史轮次。

## 4. 推荐方案

建议把“应征关系”和“订单履约”分成两层，不再要求一个数字同时表达两者。

### 4.1 应征关系状态

建议保留：

- `0`：等待企划方处理
- `1`：已被选定
- `2`：已拒绝（如果产品需要企划方拒绝入口）
- `3`：画师主动撤销
- `4`：合作已结束（新增，订单完成后写入）

如果产品不需要“拒绝应征”，应删除状态 `2` 的用户文案和死分支，不保留一个永远无法进入的状态。

### 4.2 合作进度

`/applications/mine` 应批量附加当前或最近关联订单：

```json
{
  "orderId": 28,
  "orderStatus": 0,
  "hasActiveOrder": true
}
```

页面优先显示订单进度：待接单、进行中、待验收、争议中；终态显示合作已完成或订单已取消。没有关联订单时，再显示等待处理、已被选定、已拒绝或已撤销。

### 4.3 操作保护

- 存在待接单、进行中、待验收或争议中订单时，禁止撤销应征和修改报价。
- 订单金额继续使用创建时快照，不受后续报价变化影响。
- 订单完成后使用“合作已结束”而不是“已撤销”；是否允许再次应征继续沿用企划仍在招募且没有非终态订单的规则。

## 5. 建议实施顺序

1. 先确认是否需要企划方“拒绝应征”功能，以及完成合作后是否允许同一画师再次应征。
2. 确认后补状态迁移和历史数据分类，不能直接把现有全部 `3` 批量改成同一新状态。
3. 扩展“我的应征”DTO，批量读取关联订单并增加撤销/改价保护。
4. 最后再调整“我的应征”页面卡片和用户文案，并做多订单、取消、完成和重新应征回归。
