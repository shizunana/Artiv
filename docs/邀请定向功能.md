# 定向邀请功能重做计划书

> 文档状态：重构基准。2026-08-24 已产生第一版实现，但尚未完成真实双账号 E2E，且已决定继续重构，不能视为正式验收完成。
> 原始审阅日期：2026-08-24。
> 审阅范围：定向企划发布、企划可见性、收到的邀请、接受/拒绝、应征、会话、系统消息及相关数据。
> 说明：第 1–3 节记录第一版实现开始前的代码与数据现状；后续章节作为重构时的产品规则和验收基准保留。

## 1. 审阅结论

当前邀请功能存在的不是单一页面问题，而是邀请状态没有和真实业务流程绑定。

现有“接受”操作只把 invitation.status 从待处理改成已接受，没有同步完成以下事项：

1. 没有创建 application 应征记录。
2. 没有建立企划方与画师的会话。
3. 没有写入会话中的系统提示卡片。
4. 没有向企划方产生对应的未读消息。
5. 接受后缺少稳定的企划详情入口。

因此页面会出现“邀请已接受”，但企划方应征列表、双方会话和后续选定画师流程均没有真实结果的伪状态。用户在“收到的邀请”列表直接接受时，甚至可能在尚未完整阅读企划内容的情况下改变业务状态。

代码审阅还确认了以下高风险问题：

1. 定向企划详情尚未完整校验受邀关系，其他用户可能通过已知企划 ID 读取定向企划。
2. 普通应征接口尚未在服务端严格阻止非受邀画师应征定向企划。
3. 企划与邀请关系创建尚未形成完整事务，失败时可能留下没有目标画师的定向企划。
4. 旧邀请响应接口只修改状态，无法满足新的接受/拒绝业务原子性。
5. 旧的独立邀请创建入口允许向已有定向企划追加邀请，与“一个定向企划只对应一名画师”的产品定义冲突。
6. “收到的邀请”接口直接返回邀请实体，无法稳定提供封面、企划名、类型、预算和详情入口。

结论：保留现有 project、invitation、application、message 数据模型主干，重做邀请响应流程；不再维护一条独立于应征和会话之外的“接受邀请”伪流程。

## 2. 最终产品规则

### 2.1 定向企划定义

- mode = 0：公开招募企划，可进入企划大厅，符合条件的已认证画师可以应征。
- mode = 1：定向邀请企划，不进入企划大厅、首页推荐或普通企划搜索。
- 一个定向企划只允许指定一名画师。
- 受邀对象必须是正常状态且 cert_status = 2 的已认证画师。
- 企划方不能邀请自己。
- 定向企划正文只允许企划创建者、受邀画师和管理员读取。
- 接受邀请不等于接单，也不自动创建订单；接受后仍由企划方在应征列表中完成后续选定。

### 2.2 最终流程

    企划方发布定向企划
      → 系统在同一事务中创建企划和唯一邀请关系
      → 画师在“收到的邀请”中点击“查看详细”
      → 进入定向企划详情
      → 画师在详情页选择“接受”或“拒绝”

接受：

    填写报价
      → 确认邀请
      → 创建普通 application 应征
      → invitation 改为已接受
      → 建立双方企划会话
      → 会话内写入带“查看详情”的系统提示卡片
      → 企划方后续查看应征、选定画师、创建订单

拒绝：

    填写婉拒理由
      → invitation 改为已拒绝并保存理由
      → 不创建 application
      → 不建立会话
      → 向企划方发送带“查看详情”的系统消息

### 5.3 接受弹窗

点击“接受”后复用普通应征弹窗的布局，但只保留：

- 报价（元），必填且大于 0。
- 取消。
- 确认邀请。

邀请接受场景不显示“应征介绍”，创建的 application.intro 允许为空。

接受仍必须满足普通应征的核心校验：

- 当前账号正常。
- cert_status = 2。
- 至少有 4 件公开作品。
- 企划仍处于有效招募期。
- 当前用户是该企划唯一受邀画师。
- 报价合法。
- 当前画师尚未对该企划形成有效应征。

### 5.4 拒绝弹窗

- 婉拒理由必填，最多 500 字。
- 提交前进行二次确认。
- 成功后详情页显示“已拒绝”。
- 拒绝后不能再次接受；如需重新邀请，必须由后续独立产品流程处理，本期不自动恢复。

## 6. 接受与拒绝的后端事务

### 6.1 接受事务

建议新增 InvitationService.accept，并使用事务完成：

1. 按邀请 ID 锁定或条件更新待处理邀请。
2. 校验当前用户就是 painter_id。
3. 校验企划 mode = 1、企划有效且邀请与企划一致。
4. 复用普通应征校验，创建一条 application，intro 为空、quote 为画师填写报价。
5. 更新 invitation.status = 1、application_id 和 responded_at。
6. 建立 employer 与 painter 的企划会话。
7. 在会话中写入居中的业务系统卡片，携带 projectId 和“查看详情”。
8. 事务提交后再通过 WebSocket 推送，避免数据库回滚但客户端已经收到消息。

会话系统提示文案固定为：

画师【名字】接受了您的企划【企划标题】的邀请，双方已建立会话，您可以开始与画师沟通后续合作内容。

该消息就是接受后的会话启动消息，不再额外产生一张内容相同的系统通知，避免企划方收到两条重复未读。

接受只创建应征和会话，不自动选定画师，不自动创建订单。

### 6.2 拒绝事务

建议新增 InvitationService.reject，并使用事务完成：

1. 锁定或条件更新待处理邀请。
2. 校验当前用户就是受邀画师。
3. 校验并保存拒绝理由。
4. 更新 invitation.status = 2 和 responded_at。
5. 不创建 application、会话或订单。
6. 向企划方系统消息中心写入一条通知，携带 projectId 和“查看详情”。
7. 事务提交后再推送 WebSocket 未读变化。

系统消息文案固定为：

画师【名字】婉拒了您的企划【企划标题】的邀请，婉拒理由【拒绝理由】

### 6.3 并发与幂等

- 接受和拒绝都只能处理 status = 0 的邀请。
- 使用条件更新或行锁，确保接受、拒绝并发时只有一个成功。
- application 继续依赖 project_id + painter_id 唯一约束防止重复应征。
- 会话启动消息使用唯一 starter_key，例如 invitation:{invitationId}:accepted。
- 重复点击接受不得产生第二条应征或第二个会话启动卡片。
- 任一步骤失败时，邀请状态、应征和消息必须整体回滚。

## 7. 权限规则

所有权限由后端强制校验，前端按钮只负责体验。

| 操作 | 企划创建者 | 受邀画师 | 其他用户 | 管理员 |
| --- | --- | --- | --- | --- |
| 在公开企划列表看见定向企划 | 否 | 否 | 否 | 否，管理端另查 |
| 读取定向企划正文 | 是 | 是 | 否 | 是 |
| 接受或拒绝 | 否 | 是，仅待处理 | 否 | 否 |
| 对定向企划创建应征 | 否 | 是，只能通过接受事务 | 否 | 否 |
| 查看完整应征列表 | 是 | 仅查看自己的结果 | 否 | 是 |
| 选定应征并创建订单 | 是 | 否 | 否 | 否 |

服务端必须补充：

1. GET /projects/{id} 遇到 mode = 1 时验证创建者、受邀画师或管理员。
2. 普通 POST /projects/{id}/applications 遇到 mode = 1 时拒绝外部直接创建，定向应征只允许邀请接受服务内部调用。
3. 定向企划应征列表不得向无关用户泄露画师、报价和作品信息。
4. 无权访问时按资源不存在返回，避免泄露企划是否存在。

## 12. 必须验证的模块

### 12.1 列表与详情

- [ ] 邀请列表严格显示封面、企划名、类型、预算、企划详情。
- [ ] 无封面行与有封面行等高，不显示破图。
- [ ] 列表没有接受、拒绝。
- [ ] 查看详细进入正确的定向企划。
- [ ] 其他用户按 ID 访问同一企划时无法获得正文。

### 12.2 接受

- [ ] 接受弹窗只有报价。
- [ ] 认证、4 件公开作品、招募期和报价校验继续生效。
- [ ] 成功后恰好生成一条 application。
- [ ] invitation 状态、application_id、responded_at 同步正确。
- [ ] 双方建立一个企划会话。
- [ ] 会话中出现固定文案的系统卡片及查看详情。
- [ ] 企划方收到一条未读，打开会话后未读正确消除。
- [ ] 接受不会自动创建订单。

### 12.3 拒绝

- [ ] 空理由不能提交，超过 500 字不能提交。
- [ ] 拒绝后不创建 application、会话或订单。
- [ ] 企划方收到固定格式的系统消息。
- [ ] 系统消息查看详情进入正确企划。
- [ ] 系统消息未读数量和消除行为正确。

### 12.4 并发、回滚与权限

- [ ] 双击接受只生成一条应征和一条会话启动卡片。
- [ ] 接受和拒绝并发时只有一个成功。
- [ ] 应征、邀请状态或消息任一步失败时全部回滚。
- [ ] 非受邀画师伪造接受、拒绝或应征请求均被后端拒绝。
- [ ] 一个定向企划不能追加第二名画师。
- [ ] 企划与邀请任一创建失败时整体回滚。

### 12.5 回归

- [ ] 普通公开企划应征不受影响。
- [ ] 企划方查看应征、沟通、选定和创建订单不受影响。
- [ ] 原有消息会话、系统消息、未读和 WebSocket 不受影响。
- [ ] 定向企划仍不会出现在公共企划列表和推荐中。

## 13. 验收标准

1. 邀请列表只有企划摘要和详情入口，不再直接改变业务状态。
2. 接受、拒绝只能由唯一受邀画师在定向企划详情执行。
3. 接受在一个事务中生成真实应征和会话系统卡片，不产生订单。
4. 拒绝保存结构化理由，只发送系统消息，不建立会话。
5. invitation.status 与 application、会话和拒绝原因始终一致。
6. 定向企划正文不会泄露给无关用户。
7. 后续应征管理、选定画师和订单流程完全复用普通企划。
8. 并发、重复提交、异常回滚、未读和详情跳转均通过验证。
9. 数据迁移、init.sql、接口文档和进度文档同步完成。
