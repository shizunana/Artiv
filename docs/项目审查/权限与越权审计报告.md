# 艺绘（Artiv）权限与越权审计报告

> 所属文档集：项目审查  
> 审查日期：2026-08-28  
> 审查基线：`main` / `153e6ad`  
> 项目版本口径：`v0.8.13-beta`  
> 审查范围：HTTP 接口、管理员接口、资源归属、账号状态、文件访问、WebSocket、跨域配置  
> 说明：本报告为静态代码与调用链审查，不等同于完整渗透测试；本次只输出报告，未修改业务代码。

## 1. 结论摘要

Artiv 的主体业务权限并没有出现“只要登录就能随意操作别人资源”的普遍性问题。企划、橱窗、作品、订单、应征、邀请、争议、评价和私信等核心服务普遍在服务层再次检查资源归属或交易参与者；管理员接口也会以数据库中的当前角色、封禁状态和删除状态为准，而不是仅相信 JWT 中的旧角色。

本次确认 6 项需要整改的权限边界问题：

| 级别 | 数量 | 主要内容 |
| --- | ---: | --- |
| P1 高 | 3 | 用户私有字段越权读取、订单原稿匿名访问、仓库内固定 JWT 密钥 |
| P2 中 | 3 | 上传文件缺少归属模型、WebSocket 鉴权边界不足、生产跨域范围过宽 |

其中前两项是已经存在的直接越权路径：登录用户可枚举旧用户详情接口，匿名访问者可在已知 URL 时直接读取订单原稿。正式部署前应优先解决。

## 2. 已核对且基本正确的权限边界

| 模块 | 当前边界 | 结论 |
| --- | --- | --- |
| 管理员接口 | `AuthInterceptor` 对 `/api/v1/admin/**` 重新查询用户，要求 `role=3`、正常状态且未删除 | 正确；不会只依赖 JWT 中可能过期的角色 |
| 企划管理 | 更新、上下架、修改截稿日期和删除均通过 `ProjectServiceImpl.requireOwned` 校验企划方 | 正确 |
| 橱窗与作品 | 修改、状态变化和删除均比较当前用户与 `painterId/userId` | 正确 |
| 订单 | 查看与所有状态动作均通过 `requireParticipant`，再区分企划方或画师动作权限 | 正确 |
| 争议与评价 | 发起、查看、补证、评价和申诉均校验订单参与者或评价接收方 | 正确 |
| 应征与邀请 | 企划方操作校验企划归属；画师处理邀请、改价和撤回应征校验 `painterId` | 正确，但并发一致性问题见事务专项报告 |
| 私信 | 企划会话要求真实应征关系且已建立会话；订单会话要求双方与订单参与者完全匹配 | 正确 |
| 封禁策略 | 已封禁账号仍可登录、浏览公开内容和查看历史交易，但新建交易关系由 `AccountRestrictionService` 拦截 | 与现有产品文档口径一致，不作为漏洞 |
| 公共企划应征画师 | `/projects/{id}/applications` 被明确作为企划详情公开展示信息 | 属于当前产品设计，不作为越权问题；如未来要隐藏报价或身份，应改为专用公开 DTO |

## 3. 详细问题

## PA-01：旧用户详情接口暴露完整持久化实体

- **级别：P1 高**
- **类型：水平越权读取 / 隐私泄露**

### 证据

- `backend/src/main/java/com/artiv/controller/UserController.java:170-177` 的 `GET /api/v1/users/{id}` 直接返回 `Result<User>`，只清空密码；
- `backend/src/main/java/com/artiv/entity/User.java:32-73` 中的余额、角色、认证状态、封禁原因、封禁管理员和封禁时间等字段仍会序列化；
- `backend/src/main/java/com/artiv/security/AuthInterceptor.java:66-104` 未将该旧接口列为匿名公开路径，因此任意登录账号均可通过替换数字 ID 枚举他人资料；接口没有“只能查看自己”的限制；
- 项目已经提供 `/users/{id}/public-profile` 专用公开响应，因此旧接口没有继续返回完整实体的必要。

### 影响

普通登录用户能够读取其他账号的余额和内部治理信息。未来只要给 `User` 实体新增字段，该接口还会在没有安全评审的情况下自动扩大暴露面。

### 建议

1. 删除或废弃 `GET /api/v1/users/{id}`；
2. 公开主页统一使用 `PublicProfileResponse`，本人资料使用独立私有 DTO；
3. 控制器禁止直接返回持久化实体；
4. 增加越权测试，断言响应中不存在 `balance`、`banReason`、`bannedBy`、`bannedAt`、`bannedUntil`。

## PA-02：订单原稿位于匿名可访问的静态上传目录

- **级别：P1 高**
- **类型：文件级越权 / 授权绕过**

### 证据

- `backend/src/main/java/com/artiv/config/WebMvcConfig.java:37-41` 将整个上传目录映射为 `/uploads/**`，而拦截器只覆盖 `/api/**`；
- `backend/src/main/java/com/artiv/service/impl/OrderServiceImpl.java:306-334` 将交付原稿 URL 写入 `OrderStage.originals`，同时生成水印预览；
- `backend/src/main/java/com/artiv/service/impl/OrderServiceImpl.java:618-622` 仅在订单未完成时从接口响应副本中隐藏原稿地址；
- `backend/src/main/java/com/artiv/service/OrderPreviewService.java:35-70` 的原稿与预览共用同一个上传根目录。

### 影响

只要原稿 URL 从浏览器历史、日志、数据库、消息或其他页面泄露，匿名访问者就能绕过订单参与者和订单状态直接下载文件。UUID 文件名只能降低猜中概率，不能替代权限校验。

### 建议

1. 将订单原稿迁移到静态资源映射之外的私有目录；
2. 通过受控下载接口读取，校验访问者是否为订单参与者以及当前订单状态；
3. 为历史原稿做引用迁移，不能只修复新上传文件；
4. 水印预览与公开业务图片可继续使用公开 URL，但应明确用途边界。

## PA-03：默认配置提交了可直接使用的固定 JWT 密钥

- **级别：P1 高**
- **类型：鉴权根密钥泄露**

### 证据

- `backend/src/main/resources/application.yml:29-33` 提交了固定 JWT 签名密钥；
- 同一配置的 `8-10` 行还包含 `root / 123456` 数据库凭据；
- 当前只有“生产环境务必覆盖”的注释，没有启动时强制校验。

### 影响

若演示或部署环境直接使用仓库默认配置，知道源码的人可以签发任意用户甚至管理员令牌。此问题会使其他接口层权限检查失去意义。

### 建议

1. 生产密钥和数据库凭据只从环境变量或未提交的本地配置读取；
2. 非开发环境命中默认值时拒绝启动；
3. 部署前轮换当前密钥，并使旧令牌失效；
4. 数据库改用最小权限账号，不使用 `root`。

## PA-04：上传记录没有上传者、用途和业务归属

- **级别：P2 中**
- **类型：对象归属缺失 / 文件地址复用**

### 证据

- `backend/src/main/java/com/artiv/controller/UploadController.java:41-63` 只保存随机文件名并返回 URL，没有写入上传记录；
- 头像、订单交付、争议、评价和举报等入口主要通过 `startsWith("/uploads/")` 与 `..` 检查验证地址；
- 例如 `UserController.java:157-164`、`DisputeServiceImpl.java:251`、`ReportServiceImpl.java:266`、`ReviewServiceImpl.java:380` 和 `OrderServiceImpl.java:610-615` 都无法证明该文件由当前用户上传，也无法证明它属于当前业务用途。

### 影响

已登录用户只要知道另一个上传 URL，就可能把对方图片绑定为自己的头像、作品、评价证据或交付文件。虽然不会修改原文件，但会造成冒用、错误归属和后续清理困难。

### 建议

建立上传元数据表，至少记录 `uploader_id`、用途、存储键、可见性、关联业务 ID 和创建时间；业务保存文件地址时必须校验当前用户、用途与一次性绑定状态。

## PA-05：WebSocket 使用 URL 长期 JWT，且握手不校验当前账号状态

- **级别：P2 中**
- **类型：实时通信鉴权边界**

### 证据

- `frontend/src/utils/ws.js:10-20` 将登录 JWT 拼接到 `?token=`；
- `backend/src/main/java/com/artiv/websocket/MessageWebSocketHandler.java:67-77` 只验证令牌签名并解析用户 ID，没有查询账号是否已封禁或删除；
- `backend/src/main/java/com/artiv/config/WebSocketConfig.java:22-25` 允许任意 Origin；
- 已建立连接不会在用户封禁后被主动关闭。

### 影响

查询参数可能进入代理访问日志、诊断工具和错误报告。账号被封禁或删除后，未过期令牌仍可建立实时连接；原有连接也可能继续接收消息。

### 建议

使用短时、单次 WebSocket ticket；握手时查询账号当前状态；限制生产 Origin；封禁或删除账号时关闭其现有连接。

## PA-06：生产 API 跨域允许任意来源并携带凭据

- **级别：P2 中**
- **类型：浏览器安全边界 / 部署配置**

### 证据

- `backend/src/main/java/com/artiv/config/CorsConfig.java:13-20` 对 `/api/**` 使用 `allowedOriginPatterns("*")`、任意请求头和 `allowCredentials(true)`；
- WebSocket 同样允许任意 Origin。

### 影响

当前令牌主要通过 `Authorization` 头发送，传统 Cookie CSRF 风险有限，但任意站点仍可从浏览器直接调用接口，扩大钓鱼页面、令牌泄露后的滥用面，也容易在未来引入 Cookie 后形成真实跨站风险。

### 建议

区分开发和生产配置；生产只允许实际前端域名，并同步限制 WebSocket Origin。若未来改用 Cookie，需要同时设计 SameSite 与 CSRF 防护。

## 4. 推荐整改顺序

1. **立即处理 PA-01、PA-02、PA-03**：分别关闭直接数据越权、文件授权绕过和令牌伪造根风险；
2. **建立文件元数据后处理 PA-04**：与私有原稿迁移一起设计，避免重复改造；
3. **部署前处理 PA-05、PA-06**：统一真实前端域名、WebSocket ticket 与账号状态校验；
4. 增加权限回归矩阵：匿名、普通用户、资源所有者、交易对方、封禁用户、管理员分别访问同一接口；
5. 所有新增控制器继续遵循“控制器取当前用户，服务层校验资源归属”的现有模式。

## 5. 最终判断

除上述问题外，本次没有发现可通过简单替换企划 ID、橱窗 ID、订单 ID、应征 ID、邀请 ID、争议 ID 或评价 ID 来直接修改他人核心业务数据的通用漏洞。当前权限体系的主要短板不在主体业务动作，而在旧接口、文件访问和实时通信等边缘入口。

正式部署阻断项：**PA-01、PA-02、PA-03**。
