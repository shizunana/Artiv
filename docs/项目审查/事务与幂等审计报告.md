# 艺绘（Artiv）事务与幂等审计报告

> 所属文档集：项目审查  
> 审查日期：2026-08-28  
> 审查基线：`main` / `153e6ad`  
> 项目版本口径：`v0.8.13-beta`  
> 审查范围：订单资金与库存、应征、邀请、认证、黑名单、举报、争议、评价、消息落库与实时推送  
> 说明：本报告为静态代码与数据库约束审查；本次只输出报告，未修改业务代码，也未执行并发压测。

## 1. 结论摘要

Artiv 的订单主状态机已经具备较好的事务基础：购买与发送订单、接单、拒绝、取消、交付、验收、结算、退款和仲裁均在事务中执行；订单、余额、库存、应征等关键记录按需要使用 `SELECT ... FOR UPDATE`；消息与事件和业务数据共同落库，WebSocket 推送延迟到事务提交后执行。

本次确认 6 项需要整改的问题：

| 级别 | 数量 | 主要内容 |
| --- | ---: | --- |
| P1 高 | 3 | 橱窗购买重复扣款、应征状态并发覆盖、黑名单与新订单并发突破互斥规则 |
| P2 中 | 2 | 应征/邀请并发产生未归一化数据库异常、管理员封禁锁顺序存在死锁窗口 |
| P3 低 | 1 | 数据库回滚后可能残留水印预览文件 |

## 2. 当前已经做得较好的部分

| 流程 | 事务与幂等措施 | 结论 |
| --- | --- | --- |
| 企划订单创建 | 锁定应征记录，检查同一应征是否已有非终态订单，再锁定企划方余额 | 可防止同一应征并发生成两笔有效订单 |
| 订单状态动作 | 先锁订单行，再校验当前状态和动作角色；退款、库存恢复和结算均在同一事务内 | 核心资金副作用只会成功一次；重复请求会得到状态流转错误 |
| 阶段交付与验收 | 锁订单后计算提交版本并改变订单状态 | 同一订单无法同时重复交付或重复结算 |
| 认证申请 | `requireApplicantForUpdate` 锁用户行，再检查认证状态和待审核申请 | 同一账号的重复认证提交被串行化 |
| 争议与评价 | 锁订单或争议/评价记录，同时使用唯一约束限制一单一争议、一方一评价、一评一申诉 | 边界完整；重复提交会转换为业务错误 |
| 收藏、关注、黑名单、举报 | 数据库唯一约束配合 `DuplicateKeyException` 处理 | 多数入口已具备结果幂等 |
| 会话起始消息 | `starter_key` 唯一约束，冲突后读取已有消息 | 可以避免重复建立同一企划会话入口 |
| 实时推送 | `MessageServiceImpl:538-568` 先写消息，事务存在时在 `afterCommit` 推送；推送失败不回滚已落库消息 | 避免客户端收到最终回滚的“幽灵消息”，重连后可补拉 |

需要区分两类语义：订单动作目前属于“副作用安全”，重复请求不会重复退款或结算，但第二次通常返回状态错误，并非返回第一次结果的严格 HTTP 幂等。

## 3. 详细问题

## TI-01：橱窗购买没有请求幂等键，网络重试会重复扣款并重复减库存

- **级别：P1 高**
- **类型：资金幂等 / 重复提交**

### 证据

- `backend/src/main/java/com/artiv/service/impl/OrderServiceImpl.java:141-186` 在事务内锁定橱窗与企划方余额，然后直接扣款、减库存并插入订单；
- 该流程没有客户端请求号、业务幂等键或“同一请求已创建订单”的查询；
- `order_info` 表也没有可表达购买请求唯一性的字段或唯一约束。

### 影响

用户双击购买、前端超时自动重试、反向代理重放或客户端在“提交已成功但响应丢失”后再次提交，都会被解释为两次合法购买：生成两笔订单、扣两次余额并减少两件库存。行锁只能保证余额和库存计算正确，不能判断两次请求是否属于同一次用户意图。

### 建议

1. 购买请求增加 `idempotencyKey`，由客户端为一次确认动作生成 UUID；
2. 建立 `(employer_id, idempotency_key)` 唯一约束，并在同一事务中先查或插入；
3. 重复请求返回第一次创建的订单，而不是再次扣款；
4. 幂等键应绑定请求摘要（橱窗、价格、买家），防止同一键被复用于不同请求；
5. 增加“提交成功但响应丢失后重试”的集成测试。

## TI-02：应征选择、改价、撤回和重新激活可能发生陈旧实体覆盖

- **级别：P1 高**
- **类型：并发状态机 / 丢失更新**

### 证据

- `backend/src/main/java/com/artiv/service/impl/ApplicationServiceImpl.java:302-365` 的选择、改价和撤回先普通查询，再修改完整实体并 `updateById`，方法没有事务锁；
- `ApplicationServiceImpl.java:256-288` 的重新激活也采用“查询后覆盖实体”；
- `backend/src/main/java/com/artiv/mapper/ApplicationMapper.java:13` 已提供 `selectByIdForUpdate`，但上述入口没有使用；
- 订单结算会在 `OrderServiceImpl.java:544-554` 锁定应征并将其结束。

### 影响

改价请求可能先读取 `active=1`，订单随后完成并写入 `active=0`，最后改价以旧实体执行完整更新，从而把已结束应征重新写回有效。选择与撤回并发时也可能出现 `status`、`active`、`endedReason` 不一致。

### 建议

1. 所有应征状态变化统一加入事务并锁定应征；
2. 简单动作优先使用窄字段条件更新并检查影响行数，例如只在 `active=1` 时更新报价；
3. 增加乐观锁版本字段，避免未来入口再次覆盖新状态；
4. 添加并发测试：改价 vs 订单完成、撤回 vs 企划方选中、重新应征 vs 邀请接受。

## TI-03：加入黑名单与创建新订单之间存在检查后使用竞态

- **级别：P1 高**
- **类型：跨聚合事务 / 业务互斥失效**

### 证据

- `backend/src/main/java/com/artiv/service/impl/UserBlockServiceImpl.java:54-93` 先查询双方非终态订单数量，确认没有订单后才插入黑名单；该查询没有锁定双方用户或一个稳定的关系键；
- `OrderServiceImpl.java:142-185` 的橱窗购买先检查双方未拉黑，再在后续插入订单；
- `OrderServiceImpl.java:191-252` 的企划订单同样先检查黑名单，之后才扣款并插入订单；
- 两条事务没有共同的锁顺序，也没有数据库约束表达“黑名单关系与非终态订单不能同时存在”。

### 可能时序

1. 下单事务检查双方尚未拉黑；
2. 黑名单事务检查双方尚无非终态订单；
3. 黑名单事务插入关系；
4. 下单事务插入非终态订单并提交；
5. 最终同时存在黑名单和进行中订单，违反产品规则。

### 建议

为“双方关系变化”建立统一串行化点。可按用户 ID 排序后依次锁定两条用户记录，再重新检查黑名单和非终态订单；所有下单与拉黑入口遵循完全相同的锁顺序。随后增加“拉黑 vs 橱窗购买”“拉黑 vs 企划订单”并发测试。

## TI-04：普通应征与邀请接受并发时，唯一约束异常未统一转换

- **级别：P2 中**
- **类型：并发重试体验 / 异常归一化**

### 证据

- `application` 表通过 `uk_project_painter(project_id, painter_id)` 阻止重复关系；
- `ApplicationServiceImpl.java:256-288` 先查询再插入或重新激活，插入没有捕获 `DuplicateKeyException`；
- `InvitationServiceImpl.java:180-246` 在条件更新邀请状态前先调用 `createFromInvitation`；
- 同一画师若同时从企划页普通应征、从邀请页接受，或重复发送接受请求，数据库能阻止两条应征，但其中一个请求可能直接冒出数据库冲突而不是明确的业务结果。

### 影响

数据通常不会重复，但用户可能看到通用服务器错误；日志与监控也会把可预期并发冲突记录为系统异常。对已结束应征的并发重新激活仍可能重复发送业务通知。

### 建议

在同一企划与画师维度串行化创建/激活，或捕获唯一键冲突后重新读取关系并按当前状态返回明确业务结果。邀请状态仍应保留现有 `WHERE status=PENDING` 条件更新。

## TI-05：管理员封禁与订单动作的锁获取顺序可能形成数据库死锁

- **级别：P2 中**
- **类型：锁顺序 / 运维可靠性**

### 证据

- `backend/src/main/java/com/artiv/service/impl/AdminUserServiceImpl.java:83-128` 封禁流程先锁用户，再调用订单取消；
- `OrderServiceImpl.java:400-415` 随后按订单 ID 锁订单；退款路径又锁企划方与橱窗；
- 普通订单动作则通常先锁订单，再在结算或退款时锁用户（`OrderServiceImpl.java:420-457`、`:532-554`）；
- 这形成“用户 → 订单”和“订单 → 用户”两种相反锁顺序。

### 影响

管理员封禁与用户验收、取消、拒绝或仲裁同时发生时，数据库可能检测到死锁并回滚其中一个事务。数据库回滚能保护一致性，但管理员会遇到偶发失败，若上层无重试会留下未完成治理动作。

### 建议

统一核心锁顺序，例如始终先按 ID 锁订单，再按 ID 顺序锁相关用户和橱窗；或将封禁标记与订单清理拆为可重试的治理任务。对数据库死锁异常增加有限次数重试和明确审计记录。

## TI-06：水印预览文件不参与数据库事务，回滚后可能留下孤儿文件

- **级别：P3 低**
- **类型：数据库与文件系统一致性**

### 证据

- `OrderServiceImpl.java:307-334` 在订单事务内先生成水印预览文件，再插入阶段记录并更新订单；
- 文件系统写入无法随数据库事务回滚；
- 如果后续数据库插入、消息写入或事务提交失败，已生成预览文件不会自动删除。

### 影响

不会导致重复结算，但会积累没有数据库引用的文件，增加磁盘占用，并使未来私有文件清理更困难。

### 建议

记录临时文件并在事务回滚回调中删除，或先写临时目录、提交后再原子移动；同时增加定期孤儿文件清理任务和引用审计。

## 4. 关键流程幂等矩阵

| 操作 | 当前重复请求表现 | 数据副作用是否安全 | 评价 |
| --- | --- | --- | --- |
| 橱窗购买 | 每次都创建新订单并扣款 | 否 | **必须补幂等键** |
| 发送企划订单 | 应征行锁串行化，已有非终态订单时报错 | 是 | 可接受；可进一步返回已有订单 |
| 接单、拒单、取消、交付、验收、仲裁 | 首次成功，后续因状态不符报错 | 是 | 副作用幂等，不是响应幂等 |
| 提交认证 | 用户行锁与状态检查阻止重复 | 是 | 良好 |
| 发起争议 | 订单行锁与一单一争议约束 | 是 | 良好 |
| 提交评价、评价申诉 | 行锁、唯一约束和冲突转换 | 是 | 良好 |
| 收藏、关注、拉黑、举报 | 唯一约束，重复写入被吞并或返回已有结果 | 是 | 单动作良好；拉黑与下单跨动作竞态仍需处理 |
| 建立企划会话 | `starter_key` 唯一，冲突后返回已有起始消息 | 是 | 良好 |
| 普通应征/邀请接受 | 唯一约束保数据，但并发冲突可能暴露数据库异常 | 基本安全 | 需要异常归一化和锁 |

## 5. 推荐整改顺序

1. **TI-01**：先为橱窗购买补传输级幂等键，直接消除重复扣款风险；
2. **TI-02**：统一应征状态机的锁与条件更新；
3. **TI-03**：为拉黑和下单建立共同串行化点；
4. **TI-04、TI-05**：统一并发冲突的业务错误和全局锁顺序；
5. **TI-06**：在私有文件存储改造时一并建立提交/回滚清理机制；
6. 使用两个独立数据库连接编写并发集成测试，不能只用串行单元测试模拟。

## 6. 最终判断

订单状态机内部的事务、行锁、退款和结算路径总体可靠，消息也不会早于事务提交推送。当前正式部署的主要阻断点不是“完全没有事务”，而是三个跨请求或跨聚合边界：**购买请求缺少幂等身份、应征更新可能陈旧覆盖、拉黑与下单缺少共同锁**。

正式部署阻断项：**TI-01、TI-02、TI-03**。
