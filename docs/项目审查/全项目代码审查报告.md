# Artiv 全项目代码审查报告

> 审查日期：2026-08-29
>
> 审查基线：`f0a5643`
>
> 审查性质：正式全项目源码审查，仅输出审查结论，不包含功能开发或代码修改
> 审查范围：`backend`、`frontend`、`backend/sql/init.sql`、根目录配置及 `docs` 中的业务、接口、交接、测试和既有审计文档

## 1. 总体结论

### 1.1 项目结构与规模

Artiv 是一个围绕企划发布、画师应征、摊位购买、订单履约、站内沟通、评价申诉和后台治理构建的前后端分离项目：

- 前端：Vue 3、Vite、Pinia、Vue Router、Axios、Element Plus。
- 后端：Spring Boot、MyBatis-Plus、JWT、WebSocket、MySQL。
- 核心领域：用户、作品、摊位、企划、应征、邀请、订单、订单阶段、消息、评价、申诉、举报、画师认证和后台管理。
- 数据库：初始化脚本共 24 张业务表。
- 接口层：约 25 个 Controller、129 个接口映射。
- 自动化测试：后端 26 个测试类、170 个测试用例；前端暂未发现自动化测试。

本次审查覆盖了控制器、服务层、实体与 DTO、Mapper、鉴权与 WebSocket、前端 API/路由/状态管理/主要页面、数据库表和索引，以及文档中定义的业务规则。审查以静态分析和已有自动化验证为主，没有连接生产数据库，也没有执行真实支付、渗透、压力或多实例并发测试。

### 1.2 健康度判断

项目核心业务闭环已经比较完整，订单关键状态迁移普遍使用事务和行锁，评价、申诉、举报、认证、封禁等功能也已有成体系的实现。代码并不是“不可维护”状态，且后端测试和前端生产构建均能通过。

但当前版本仍不适合在未整改的情况下直接按公网生产标准发布。阻断发布的主要原因不是普通代码风格，而是以下五类确定性高风险：

1. 旧用户详情接口返回完整用户实体，存在越权读取敏感字段的问题。
2. `/uploads/**` 被直接公开映射，使订单原图、举报/争议证据等业务授权可以被静态资源入口绕过。
3. 仓库内存在可工作的固定 JWT 默认密钥和数据库默认凭据；若部署未覆盖，令牌可被伪造。
4. 摊位购买没有幂等键，重复请求会重复扣款、减库存和创建订单。
5. 普通私信接口允许任意登录用户在没有业务关系和会话发起权的情况下直接创建会话。

- `npm.cmd run build`：通过。

### 1.5 做得较好的部分

- 订单接单、交付、验收、取消、争议及结算等关键路径普遍放在事务内，并对订单、用户或相关记录使用了行锁。

## 2. 安全、权限与资金安全：必须立即处理

### CR-001 旧用户详情接口可越权读取完整用户实体

- **优先级**：P0
- **问题类型**：权限 / 隐私泄露 / API 契约
- **涉及文件**：`backend/src/main/java/com/artiv/controller/UserController.java`、`backend/src/main/java/com/artiv/entity/User.java`
- **涉及方法或接口**：`GET /api/users/{id}`，`UserController#getById`
- **当前实现**：接口接收任意用户 ID，直接执行 `userMapper.selectById(id)` 并返回 `Result<User>`。实体仅通过 `@JsonIgnore` 隐藏密码和删除标记。
- **问题说明**：任意已登录用户可枚举其他用户 ID，读取不属于公开资料契约的字段，包括用户名、余额、角色、认证状态、封禁状态及原因、封禁操作者和时间、后台状态等。项目已经有 `/users/{id}/public-profile` 安全 DTO，但旧接口仍然可用。
- **触发条件**：攻击者拥有任意正常账号，并请求其他用户的 `/api/users/{id}`。
- **影响范围**：全部用户；管理员或被封禁用户的状态信息尤其敏感。还会使前端或外部调用方继续依赖内部实体字段，增加后续收口难度。
- **证据**：`UserController.java:171-177` 直接按路径 ID 查询并返回 `User`；`User.java` 中只有 `password`、`deleted` 被隐藏，其余内部字段可序列化。
- **建议修复方式**：移除或限制旧接口；若确有后台用途，应拆成管理员专用接口并返回白名单 DTO。普通用户资料统一复用 `PublicProfileResponse` 一类的公开 DTO。增加“普通用户不能读取他人内部字段”的接口测试。
- **修复风险**：中。可能存在未被仓库内代码引用的旧客户端，需要先通过访问日志确认调用方。
- **是否需要人工确认**：需要确认旧接口是否仍被外部客户端使用，但不影响其必须收口的结论。

### CR-002 公开静态资源映射绕过订单原图和证据文件授权

- **优先级**：P0
- **问题类型**：权限 / 敏感文件访问
- **涉及文件**：`backend/src/main/java/com/artiv/config/WebMvcConfig.java`、`backend/src/main/java/com/artiv/config/AuthInterceptor.java`、`backend/src/main/java/com/artiv/service/impl/OrderServiceImpl.java`、上传及评价/举报/争议相关服务
- **涉及方法或接口**：`/uploads/**` 资源映射；订单详情原图展示逻辑；上传接口
- **当前实现**：`WebMvcConfig#addResourceHandlers` 将上传目录整体映射为公开 `/uploads/**`。鉴权拦截器只处理 `/api/**`。订单详情服务虽然按订单状态和参与者决定是否返回原图地址，但知道或猜到 URL 的访问者可直接访问静态文件。
- **问题说明**：业务层的“雇主完成订单后才能查看原图”“只有争议参与方或管理员可查看证据”等规则，只限制了 URL 的返回，并没有限制文件本身。URL 一旦出现在日志、历史消息、浏览器缓存或被分享，即可绕过业务授权。
- **触发条件**：获得任意受保护文件的 `/uploads/...` 地址，或文件命名/目录信息泄露。
- **影响范围**：订单交付原图、评价图片、举报证据、争议证据，以及未来上传到同一目录的所有文件。
- **证据**：`WebMvcConfig.java:38-41` 对上传目录做无条件资源映射；订单阶段记录保存 `/uploads/` 路径，授权发生在订单详情响应层而不是文件读取层。
- **建议修复方式**：将公开素材和受保护素材分离存储。受保护文件通过带业务授权的下载接口或短时签名 URL 提供；数据库保存文件对象 ID、所有者、用途和可见性，不直接把物理路径当权限凭据。迁移期间应避免继续生成永久公开的原图 URL。
- **修复风险**：高。会涉及历史文件路径、前端图片展示和可能的对象存储迁移，应设计兼容期。
- **是否需要人工确认**：需要确认线上存储结构和历史 URL，但漏洞本身无需再确认。

### CR-003 默认 JWT 密钥与数据库凭据进入版本库

- **优先级**：P0
- **问题类型**：配置安全 / 身份伪造
- **涉及文件**：`backend/src/main/resources/application.yml`、`backend/src/main/java/com/artiv/security/JwtUtil.java`、部署配置
- **涉及方法或接口**：JWT 签发与验证；数据源初始化
- **当前实现**：主配置包含固定且可工作的 JWT 默认密钥及数据库默认连接凭据。`JwtUtil` 直接以该配置进行 HMAC 签名验证。
- **问题说明**：如果任一环境没有显式覆盖默认密钥，取得源码的人可以自行签发任意用户 ID 的有效令牌。管理员拦截器虽然会回查数据库角色，但攻击者只需伪造一个实际管理员用户 ID 即可进入管理员接口。数据库凭据复用还会扩大泄露影响。
- **触发条件**：测试、演示或生产部署沿用仓库默认值；或相同凭据在其他环境复用。
- **影响范围**：所有受 JWT 保护的接口、管理员功能和数据库。
- **证据**：`application.yml` 存在非空默认值；`JwtUtil` 使用配置密钥生成和解析令牌，令牌有效期为 24 小时，未引入服务端版本或撤销校验。
- **建议修复方式**：从版本库移除真实可用默认值，改为环境变量/密钥管理系统强制注入；应用启动时拒绝空值、示例值或低强度密钥；轮换所有可能已使用的密钥和密码。为 JWT 增加密钥版本、用户令牌版本或撤销机制。
- **修复风险**：中。轮换会使现有会话失效，应提前安排登录态切换窗口。
- **是否需要人工确认**：必须人工确认各部署环境是否已覆盖，并核查这些值是否曾被真实使用。

### CR-004 摊位购买缺少请求幂等，重复请求会重复扣款和建单

- **优先级**：P0
- **问题类型**：资金 / 幂等 / 数据一致性
- **业务规则说明**：一次明确的购买确认只能对应一张订单、一次扣款和一次库存扣减。用户再次购买同一摊位可以是新的业务行为，但网络重试或同一个请求的重复提交不能被当成第二次购买。
- **涉及文件**：`backend/src/main/java/com/artiv/controller/StallController.java`、`backend/src/main/java/com/artiv/service/impl/OrderServiceImpl.java`、`backend/sql/init.sql`、`frontend/src/views/stalls/StallDetail.vue`
- **涉及方法或接口**：`POST /api/stalls/{id}/purchase`，`OrderServiceImpl#createStallPurchase`
- **当前实现**：购买流程在事务内锁定摊位和雇主，检查库存及余额后扣款、减库存并创建订单。接口没有接收幂等键，`order_info` 也没有请求唯一键或“同一请求只创建一次”的约束。
- **问题说明**：事务和行锁只能保证每次请求内部一致，不能识别两个语义相同的请求。浏览器重试、代理重放、超时后再次提交或直接并发调用会被当成两次独立购买，只要余额和库存足够，就会重复扣款、重复减库存并创建两张订单。
- **触发条件**：同一购买动作被提交两次，且第二次执行时库存和余额仍满足条件。
- **影响范围**：雇主余额、画师冻结/应收资金、摊位库存、订单和消息会话。
- **证据**：`OrderServiceImpl.java:182-225` 只有业务锁和插入流程，没有读取客户端请求 ID；`order_info` 没有幂等键唯一索引。前端 `buying` 仅能减少普通双击，不能处理网络重试和直接 API 调用。
- **建议修复方式**：客户端生成一次性 `Idempotency-Key`，服务端建立购买请求记录或在订单表保存并唯一约束该键；同一用户、同一操作、同一键重复请求返回首次结果。对“超时但服务端已成功”的重试编写集成测试。
- **修复风险**：中。需要定义幂等键作用域、保留周期和失败重试语义。
- **是否需要人工确认**：不需要。

### CR-005 普通私信接口绕过会话发起权限

- **优先级**：P0
- **问题类型**：权限 / 骚扰风险 / 业务规则绕过
- **业务权限规则说明**：企划应征场景由雇主发起首次沟通，画师在会话建立后回复；订单建立后双方按订单参与者关系沟通。是否另行开放“无业务关系的社交私信”尚需产品确认，但即使开放，也必须遵守拉黑、接收偏好和频率限制。
- **涉及文件**：`backend/src/main/java/com/artiv/service/impl/MessageServiceImpl.java`、`backend/src/main/java/com/artiv/controller/MessageController.java`、`frontend/src/views/messages/MessageList.vue`、`docs/开发计划/沟通与消息设计.md`
- **涉及方法或接口**：`POST /api/messages/private`，`MessageServiceImpl#sendPrivateMessage`
- **当前实现**：带企划上下文时，服务会校验企划、应征关系和“雇主先发起”规则；但当 `projectId`、`orderId` 都为空时，只校验接收者为正常用户，随后即可创建普通私信和会话。
- **问题说明**：任意登录用户可直接构造 `{toId, content}` 向任意正常用户发消息，不需要已有会话、关注关系、订单、应征或邀请关系，也不检查拉黑关系。这样可以绕过文档中“普通应征由雇主发起，画师只能在会话已建立后回复”的产品权限。
- **触发条件**：调用私信接口时省略业务上下文字段并指定任意接收者 ID。
- **影响范围**：全部用户的站内消息与 WebSocket 通知；可能形成骚扰、垃圾消息和绕过拉黑的问题。
- **证据**：`MessageServiceImpl.java:66` 起的无上下文分支没有会话发起资格检查；`MessageList.vue:308/360` 的常规发送也使用仅含 `toId` 的请求。现有测试覆盖了“带 projectId 的画师不能先发”，但无上下文发送被允许。
- **建议修复方式**：明确普通私信的产品规则。若只允许回复已有会话，则发送前检查已存在双方会话且当前用户具有回复权；若允许社交私信，则至少增加拉黑、接收偏好、频率限制、举报和首条消息限额。后端不能依赖前端是否展示入口。
- **修复风险**：中。需要确认订单会话、企划会话和普通社交会话是否应共享一个接口。
- **是否需要人工确认**：需要产品确认是否保留“无业务关系私信”，但当前无约束行为必须处理。

## 3. 并发、数据安全与接口治理：应尽快处理

### CR-006 应征更新使用“先读后整行覆盖”，可复活已结束关系

- **优先级**：P1
- **问题类型**：并发 / 丢失更新
- **业务规则说明**：画师可以随时主动撤回应征，且不影响已经创建的订单；撤回后不能再基于该应征发送新订单。订单完成时可以自动结束仍为 active 的应征。这里审查的是并发写入覆盖最新状态，不是限制画师撤回应征。
- **涉及文件**：`ApplicationServiceImpl.java`、`OrderServiceImpl.java`
- **涉及方法或接口**：`updateQuote`、`withdraw`、旧 `select`；订单完成时的应征关闭逻辑
- **当前实现**：报价更新和撤回应征没有事务/行锁，先 `selectById` 得到完整实体，修改少数字段后调用 `updateById`。订单结算流程会锁定同一应征并设置 `active=0`、结束原因和状态。
- **问题说明**：若报价更新先读到 `active=1`，随后订单完成将其置为 0，报价线程再用旧实体整行更新，就可能把 `active`、`status` 或结束原因写回旧值，复活已完成关系或覆盖订单结算结果。
- **触发条件**：报价修改/撤回与订单完成或其他关闭应征操作并发。
- **影响范围**：应征状态、企划申请人列表、再次发单资格、消息关系。
- **证据**：`ApplicationServiceImpl.java:324-363` 为普通查询加实体整行 `updateById`；`OrderServiceImpl` 的结算路径会更新同一行。
- **建议修复方式**：使用事务和统一行锁；改为带前置状态条件的字段级更新，例如 `WHERE id=? AND active=1 AND version=?`；增加版本号或明确的状态机更新方法，受影响行数为 0 时返回冲突。
- **修复风险**：中。需整理所有写 `application` 的入口，避免只修一个方法。
- **是否需要人工确认**：不需要。

### CR-007 跨聚合“检查后执行”缺少统一锁，删除、拉黑可与建单并发穿透

- **优先级**：P1
- **问题类型**：并发 / 跨表一致性
- **业务规则说明**：企划或摊位存在活跃订单时不能删除；双方存在活跃订单时不能互相拉黑；已删除/不可售资源不能再创建新订单。问题在于并发请求可以同时通过这些既有规则，而不是建议改变规则本身。
- **涉及文件**：`ProjectServiceImpl.java`、`StallServiceImpl.java`、`UserBlockServiceImpl.java`、`OrderServiceImpl.java`
- **涉及方法或接口**：企划删除、摊位删除、用户拉黑、企划发单、摊位购买
- **当前实现**：删除企划/摊位和拉黑前会查询是否存在活跃订单；建单流程也检查对象状态。但这些检查没有共同锁定同一“准入行”或使用数据库约束。
- **问题说明**：两个事务可分别在对方写入前通过检查：例如删除摊位线程确认无活跃订单，购买线程确认摊位可售并创建订单，随后删除线程仍将摊位置为删除；拉黑和建单也可同时成功。最终会出现活跃订单引用已删除资源，或已经互相拉黑的双方新建了订单。
- **触发条件**：资源删除/拉黑与建单请求在较窄时间窗口并发。
- **影响范围**：订单、企划、摊位、用户关系和后续消息权限。
- **证据**：上述服务都采用独立 `COUNT/SELECT -> UPDATE/INSERT`，但没有共享锁顺序或单一条件更新作为并发闸门。
- **建议修复方式**：为每类竞争定义唯一锁顺序和准入记录。删除企划先锁企划，建企划单也先锁企划；删除摊位和购买都先锁摊位；拉黑和建单可锁规范化用户对关系记录。状态变更采用条件更新，并补充真实 MySQL 并发集成测试。
- **修复风险**：高。错误的锁顺序会引入死锁，需统一设计而不是分散加锁。
- **是否需要人工确认**：不需要。

### CR-011 多个核心列表存在 N+1 查询或把全表装入内存

- **优先级**：P1
- **问题类型**：数据库性能 / 可扩展性
- **涉及文件**：`ApplicationServiceImpl.java`、`MessageServiceImpl.java`、`StallServiceImpl.java`、`AdminProjectServiceImpl.java`、`AdminDisputeServiceImpl.java`、`ReportServiceImpl.java`、`PublicProfileServiceImpl.java`、`AdminStatsServiceImpl.java`
- **涉及方法或接口**：申请人列表、会话列表、我的摊位、后台企划/争议/举报、公开资料统计、运营和供需统计
- **当前实现**：多处先查一页主记录，再逐条查询用户、作品、订单或计数；消息会话先加载用户全部私信再在 Java 中分组分页；后台统计会加载日期范围数据，部分指标还加载全部用户、全部订单或全部认证画师到内存聚合。
- **问题说明**：数据量增长后，单个请求的 SQL 次数或内存占用与总数据量线性增长。分页接口表面有页码，但消息会话等实现仍会扫描用户全量历史数据。
- **触发条件**：活跃用户、消息、订单、作品或后台统计时间跨度增加。
- **影响范围**：企划详情、消息中心、个人管理页和后台仪表盘；高峰期会进一步耗尽数据库连接池。
- **证据**：应征列表逐条查用户/代表作/活跃订单；`MessageServiceImpl#listConversations` 全量加载后分组；我的摊位逐条 `COUNT` 未完成订单；后台统计存在 `allUsers/allOrders` 类全量集合。
- **建议修复方式**：按接口建立 SQL 级分页和批量聚合；用 `GROUP BY`、条件聚合、批量 `IN`、窗口查询或会话摘要表替代 Java 全量聚合。先对消息中心、企划申请人和后台统计做真实数据量基准测试。
- **修复风险**：中到高。聚合 SQL 改写必须校验统计口径。
- **是否需要人工确认**：需要根据预计数据规模确定先后，但问题成立。

### CR-012 客户端可传入过大的分页 size

- **优先级**：P1
- **问题类型**：资源滥用 / API 防护
- **涉及文件**：多个 Controller 和列表 Service，重点包括企划、摊位、应征、邀请、消息、个人列表和后台列表
- **涉及方法或接口**：含 `page`、`size` 参数的分页接口
- **当前实现**：多个接口把客户端传入的 `size` 直接交给 MyBatis-Plus 或内存分页，没有统一的最小值、最大值和默认值规范。
- **问题说明**：调用者可请求非常大的页面，放大 SQL、DTO 装配、N+1 查询和响应体开销。与 CR-011 叠加时，一个请求就可能触发大量数据库访问。
- **触发条件**：传入超大 `size` 或异常页码。
- **影响范围**：公共列表和登录后列表接口。
- **证据**：企划、摊位、应征和消息等控制器直接透传分页参数；未发现统一 `PageRequest` 校验器。
- **建议修复方式**：建立统一分页 DTO/解析器，例如 `page>=1`、普通接口 `1<=size<=50`、后台导出走独立异步通道；服务层再次约束，不能只靠前端。
- **修复风险**：低。
- **是否需要人工确认**：需要确认各页面最大合理页长。

### CR-013 WebSocket 令牌放在 URL 且跨域策略过宽

- **优先级**：P1
- **问题类型**：认证传输 / 跨域 / 会话安全
- **涉及文件**：`MessageWebSocketHandler.java`、`WebSocketConfig.java`、`CorsConfig.java`、前端 WebSocket 连接代码
- **涉及方法或接口**：WebSocket 握手、全局 CORS
- **当前实现**：前端把 JWT 放在 WebSocket 查询参数；服务端从 query token 解析身份，WebSocket 和 HTTP CORS 都使用通配 origin 模式，HTTP 同时允许 credentials。握手只验证令牌签名和有效期，没有回查用户当前封禁/删除状态。
- **问题说明**：查询参数更容易进入代理、网关、浏览器或服务日志；通配 Origin 增加跨站连接面；已建立连接或旧令牌也不能及时感知账号状态变化。
- **触发条件**：日志系统记录完整 URL、恶意站点诱导连接，或用户封禁后令牌仍有效。
- **影响范围**：消息推送、登录令牌和跨域 API。
- **证据**：`MessageWebSocketHandler` 从 query 读取 token；`WebSocketConfig`、`CorsConfig.java:16` 使用 `allowedOriginPatterns("*")`。
- **建议修复方式**：生产环境配置明确 Origin 白名单；WebSocket 使用短时一次性 ticket、受支持的鉴权子协议或安全 Cookie 方案，避免长期 JWT 出现在 URL；握手时回查用户状态，并支持封禁/退出后断开连接。
- **修复风险**：中。浏览器原生 WebSocket 不能任意设置 Authorization，需要前后端一起设计。
- **是否需要人工确认**：需要确认生产域名和网关日志策略。

### CR-014 上传只校验扩展名和大小，缺少内容、归属和生命周期治理

- **优先级**：P1
- **问题类型**：文件安全 / 数据治理
- **涉及文件**：`UploadController.java`、订单/评价/举报/争议 DTO 与服务、`application.yml`
- **涉及方法或接口**：上传接口及所有接收 `/uploads/` URL 的业务提交接口
- **当前实现**：上传端主要检查后缀和 5 MB 大小并生成 UUID 文件名；业务服务通常只检查字符串以 `/uploads/` 开头。没有验证 MIME、文件签名、图片解码结果、尺寸、EXIF，也没有把上传者、用途和业务绑定写入独立文件记录。
- **问题说明**：后缀不能证明文件内容；用户还可把别人已知的上传 URL 绑定到自己的订单、评价或证据。孤立上传也没有清理、引用计数和审计能力。
- **触发条件**：伪造扩展名、提交他人文件 URL、上传后放弃业务流程，或上传超大像素压缩炸弹。
- **影响范围**：存储空间、图片处理、证据可信度和用户隐私。
- **证据**：上传控制器仅做后缀/大小检查；多个服务只做 `/uploads/` 前缀判断。
- **建议修复方式**：引入上传对象表，记录上传者、哈希、真实类型、尺寸、用途、状态和绑定业务；服务端解码并重编码图片，去除元数据；绑定时校验所有权和用途；建立未绑定文件过期清理。
- **修复风险**：中到高。需兼容历史 URL。
- **是否需要人工确认**：需要确认允许的文件类型和历史文件迁移策略。

### CR-015 业务失败和系统异常普遍返回 HTTP 200

- **优先级**：P1
- **问题类型**：接口语义 / 可观测性 / 客户端健壮性
- **涉及文件**：`GlobalExceptionHandler.java`、`Result.java`、前端 Axios 封装
- **涉及方法或接口**：全局异常处理
- **当前实现**：除少数 forbidden/no_permission 返回 403 外，未登录、参数校验、资源不存在、业务冲突和未处理异常通常都用 HTTP 200 包装失败响应。
- **问题说明**：网关、APM、缓存、浏览器和通用客户端无法通过状态码区分成功、客户端错误与服务端故障；监控成功率失真，重试策略和安全审计也更困难。
- **触发条件**：任何业务或系统异常。
- **影响范围**：全部 API、前端错误处理、日志告警和未来第三方客户端。
- **证据**：全局异常处理器多数分支返回普通 `Result.fail(...)` 而未设置对应 HTTP 状态。
- **建议修复方式**：制定稳定的错误码与 HTTP 映射：401 未认证、403 无权限、404 不存在、409 状态冲突/重复、422 业务校验、500 未处理异常。前端过渡期同时兼容旧 envelope 和新状态码。
- **修复风险**：中到高。会影响现有前端拦截器和测试，应分阶段迁移。
- **是否需要人工确认**：需要确认兼容窗口。

### CR-017 管理员封禁与普通订单流程存在相反锁顺序

- **优先级**：P1
- **问题类型**：并发 / 死锁
- **涉及文件**：`AdminUserServiceImpl.java`、`OrderServiceImpl.java`
- **涉及方法或接口**：管理员修改用户状态、订单接单/结算/取消等涉及用户余额的流程
- **当前实现**：管理员封禁路径先锁用户，再处理或检查关联订单；部分订单路径先锁订单，再锁相关用户。
- **问题说明**：两个事务分别持有用户锁和订单锁后再等待对方资源，可形成数据库死锁。数据库通常会回滚其中一个事务，但当前接口未提供明确重试和幂等语义。
- **触发条件**：管理员封禁某用户与该用户的订单状态迁移同时发生。
- **影响范围**：封禁操作、订单结算/取消和资金状态；低频但影响关键治理流程。
- **证据**：`AdminUserServiceImpl#changeStatus` 与 `OrderServiceImpl` 的加锁入口顺序不一致。
- **建议修复方式**：制定全项目锁顺序，例如资源/订单在前、用户按 ID 升序在后；封禁流程按相同顺序重构。对可安全重试的死锁异常增加有限次数重试，并用双线程 MySQL 集成测试验证。
- **修复风险**：高。需与 CR-007 一并设计锁协议。
- **是否需要人工确认**：不需要。

### CR-018 Controller 中存在 Mapper 和业务规则直调

- **优先级**：P2
- **问题类型**：分层 / 可测试性
- **涉及文件**：`MessageController.java`、`UserController.java`

- **当前实现**：部分控制器直接查询或更新 Mapper，并在 Controller 中组装权限和业务判断。

- **触发条件**：修改消息已读、用户头像或复用相关能力。

- **是否需要人工确认**：不需要。

### CR-019 响应模型混用 Entity、DTO 和 Map

- **优先级**：P2
- **问题类型**：API 契约 / 可维护性
- **涉及文件**：多个 Controller、Entity、DTO 和后台 Service
- **涉及方法或接口**：用户、应征、订单、后台统计等响应
- **当前实现**：新接口多使用 DTO，但旧接口仍直接返回 Entity；后台和若干聚合接口大量使用 `Map<String,Object>`。
- **问题说明**：字段暴露依赖实体注解和字符串键，编译器不能检查契约，容易再次出现 CR-001 类敏感字段泄露，也使接口文档和前端类型难以同步。
- **触发条件**：实体新增字段、Map 键重命名或前端扩展接口。
- **影响范围**：全局接口演进。
- **证据**：`Result<User>`、`Result<Application>` 与多处 `Result<Map<String,Object>>` 并存。
- **建议修复方式**：为公开、本人、管理员三类视图建立明确 DTO；统计接口使用具名响应类型；实体只在持久化层流转。
- **修复风险**：中。
- **是否需要人工确认**：需要确认旧客户端兼容期。

### CR-020 GET 订单详情会写文件和更新数据库

- **优先级**：P2
- **问题类型**：副作用 / 文件与事务一致性
- **涉及文件**：`OrderServiceImpl.java`
- **涉及方法或接口**：订单详情、`repairLegacyPreview`
- **当前实现**：读取订单详情时会尝试为历史阶段修复预览图，创建文件并更新 `order_stage`；失败日志可能包含原图路径。
- **问题说明**：幂等读取产生持久副作用，缓存、重复刷新和爬虫都会触发修复；文件系统写入不受数据库事务回滚控制，可能产生孤儿文件；原始路径进入日志也增加信息泄露面。
- **触发条件**：访问含旧格式阶段数据的订单详情。
- **影响范围**：订单详情延迟、存储一致性、日志敏感信息。
- **证据**：`OrderServiceImpl.java:164` 在详情装配中调用 `repairLegacyPreview`，实现位于约 690 行。
- **建议修复方式**：改为一次性迁移任务或受控后台修复；详情 GET 只读。文件先写临时对象，数据库提交后再切换引用，并清理失败对象。日志只记录业务 ID。
- **修复风险**：中。
- **是否需要人工确认**：需要确认历史数据仍有多少依赖在线修复。

### CR-021 核心状态和业务规则在多层重复定义

- **优先级**：P2
- **问题类型**：重复逻辑 / 漂移风险
- **涉及文件**：订单、企划、应征、摊位、用户相关后端 Service；前端 `utils`、页面；业务文档
- **涉及方法或接口**：状态判断、可执行操作、分类题材选项
- **当前实现**：大量整数状态和状态集合由各服务自行声明，前端再维护一套映射；CR-009 已出现实际漂移。
- **问题说明**：新增状态或调整规则时必须同步多处，漏改会造成统计、按钮、权限和数据库查询口径不一致。
- **触发条件**：扩展售后、封禁、企划或应征状态。
- **影响范围**：所有核心业务。
- **证据**：状态 5 在 `PublicProfileServiceImpl` 与 `UserBlockServiceImpl` 中语义相反；分类/题材也同时存在于多个表单和文档。
- **建议修复方式**：后端建立领域枚举和单一状态机语义；前端使用集中常量；必要时由后端提供只读元数据。不要直接让前端导入后端代码，但应有契约测试。
- **修复风险**：中。
- **是否需要人工确认**：不需要。

### CR-023 前端错误提示可能重复，登录页导航会静默退出

- **优先级**：P2
- **问题类型**：前端体验 / 状态管理
- **涉及文件**：`frontend/src/utils/request.js`、多个页面 catch 分支、`frontend/src/router/index.js`
- **涉及方法或接口**：Axios 响应拦截、购买/应征/消息等提交、路由守卫
- **当前实现**：请求拦截器统一弹出错误提示，页面 catch 中又常再次 `ElMessage.error`；已登录用户访问 Login/Register 时，路由守卫直接执行 logout。
- **问题说明**：一次错误可能出现两个提示；仅访问登录地址就清除登录态不符合通常预期，也不利于排查用户“突然退出”。

- **影响范围**：全局交互体验和登录稳定性。

- **建议修复方式**：定义错误展示归属，默认由页面或拦截器其中一方负责，并允许 `silent`；登录页对已登录用户重定向，不主动退出，退出应由显式操作触发。
- **修复风险**：低。
- **是否需要人工确认**：需要确认登录页原产品意图。

### CR-024 部分 Vue 页面承担过多职责

- **优先级**：P2
- **问题类型**：前端可维护性
- **涉及文件**：`ProjectNew.vue`、`StallDetail.vue`、`MessageList.vue`、`Home.vue`、`ArtistProfile.vue`、`ProjectDetail.vue`
- **涉及方法或接口**：表单、列表、消息、WebSocket、上传、订单卡片等页面逻辑

### CR-027 数据库缺少外键、CHECK 约束，部分高频查询索引不匹配

## 5. 业务规则类问题：后置处理

本节刻意放在安全、权限、资金安全、并发一致性和工程问题之后。这里的问题依赖 Artiv 的产品规则，修复前必须先确认“系统本来应该怎样运行”，不能仅凭常见产品习惯修改代码。

### CR-008 接受邀请与正常应征并发时会暴露唯一键异常

- **优先级**：P1
- **问题类型**：业务流程 / 并发 / 异常治理
- **业务规则说明**：同一画师对同一企划只能存在一条当前应征关系。接受邀请和画师主动应征只是建立该关系的两个入口；它们同时发生时，不应创建两条应征，也不应把可恢复的重复操作显示成系统故障。
- **涉及文件**：`InvitationServiceImpl.java`、`ApplicationServiceImpl.java`、`backend/sql/init.sql`
- **涉及方法或接口**：接受邀请、创建应征
- **当前实现**：接受邀请会读取待处理邀请，再调用创建/恢复应征逻辑，最后条件更新邀请。`application` 有 `(project_id, painter_id)` 唯一约束，但服务没有把重复键转换为幂等成功或业务冲突。
- **问题说明**：画师同时点击接受邀请和正常应征，或重复并发接受时，两个事务可能都认为应征尚不存在，随后一个插入成功、另一个触发 `DuplicateKeyException`，最终表现为通用系统错误。数据库能够阻止重复数据，缺陷主要在并发结果没有按业务语义处理。
- **触发条件**：同一企划、同一画师的两个应征创建入口并发。
- **影响范围**：邀请状态、应征建立体验、错误监控。
- **证据**：数据库唯一索引能防止重复数据，但服务未捕获并重新查询现有结果；创建流程没有统一的行锁/幂等语义。
- **建议修复方式**：将“确保当前应征存在”收口为一个事务方法；对唯一键冲突重新读取并按当前状态返回确定结果，或使用受控的 upsert/条件恢复。邀请状态更新继续使用条件更新。
- **修复风险**：中。
- **是否需要人工确认**：需要确认重复接受邀请应返回“成功并返回已有应征”还是 409；不能返回通用 500。

### CR-009 订单状态 5 在公开资料统计中被误判为终态

- **优先级**：P1
- **问题类型**：业务规则漂移 / 统计错误
- **业务规则说明**：当前订单状态含义为：0 待接单、1 履约中、2 待评价、3 已完成、4 已取消、5 争议/售后中。状态 5 仍可能继续处理并改变最终结果，因此按现有订单流程属于非终态；只有产品明确把“进入争议”定义为统计结案时，才应计入终态。
- **涉及文件**：`PublicProfileServiceImpl.java`、`UserBlockServiceImpl.java`、`OrderServiceImpl.java`、前端订单状态工具
- **涉及方法或接口**：公开资料完成率计算
- **当前实现**：`PublicProfileServiceImpl` 定义 `TERMINAL_ORDER_STATUSES = [3,4,5]`，完成率分母把状态 5 计算为已结束；其他订单逻辑则把状态 5 视为争议/售后中的非终态。
- **问题说明**：按当前状态定义，争议尚未处理时就被计入已结束订单，使完成率提前变化；若最终处理结果改变订单状态，统计又会跳变。状态语义在不同模块不一致。
- **触发条件**：用户存在状态 5 的订单并查看公开资料统计。
- **影响范围**：画师/雇主公开信誉指标和用户决策。
- **证据**：`PublicProfileServiceImpl.java:42,185-191`；`UserBlockServiceImpl.java:31` 明确把 `[0,1,2,5]` 视为非终态。
- **建议修复方式**：先确认完成率统计口径，再建立后端唯一订单状态枚举及 `isTerminal/isActive/isSettled` 语义方法；统计查询直接复用。为状态 5 增加单元和数据库统计测试。
- **修复风险**：低。
- **是否需要人工确认**：需要确认“完成率”的分母是否只包含已完成/已取消，还是也包含争议中的订单。

### CR-010 被封禁用户的公开资料被隐藏，与既定治理规则冲突

- **优先级**：P1
- **问题类型**：业务规则漂移 / 可见性
- **业务规则说明**：现有文档将封禁定义为“限制新增业务写操作”，而不是删除账号。被封禁用户仍可登录、浏览、查看公开个人主页和历史内容，但不能发布企划、应征、创建摊位、购买或发送企划订单。
- **涉及文件**：`PublicProfileServiceImpl.java`、`docs/项目交接说明.md`、后台管理设计文档
- **涉及方法或接口**：`requireActiveUser`、公开资料及公开作品/摊位/企划接口
- **当前实现**：公开资料服务要求用户状态正常，否则按不存在/不可访问处理。
- **问题说明**：当前公开资料服务把“禁止业务写操作”扩大成“隐藏公开身份”，与现有治理规则不一致。这不是外部用户读取越权，而是产品可见性口径冲突，因此放在业务规则章节。
- **触发条件**：访问状态为封禁的用户公开主页或其公开列表。
- **影响范围**：历史订单评价的身份追溯、举报/治理透明度、用户公开资料。
- **证据**：`PublicProfileServiceImpl.java:128-134` 对非正常状态直接拒绝；交接文档和后台设计明确保留浏览及公开资料权限。
- **建议修复方式**：若维持现有规则，公开读取只检查用户存在且未逻辑删除，写操作继续统一检查封禁状态。若产品决定封禁后隐藏主页，则应同步修改治理文档和历史内容展示策略。
- **修复风险**：低。
- **是否需要人工确认**：需要最终确认封禁后的公开主页可见性；在确认前不要直接修改。

### CR-016 领域输入和状态值缺少服务端白名单校验

- **优先级**：P1
- **问题类型**：业务输入 / 数据完整性
- **业务规则说明**：前端当前把摊位状态和作品可见性限制为 0/1，并使用文档中的分类、题材集合。负库存和未知状态没有已定义业务含义。分类/题材是否永久固定，还是未来由后台动态维护，尚需产品确认。
- **涉及文件**：`StallRequest.java`、`WorkRequest.java`、`ProjectRequest.java`、`ApplicationController.java`、对应 Service、`backend/sql/init.sql`
- **涉及方法或接口**：摊位创建/上下架、作品创建/编辑、企划创建/编辑、应征创建/报价
- **当前实现**：摊位状态修改接受任意整数；创建库存缺少非负约束，价格可为空；作品可见性没有 0/1 白名单；企划、作品和摊位的分类/题材主要由前端选项限制，服务端未统一校验；部分接口直接接收实体或字段校验不完整。
- **问题说明**：直接调用 API 可写入前端不会产生的非法状态和领域值，导致公共查询遗漏、管理页无法处理、状态机分支失效或脏数据长期存在。
- **触发条件**：绕过前端提交负库存、任意状态/可见性、非法分类题材或超长文本。
- **影响范围**：摊位、作品、企划、应征及相关公共列表。
- **证据**：`StallServiceImpl#changeStatus` 未限定 0/1；请求 DTO 注解不完整；`init.sql` 没有 CHECK 约束兜底。
- **建议修复方式**：对确定无争议的规则先加服务端校验，例如库存非负、已知状态范围、长度限制；分类/题材白名单在确认是固定配置还是动态元数据后再实现。数据库对稳定整数状态增加 CHECK 或等价约束。
- **修复风险**：中。需先扫描存量非法值并决定兼容方式。
- **是否需要人工确认**：需要确认分类/题材是否允许后台动态扩展；库存非负和已定义状态范围无需确认。

| 用户正常/封禁/删除与可执行操作 | `AuthInterceptor`、多个 Service、公开资料服务 | 路由/页面、后台治理和交接文档 | 公开资料服务把封禁用户隐藏，与文档冲突 | 统一 `AccountRestrictionPolicy`，按“读取/写入/管理”分类 |
| 分类和题材选项 | 企划/作品/摊位请求与服务 | 多个表单及交接文档中的 10 分类、35 题材 | 主要靠前端，直接 API 可绕过；是否允许动态扩展不明确 | 后端元数据或统一领域配置，前端读取/同步 |
| 会话发起和回复资格 | `MessageServiceImpl` 的上下文分支 | `MessageList.vue`、沟通与消息设计 | 无上下文私信绕过“雇主先发”规则 | 独立 `ConversationPolicy`，所有发送入口统一调用 |
| 分页上限 | 各 Controller 自行接收 page/size | 各页面自行传值 | 没有统一上限，且与 N+1/全表聚合相互放大 | 全局分页请求类型和服务层兜底 |

建议优先收口“状态语义”和“准入策略”，而不是只抽取显示文本。真正需要单一来源的是 `是否允许执行某操作`，不仅是数字到中文的映射。

## 8. 数据库访问与数据一致性审查

### 8.1 表结构评价

24 张表基本覆盖了当前业务，关系表的唯一约束整体优于常见毕业设计项目：关注、收藏、评价、申诉、争议、举报和应征等均有关键唯一约束。订单采用快照字段、业务资源采用软删除，也与历史交易可追溯目标一致。

主要不足是数据库承担的最终防线较弱：没有外键和 CHECK，订单购买没有幂等唯一键，部分状态只能靠应用代码约束。对于软删除和历史快照，确实不能简单使用级联删除，但“完全无约束”也不是唯一选择。

### 8.2 重点查询风险

| 场景 | 当前访问方式 | 风险 | 优先建议 |
| --- | --- | --- | --- |
| 企划申请人列表 | 一页应征后逐条查画师、代表作、活跃订单 | 约 3N 查询 | 批量查询用户/作品/订单并按 ID 分组 |
| 消息会话列表 | 读取用户全部私信，在 Java 分组和分页，再逐会话查用户 | 历史消息越多越慢，分页失真 | SQL 查询每个 conversation 最新消息和未读数，或维护摘要表 |
| 我的摊位 | 每个摊位单独 COUNT 未完成订单 | N+1 | 一次按 stall_id 分组统计 |
| 后台企划/争议/举报 | 主列表后逐条查用户、订单或计数 | 后台页 SQL 数量随页长增长 | 批量 IN 与聚合子查询 |
| 公开资料统计 | 加载用户相关订单后 Java 计算 | 大户数据量增长，且状态口径易漂移 | 数据库条件聚合并复用统一状态语义 |
| 后台运营/供需统计 | 加载日期范围乃至全体用户/订单/画师/作品 | 内存和连接占用不可控 | 按时间桶和维度直接 GROUP BY；必要时统计快照 |

### 8.3 索引建议

索引必须以生产形态数据和 `EXPLAIN ANALYZE` 为依据。当前可以优先验证：

1. 作品公共列表：围绕 `deleted + visibility + created_at` 的组合索引。
2. 摊位公共列表：围绕 `deleted + status + stock + 排序列` 的组合索引。
3. 消息：发送方/接收方、类型、删除标记和时间的索引；重新评估 `(conversation_key, project_id, created_at)` 是否符合不限定 `project_id` 的会话查询。
4. 订单：现有雇主、画师、企划、状态索引较完整，先保留并基于慢查询调整，不建议继续无差别加索引。
5. 企划关键词搜索使用前导模糊匹配时普通 B-Tree 帮助有限；数据规模大后再考虑全文索引或搜索服务。

### 8.4 事务和锁

订单服务内部锁设计整体是项目的强项，但跨服务没有形成书面锁协议。建议在代码和文档中明确：

- 同一事务涉及多个用户时，始终按用户 ID 升序锁定。
- 涉及企划/摊位和订单时，先锁业务资源准入行，再锁订单，再锁用户。
- 应征的所有状态写都通过同一锁定/条件更新入口。
- 唯一键冲突不是 500，而应转换为幂等结果或 409 业务冲突。
- 用真实 MySQL 测试，而不是只用 Mockito 验证方法调用顺序。

## 9. 前端代码质量审查

### 9.1 总体评价

前端页面和流程完成度较高，API 模块、路由、状态管理和通用工具已有基本分层。主要问题集中在页面职责过重、错误处理重复、自动化质量门禁缺失，以及安全规则有时只通过“是否展示按钮”表达。

### 9.2 确认问题

- 应征撤回入口允许在已有订单期间使用，符合“应征只控制后续发单资格、已有订单独立履约”的产品规则；前端无需因为活跃订单而禁用该入口。
- 消息发送常使用只含 `toId` 的通用私信请求，后端无上下文分支成为权限绕过入口。

- JWT 存在 `localStorage`。当前未发现 `v-html` 等直接注入点，但一旦未来发生 XSS，令牌可被读取；应配合 CSP、依赖治理和更安全的会话方案评估。
- WebSocket URL 携带 JWT。
- 多个页面超过 500 行且包含多类副作用。
- 没有前端自动化测试，ESLint 9 配置缺失。
- 构建包和图片资源偏大。

### 9.3 值得保留的实现

- 当前路由级懒加载方向正确，包体优化应在此基础上按构建分析结果进行。

## 10. 后端代码质量审查

### 10.1 总体评价

后端已经形成 Controller、Service、Mapper 的主体结构，核心订单服务虽然较大，但关键资金和状态操作大多有事务意识。主要不足是旧接口没有彻底收口、状态规则散落、Controller 偶尔越层、部分更新未使用条件写，并且数据库级集成测试不足。

### 10.2 安全与权限

- 管理员拦截器回查数据库是正确做法，应保留。
- 普通 JWT 认证只根据令牌中的用户 ID 建立上下文，没有统一回查账号当前状态；目前各写服务再做限制，容易漏入口。可考虑集中账户状态策略，但要保留“封禁用户仍可登录和浏览”的业务区分。
- 旧用户实体接口和公开上传目录是当前最严重的两条越权链。
- 消息权限应建立独立策略，不能由 `projectId` 是否存在来决定是否校验。
- CORS/WebSocket Origin 需要环境化白名单。

### 10.3 业务一致性

- 订单状态迁移、结算、退款和评价的事务处理总体可靠。
- 应征模块的非事务整行更新是当前状态一致性短板。
- 项目、摊位、拉黑与订单属于跨聚合竞争，需要统一锁协议。
- 状态 5 的统计漂移证明“魔法数字 + 各服务自行解释”已经产生实际缺陷。

### 10.4 可维护性

- `OrderServiceImpl`、`MessageServiceImpl`、`ProjectServiceImpl` 等服务体积较大，但不建议只按行数机械拆分；应先按状态机、查询装配、文件处理、通知等真实职责拆。
- Entity、DTO 和 Map 混用应逐步收敛，优先从外部可访问和含敏感信息的接口开始。
- Controller 直连 Mapper 应迁移到服务层。
- 对已废弃接口应有明确的 deprecated 标记、调用监控和删除时间表。

### 10.5 测试

现有 170 个后端测试能提供较好的服务层回归基础，但仍缺少以下关键类型：

1. 真实 MySQL 唯一键与行锁测试。
2. 双线程购买幂等测试。
3. 应征报价与订单结算并发测试。
4. 企划/摊位删除与建单并发测试。
5. 管理员封禁与订单迁移死锁测试。
6. MockMvc/API 测试，验证 HTTP 状态、敏感字段和静态文件授权。

## 12. 当前应保留、不建议误改的实现

以下行为已与代码和文档交叉确认，不应在修复过程中被当成缺陷顺手改掉：

1. **自然过期企划与治理下架企划的规则不同**：已有应征在自然过期后仍可沟通和发单；治理隐藏也不等于自动破坏已有合法关系。应保留两种原因的区分。
2. **应征与订单采用独立生命周期**：应征用于取得和维持后续企划发单资格；订单创建后按订单参与者和订单状态独立履约。画师可以主动撤回应征，撤回只从应征列表移除关系并阻止以后基于该应征继续发单，不取消、不终止、也不改变已经创建的订单。订单完成时自动结束仍处于 active 的应征也是合理清理。后续修复不得增加“存在活跃订单就禁止撤回应征”的限制。
3. **摊位受限编辑只允许追加题材**：前端文案和进度文档均说明“已有题材不可删除，只能追加”，当前集合并集行为是有意设计。
4. **重复邀请保留历史记录**：邀请不是必须全局唯一的当前关系；多次邀请历史可用于追溯，不应仅因为存在多条记录就删除。
5. **订单快照和软删除**：历史订单不应依赖企划、摊位或用户后续编辑；快照字段和软删除方向合理。增加外键时不要使用会破坏历史的级联删除。
6. **管理员鉴权回查数据库**：不能为了减少一次查询改成只相信 JWT 角色，否则会使撤权和封禁延迟到令牌过期。
7. **事务提交后再推送 WebSocket**：这是正确的事务边界，应继续保留。
8. **评价、申诉、争议的唯一约束和行锁**：当前闭环基本合理，整改时应以补充测试和统一状态语义为主，不要无依据重写。
9. **消息页面防止旧请求覆盖新会话的请求令牌机制**：这是对异步竞态的有效防护。
10. **当前技术栈和总体分层**：没有证据表明必须更换 Vue、Spring Boot 或 MyBatis。现阶段收益最高的是修复权限、一致性和查询实现，而不是框架迁移。
