## 1. 结论摘要

Artiv 的核心业务闭环已经比较完整。订单托管、接单、阶段交付、验收、退款/仲裁等高风险主流程普遍使用事务和数据库行锁；管理员接口也会重新查询账号状态与角色，而不是只相信 JWT 中的旧角色。现有测试和生产构建均能通过，说明当前版本具备较好的继续收尾基础。

但正式部署前仍有 4 项高优先级问题需要处理：

1. 登录用户可以通过旧用户详情接口读取他人的余额、封禁原因等非公开字段；
2. 订单原图与普通图片位于同一公开静态目录，接口层隐藏原图地址不能形成真实下载权限；
3. 应征选择、改价、取消等更新缺少事务锁或条件更新，并发时可能覆盖“订单完成后结束应征”等新状态；
4. 默认配置包含固定 JWT 密钥与数据库账号密码，若直接部署，可能导致令牌伪造或数据库凭据泄露。

## 2. 详细问题

## CR-01：旧用户详情接口返回完整用户实体

- **级别：P1 高**
- **类型：越权读取 / 隐私泄露**

### 证据

- `backend/src/main/java/com/artiv/controller/UserController.java:170-177` 的 `GET /api/v1/users/{id}` 直接返回 `Result<User>`，只手动清空密码；
- `backend/src/main/java/com/artiv/entity/User.java:32-73` 中除密码和逻辑删除字段外，余额、账号角色、认证状态、封禁原因、封禁管理员、封禁时间、常用站和创建时间等字段都会参与 JSON 序列化；
- `backend/src/main/java/com/artiv/security/AuthInterceptor.java:66-104` 没有把该旧接口列为公开接口，因此它要求登录，但没有“只能查看自己”的限制。任意正常登录账号都可以遍历用户 ID；
- 项目已经存在更安全的 `/users/{id}/public-profile` DTO 入口，因此旧接口没有继续暴露完整实体的必要。

### 影响

任意登录用户可以读取其他账号的余额和内部治理信息。即使密码已隐藏，该接口仍违反最小披露原则，也会让后续给 `User` 增加字段时自动扩大泄露面。

### 建议

1. 删除或废弃 `GET /api/v1/users/{id}`；公开主页统一使用 `PublicProfileResponse`；
2. “查看自己的账号资料”单独使用 `/auth/me` 或专用私有 DTO；
3. 控制器禁止直接返回 `User` 持久化实体；
4. 增加接口测试，明确断言公开响应中不存在 `balance`、`banReason`、`bannedBy`、`bannedAt`、`bannedUntil` 等字段。

## CR-02：订单原图存放在匿名可访问的公共上传目录

- **级别：P1 高**
- **类型：文件访问控制失效**

### 证据

- `backend/src/main/java/com/artiv/config/WebMvcConfig.java:37-41` 将整个上传目录映射为 `/uploads/**` 静态资源；该路径不在 `/api/**` 拦截范围内，因此可匿名访问；
- `backend/src/main/java/com/artiv/service/impl/OrderServiceImpl.java:306-334` 将画师交付原图 URL 直接保存到 `OrderStage.originals`，同时生成水印预览；
- `backend/src/main/java/com/artiv/service/impl/OrderServiceImpl.java:618-622` 只是在订单未完成时从 API 响应副本中清空 `originals`；
- `backend/src/main/java/com/artiv/service/OrderPreviewService.java:35-70` 显示原图和水印预览图使用同一个 `uploadRoot`；
- `backend/src/main/java/com/artiv/service/OrderPreviewService.java:99-108` 只验证文件是否位于上传根目录，没有验证文件归属、上传者、订单或访问者身份。

### 影响

接口不返回原图 URL 只能降低偶然暴露，不能形成授权边界。只要原图地址从浏览器记录、日志、数据库、消息或其他途径泄露，未付款用户和匿名用户都可以绕过订单状态直接下载原图。UUID 文件名降低了猜测概率，但不是权限控制。

此外，业务目前只保存路径，没有保存上传者和用途；任意已知 `/uploads/` 地址也可能被复用到其他业务记录中。

### 建议

1. 将订单原图移出公共静态目录，例如独立保存到 `private/order-originals`；
2. 提供受控下载接口，校验订单参与者和订单状态：画师始终可取回，企划方仅在规则允许时下载，管理员按治理权限访问；
3. 为上传文件建立最小元数据：上传者、业务用途、所属业务 ID、创建时间和可见性；
4. 水印预览可以保留公开 URL，也可以同样通过受控接口读取；
5. 对历史订单原图执行引用迁移，不能只修改新上传逻辑。

## CR-03：应征状态更新存在并发覆盖风险

- **级别：P1 高**
- **类型：状态机一致性 / 并发**

### 证据

- `backend/src/main/java/com/artiv/service/impl/ApplicationServiceImpl.java:302-365` 的选择应征、修改报价和取消应征均先 `selectById`，随后修改完整实体并 `updateById`，方法没有事务锁；
- `backend/src/main/java/com/artiv/service/impl/ApplicationServiceImpl.java:256-288` 的重新激活逻辑同样采用“先查询、后覆盖实体”；
- `backend/src/main/java/com/artiv/mapper/ApplicationMapper.java:12-13` 已提供 `selectByIdForUpdate`，但上述路径没有使用；
- 订单完成路径会锁定并结束对应应征关系。如果改价请求先读到 `active=1`，订单完成随后写入 `active=0`，改价请求最后执行完整实体更新，就可能把已结束的应征重新写回有效状态。

### 影响

并发请求可能产生以下不一致：

- 已完成订单对应的应征重新出现在“我的应征”；
- 企划方选择与画师取消同时发生后，出现状态与 `active` 不匹配；
- 重复接受/重新应征请求在唯一约束附近产生数据库异常或覆盖更新；
- 企划方与画师看到的有效应征关系不同步。

### 建议

1. 状态变化方法统一加入事务，并使用 `selectByIdForUpdate`；
2. 更推荐对简单变化使用窄字段条件更新，例如 `UPDATE ... SET quote=? WHERE id=? AND active=1 AND quote_source<>1`，检查受影响行数；
3. 为 `Application` 增加乐观锁版本字段，防止未来新增入口再次覆盖新状态；
4. 增加并发集成测试：改价 vs 完成订单、取消 vs 选中、重复应征 vs 邀请接受。

## CR-04：默认配置包含可直接使用的固定密钥和数据库凭据

- **级别：P1 高**
- **类型：部署安全**

### 证据

- `backend/src/main/resources/application.yml:8-10` 固定使用 `root / 123456`；
- `backend/src/main/resources/application.yml:29-33` 提交了固定 JWT 签名密钥；
- 配置中的注释要求生产覆盖，但程序不会在生产启动时验证是否仍在使用占位值。

### 影响

如果演示、答辩或正式环境直接沿用仓库配置，知道仓库内容的人可以伪造任意用户甚至管理员 JWT。数据库弱口令也会扩大部署机器或数据库端口暴露后的风险。

### 建议

1. 将敏感配置改为环境变量或未纳入 Git 的本地配置；
2. 单独建立 `application-dev.yml`，生产配置不得提供可工作的默认密钥；
3. 在非开发环境启动时检测占位密钥、弱口令和空配置，命中后直接拒绝启动；
4. 正式部署使用最小权限数据库账号，不使用 `root`；
5. 现有固定 JWT 密钥应视为已经公开，部署前必须轮换。

## CR-05：WebSocket 在 URL 中携带长期 JWT，且握手只校验令牌签名

- **级别：P2 中**
- **类型：实时通信鉴权**

### 证据

- `frontend/src/utils/ws.js:10-20` 把登录 JWT 拼接为 `?token=...`；
- `backend/src/main/java/com/artiv/websocket/MessageWebSocketHandler.java:67-77` 只验证 JWT 并解析用户 ID，没有重新查询账号是否已封禁或删除；
- `backend/src/main/java/com/artiv/config/WebSocketConfig.java:22-25` 允许任意 Origin。

### 影响

URL 查询参数可能进入反向代理访问日志、诊断工具或错误报告。已封禁/删除账号的未过期令牌仍可能建立 WebSocket，已建立的连接也不会随治理操作主动关闭。

### 建议

使用短时、单次 WebSocket ticket 或受控握手方案；握手时查询账号状态；限制生产 Origin；封禁用户后关闭其现有会话。若暂时保留 query token，应确保代理和应用日志不会记录查询串。

## CR-06：上传接口只检查扩展名，没有验证实际文件内容

- **级别：P2 中**
- **类型：文件上传安全**

### 证据

- `backend/src/main/java/com/artiv/controller/UploadController.java:29-63` 只根据原始文件名扩展名和大小判断类型，随后原样写入公共静态目录；
- 未检查 MIME、文件魔数、图像能否解码、像素尺寸和压缩炸弹风险。

### 影响

用户可以把任意内容改名为 `.png` 等扩展后上传。浏览器是否执行取决于响应类型和内容嗅探策略，但该实现仍使公共上传域成为非预期文件托管入口，也可能让后续图片处理承受畸形文件。

### 建议

对普通图片执行解码、尺寸限制并重新编码；同时检查扩展名、声明 MIME 和真实内容。订单原图若需要保留原格式，也应进入私有目录并做独立白名单和解码验证。

## CR-07：分页参数无统一上限，会话列表先全量读取再内存分页

- **级别：P2 中**
- **类型：性能 / 拒绝服务风险**

### 证据

- `backend/src/main/java/com/artiv/config/MybatisPlusConfig.java:15-19` 启用了分页插件，但没有设置 `maxLimit`；
- 多个列表接口直接把用户提供的 `page`、`size` 传给 `Page`，没有统一限制；
- `backend/src/main/java/com/artiv/service/impl/MessageServiceImpl.java:130-170` 会先读取该用户全部私信，Java 分组后才分页；
- 同一代码在首次遇到每个会话时调用一次 `userMapper.selectById`，形成 N+1 查询。

### 影响

消息数据增长后，每次打开消息中心都需要扫描全部历史私信并创建大量 Java 对象；恶意或异常的大 `size` 也会增加数据库和响应内存压力。

### 建议

1. 统一限制 `page >= 1`、`1 <= size <= 100`，并设置 MyBatis-Plus `maxLimit`；
2. 用 SQL 查询每个会话的最新消息和未读数，再对会话结果分页；
3. 对用户资料批量查询，消除 N+1；
4. 为用户、作品、企划、橱窗、应征等分页接口复用统一的分页参数对象。

## CR-08：业务错误大量使用 HTTP 200 返回

- **级别：P2 中**
- **类型：接口语义 / 可观测性**

### 证据

- `backend/src/main/java/com/artiv/common/GlobalExceptionHandler.java:18-23` 除无权限外，其他 `BusinessException` 均返回 HTTP 200；
- `backend/src/main/java/com/artiv/common/GlobalExceptionHandler.java:29-40` 参数校验失败和未捕获异常也直接返回 `Result`，默认 HTTP 状态仍为 200。

### 影响

前端当前根据响应体 `code` 仍能工作，但网关、监控、缓存、浏览器网络面板和第三方调用方无法通过 HTTP 状态识别失败；未捕获服务端异常也会被记录为成功请求，削弱告警能力。

### 建议

保留统一响应体，同时返回对应状态：参数错误 400、未登录 401、无权限 403、资源不存在 404、状态冲突 409、未捕获异常 500。前端拦截器继续读取业务码即可兼容迁移。

## CR-09：生产跨域与 SQL 日志边界过宽

- **级别：P2 中**
- **类型：部署配置 / 信息暴露**

### 证据

- `backend/src/main/java/com/artiv/config/CorsConfig.java:13-20` 对所有来源开放带凭据的 API 跨域；
- `backend/src/main/java/com/artiv/config/WebSocketConfig.java:22-25` 对 WebSocket 开放任意 Origin；
- `backend/src/main/resources/application.yml:17-21` 默认启用 MyBatis `StdOutImpl` 输出 SQL。

### 影响

当前 JWT 主要通过 Authorization 头发送，传统 CSRF 风险有限，但任意来源仍扩大了浏览器攻击面。SQL 和参数输出也可能在部署日志中泄露业务数据，并显著增加日志量。

### 建议

开发与生产配置分离；生产只允许实际前端域名；关闭 SQL 标准输出，改用可配置日志级别并脱敏。

## CR-10：部分 DTO 的服务端约束不完整

- **级别：P3 低**
- **类型：输入校验**

### 证据

- `backend/src/main/java/com/artiv/dto/StallRequest.java:13-41` 的标题、图片列表、阶段、参数和描述没有长度上限，库存缺少非负约束；
- `backend/src/main/java/com/artiv/dto/ProjectRequest.java:23-57` 的描述、图片、阶段和列表字段缺少大小上限，类型与合作方式没有枚举范围约束；
- `backend/src/main/java/com/artiv/dto/WorkRequest.java:31-33` 的可见性只要求非空，没有限制为 0 或 1。

### 影响

绕过前端后可以提交超长、负库存或非法枚举数据，结果可能是数据库异常、隐藏记录、前后端展示不一致或额外存储开销。

### 建议

为所有字符串、集合、数字和枚举增加 Bean Validation；图片路径还应校验为本系统已登记且属于当前用户的上传记录。服务层保留状态机校验，不能只依赖 DTO。

## CR-11：前端首包过大，图表依赖可能被整体打入页面

- **级别：P3 低**
- **类型：前端性能**

### 证据

生产构建虽成功，但 Vite 报告多个超过 500 kB 的 chunk：主入口约 1.12 MB，管理员统计页约 564 kB；主样式约 360 kB。

### 影响

在弱网或移动设备上，首次访问和进入统计页的解析时间会明显增加。管理员统计页使用 ECharts，若采用全量导入会进一步放大包体。

### 建议

检查路由懒加载是否完整；ECharts 使用按需导入；将 Element Plus、图表和业务页面拆分为稳定 vendor chunk；使用 bundle visualizer 确认主要体积来源后再优化，避免盲目拆包。

## CR-12：版本号与自动化质量门禁未统一

- **级别：P3 低**
- **类型：发布工程**

### 证据

- 文档当前版本为 `v0.8.13-beta`；
- `frontend/package.json:4` 仍为 `0.1.0`；
- `backend/pom.xml:14-17` 仍为 `0.0.1-SNAPSHOT`；
- 前端 `lint` 脚本固定带 `--fix`，没有只检查不改文件的 lint 命令；
- 未发现前端测试、E2E 测试或 CI 配置。

### 影响

构建产物无法直接追溯业务版本；代码提交前缺少自动质量门禁；现有高风险回归主要依赖人工和后端 Mockito 单元测试。

### 建议

统一前后端与文档版本；增加不修改文件的 `lint:check`；在 CI 中至少执行后端测试、前端 lint 和生产构建；逐步把关键人工 E2E 转成可重复的浏览器测试。

## 3. 测试覆盖审查

### 3.1 已有优势

- 后端共有 26 个测试文件，本次执行 164 项测试全部通过；
- 订单、邀请、应征、黑名单、举报、统计等主要服务已经有较多单元测试；
- 高风险业务规则在文档和人工 E2E 中有明确验收记录；
- 前端生产构建通过，没有阻断性编译错误。

### 3.2 主要缺口

现有后端测试以 Mockito 单元测试为主，未发现 `@SpringBootTest`、`@WebMvcTest`、`@DataJpaTest` 或 Testcontainers 测试。因此下列问题很难被当前测试发现：

1. 实际 HTTP 响应是否泄露实体字段；
2. 静态 `/uploads/**` 是否绕过业务鉴权；
3. MySQL 行锁、唯一约束与并发请求的真实行为；
4. JWT、拦截器、全局异常处理和控制器组合后的状态码；
5. WebSocket Origin、封禁状态和连接生命周期；
6. 前端路由、表单、实时消息与核心交易流程的回归。

建议优先补 5 组集成测试：用户公开响应字段、订单原图下载权限、应征并发状态、订单资金/库存并发、管理员与封禁账号鉴权。

## 4. 本轮专项核对中未发现阻断问题的部分

以下结论仅表示本轮代码和测试证据中未发现明显阻断问题，不代表绝对安全：

- **订单资金与库存主流程**：关键写入普遍使用事务和 `FOR UPDATE`，比普通 CRUD 路径更稳健；
- **管理员权限**：管理员 API 会查询数据库中的最新角色、封禁和删除状态；
- **系统消息渲染**：未发现 `v-html`，对象高亮通过文本分段完成，XSS 风险较低；
- **黑名单业务收口**：关系建立入口已有统一限制，非终态订单保护和待处理关系结束逻辑比较完整；
- **管理员统计日期**：后端以 2026-08-10 为最早日期，限制结束日期不晚于今天且单次不超过一年；日/周/月聚合边界采用结束日次日零点作为排他上界；
- **成交价格分层**：只统计已完成的企划订单，按订单项目快照读取企划类型，避免后续编辑企划改变历史统计口径；
- **上传路径穿越**：水印预览服务使用规范化路径并检查仍位于上传根目录，未发现直接的 `..` 越界读取路径。

## 6. 总体评价

Artiv 当前不是“核心流程不可用”的状态。相反，订单和治理模块已经形成较完整的业务状态机，测试数量也明显高于普通毕业设计项目。当前最需要的不是继续堆功能，而是把权限边界从“接口返回时隐藏”提升到“存储和下载时强制授权”，把完整实体响应改为用途明确的 DTO，并为少数非订单状态更新补齐并发控制。

完成第一批问题后，项目才适合进入 `v0.9.0-rc` 的部署与验收阶段；第二、三批可以与部署、移动端和答辩材料收尾并行推进。
