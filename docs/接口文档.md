## 1. 通用约定

- 基础路径：`/api/v1`
- 后端端口：`8080`
- 前端开发地址：`http://localhost:5173`
- 请求与响应：JSON；上传接口使用 `multipart/form-data`
- 登录鉴权：`Authorization: Bearer <token>`
- WebSocket：`ws://localhost:8080/ws?token=<token>`
- 时间：ISO 8601；金额：十进制数；分页页码从 1 开始
- 分页限制并未全局统一：订单 `page>=1`，不带 `projectId` 时 `size=1–50`、带 `projectId` 时 `size=1–200`；黑名单列表 `size=1–50`。其他接口须以各服务为准，不能假定全部自动裁剪。
- 普通请求主要校验 JWT，账号状态/资源归属由各业务服务处理；管理员接口额外回查数据库。默认 JWT 密钥、文件授权和私信准入等未修复边界见《未解决问题》CR-001–CR-005。

统一响应：

```json
{
  "code": 200,
  "message": "操作成功",
  "data": {}
}
```

分页响应的 `data` 使用 MyBatis-Plus `Page`，常用字段：

```json
{
  "records": [],
  "total": 0,
  "size": 10,
  "current": 1,
  "pages": 0
}
```

### 1.1 匿名访问规则

以下 GET 接口允许匿名访问；如携带 JWT，服务端仍会解析身份，用于下架资源、历史订单关联资源等可选鉴权：

- 企划、橱窗、作品的公开列表及数字 ID 详情
- `GET /api/v1/projects/{projectId}/applications`
- `GET /api/v1/users/artists`
- `GET /api/v1/users/{id}/public-profile`
- `GET /api/v1/users/{id}/works`
- `GET /api/v1/users/{id}/stalls`
- `GET /api/v1/users/{id}/projects`
- `GET /api/v1/users/{id}/reviews`
- `GET /api/v1/reviews`

除登录、注册和上述公开 GET 外，其余接口默认需要 JWT。

实际拦截器对 GET `/api/v1/reviews` 使用前缀放行，因此 `GET /reviews/{reviewId}/appeal` 也未强制登录。`ReviewService.getOwnAppeal` 要求当前用户为收到评价的画师，但对空用户 ID 缺少防护：匿名访问已有评价及订单时存在空指针路径，进入通用异常处理（HTTP 200、业务码 500），不是正常的未登录响应，也不会因此取得申诉。本轮仅静态确认，未发请求复现。`/uploads/**` 不属于 API 拦截范围，当前匿名可访问，见第 12 节。

### 1.2 首页公开数据组合

首页不新增专用聚合接口，使用以下已实现的匿名公开接口并行读取真实内容：

- `GET /api/v1/projects?page=1&size=4&sort=newest`：最新公开招募企划。
- `GET /api/v1/projects/{projectId}/applications?page=1&size=1`：读取每条首页企划的有效应征总数；单条统计失败时明确显示暂不可用，不伪造为 0。
- `GET /api/v1/stalls?page=1&size=4&sort=newest`：最新在售且有库存的画师橱窗。
- `GET /api/v1/works?page=1&size=8&sort=newest`：首页精选作品。
- `GET /api/v1/users/artists?page=1&size=3`：认证画师、简介、题材标签和公开作品摘要。

`GET /api/v1/users/artists` 以正常账号、未删除且 `cert_status=2` 作为画师大厅准入条件，不检查注册主身份 `role=1/2`。因此默认企划方工作台的账号通过画师认证后同样会进入画师大厅；默认画师工作台但未认证的账号不会进入。

上述业务区域独立处理加载、空数据和失败重试；首页不使用虚构评价、硬编码业务指标或静态业务数据作为接口失败后的回退内容。首屏右侧五图是随前端发布的固定装饰资源，只用于视觉展示，不代表作品记录，也没有点击跳转。当前首页数据量较小，企划应征数沿用大厅现有逐条查询方式；数据规模扩大后可新增公开聚合接口避免 N+1 请求。

画师大厅 `subjects` 为英文逗号分隔的多选值，按“同时包含全部所选题材”筛选。认证、分类、题材和关键词条件均在数据库分页查询中执行；服务端只对当前页画师批量读取评分、公开作品分类和最近 5 件公开作品，避免全量加载及逐画师查询。

默认工作台请求：

```json
{
  "role": 2
}
```

只允许普通账号在 `1 企划方 / 2 画师` 之间切换；管理员不能调用。响应返回清除密码后的最新用户资料。`role` 不参与应征、创建橱窗、画师大厅准入等画师能力判断，这些能力继续由 `cert_status=2`、账号状态和具体业务条件决定。

账号资料请求：

```json
{
  "nickname": "示例画师",
  "employerBio": "偏好角色设计和场景企划"
}
```

画师资料请求：

```json
{
  "bio": "擅长人物与场景插画",
  "tags": ["日系", "场景", "厚涂"]
}
```

用户侧认证状态只使用 `0 未认证 / 1 审核中 / 2 已认证`。初次申请被拒后恢复为 `0`，拒绝结果继续保留在申请历史；已认证资料修改不会把用户降级为审核中。常用站首期支持 Pixiv、Lofter、微博、小红书、Bilibili、DeviantArt、站酷和涂鸦王国个人主页，平台根地址会被拒绝。

`nickname` 必填，去除首尾空格后最长 50 字；允许保留本人当前昵称，但不能与其他用户重复。服务层先排除本人 ID 检查，数据库 `uk_nickname` 负责并发写入的最终保护；冲突返回业务码 `1004` 和“昵称已被使用，无法更改”。接口返回清除密码后的最新用户资料，前端据此同步顶部导航和工作台昵称。

认证申请请求：

```json
{
  "commonId": "画师阿绘",
  "commonSite": "https://www.pixiv.net/users/12345678"
}
```

`commonId` 与 `commonSite` 均必填，长度分别不超过 100/500；常用站必须通过服务端支持站点和个人主页路径校验，不能填任意域名或平台首页。上例仅演示 URL 格式，不代表真实申请资料。提交时服务端统计公开作品并保存数量快照，管理员通过前仍重新核验简介和作品数。

头像请求：

```json
{
  "avatar": "/uploads/xxxxxxxx.jpg"
}
```

公开主页接口只应返回公开展示字段，不应扩展用户名、手机号、余额、认证材料等隐私字段。正常用户无论认证状态都能打开 `role=painter` 主页并查看公开作品；前端根据 `certStatus` 显示“认证画师”或“未认证”。认证仍是应征等交易能力的权限条件，不是公开主页的准入条件。需求完成率和准时交稿率只在画师视图统计、展示；企划方视图不计算也不展示需求完成率。

创建作品时标题必填且最长 20 个字；类型、至少一个题材风格、图片地址和可见范围必填，作品说明最长 500 个字。数据库历史字段仍可容纳旧数据，本限制作用于当前创建接口。

作品删除规则（2026-09-05）：本人公开或隐藏的作品均可删除，不套用橱窗的未完成订单限制。批量操作复用既有删除实现：服务端检查作品归属后，通过 MyBatis-Plus 逻辑删除设置 `deleted=1`；不存在、已删除或非本人记录返回无权限业务结果。普通隐藏设置 `visibility=0`，仍保留在“我的作品”；删除后不再出现在本人列表。作品广场最新/最早/热门/关注、公开主页、收藏列表和公开详情均过滤隐藏或已删除作品，所以删除即退出公开展示，无需额外调用隐藏接口或重写后端删除。此操作不物理清理上传文件。

“我的作品”的批量删除弹窗分页读取 `/works/mine`，支持跨页勾选、全选本页与清空选择，二次确认后逐件调用上述 DELETE。每件独立提交，部分失败不会撤销已成功项；弹窗显示成功数量并保留失败项，执行期间禁止重复提交与关闭。没有新增批量事务接口。

`GET /works` 的 `sort` 当前支持 `newest`、`oldest`、`popular`。作品广场各视图前端每批加载 25 件；“关注画师的”视图使用独立登录接口，不向客户端暴露关注画师 ID 集合。

```json
  "category": "立绘",
  "subject": "日系,女性",
  "image": "/uploads/xxxxxxxx.png",
  "description": "作品说明",
  "visibility": 1

```

| --- | --- | --- | --- | --- |
| GET | `/api/v1/stalls` | 已实现 | 匿名 | 只返回上架、库存大于 0、未删除的橱窗 |
| GET | `/api/v1/stalls/mine` | 已实现 | 登录 | 本人全部未删除橱窗 |
| GET | `/api/v1/stalls/{id}` | 已实现 | 匿名/可选登录 | 下架或无库存时仅画师本人、历史下单方可读 |
| POST | `/api/v1/stalls` | 已实现 | 已认证画师 | 创建固定价橱窗；服务端强制校验正常账号与 `cert_status=2` |
| PUT | `/api/v1/stalls/{id}` | 已实现 | 橱窗作者 | 受限编辑库存和题材风格 |
| PUT | `/api/v1/stalls/{id}/status` | 已实现 | 橱窗作者 | 查询参数 `status=0` 下架、`status=1` 上架 |
| DELETE | `/api/v1/stalls/{id}` | 已实现 | 橱窗作者 | 无未完成订单时逻辑删除并下架 |
| POST | `/api/v1/stalls/{id}/purchase` | 已实现 | 登录 | 按服务端固定价创建正式橱窗订单 |

公开列表参数：`page`、`size`、`category`、`keyword`、`sort`、`subject`、`priceMin`、`priceMax`、`deliverTime`。

橱窗列表、本人橱窗列表、公开主页中的橱窗列表以及橱窗详情响应均包含 `soldCount`，表示该橱窗状态为“已完成”的订单总数；无完成订单时返回 `0`。列表按当前页橱窗 ID 一次聚合统计，不会为每张卡片逐条查询订单。

创建橱窗的关键字段：

```json
{
  "title": "角色立绘约稿",
  "category": "立绘",
  "cover": "/uploads/cover.png",
  "images": "/uploads/detail-1.png,/uploads/detail-2.png",
  "price": 500,
  "stock": 3,
  "deliverTime": "30天",
  "phases": "[{\"name\":\"初稿\"},{\"name\":\"修改\"},{\"name\":\"终稿\"}]",
  "params": "{\"subject\":[\"日系\"]}",
  "description": "服务说明"
}
```

编辑接口只接受库存与追加题材；请求字段为复数 `subjects`，合并到 `params` 内的单数键 `subject`，不会移除原有题材：

```json
{
  "stock": 5,
  "subjects": ["日系", "场景"]
}
```

立即下单会校验上架、库存、余额、账号可用性、双向屏蔽及禁止购买自己的橱窗；事务内扣减余额和库存，保存订单及阶段配置快照、事件、通知和会话系统卡片。`order_stage` 提交版本在画师交稿时才插入。当前购买接口无幂等键，余额/库存充足时同一购买请求重试可产生第二笔订单（CR-004）。

创建橱窗由服务端以 `cert_status=2` 作为画师能力门槛；注册时选择的 `role` 只决定默认工作台，不会覆盖认证能力。未认证、审核中、封禁、已删除或异常账号均不能创建新橱窗，前端同时隐藏创建入口并展示认证提示。历史橱窗不会因当前认证状态变化而被自动删除。

```json
  "budgetMin": 500,
  "budgetMax": 800,
  "budget": 800,
```

标题最长 20 字；最低和最高预算均必须大于 0，且 `budgetMin <= budgetMax`；截稿日期不得为空，且至少为操作当日 +2 天，前端日期选择器和服务端均校验。`budget` 是兼容旧客户端的单值字段：新客户端应提交 `budgetMin / budgetMax`，服务端仍将最高预算同步写入 `budget`；只提交旧 `budget` 时按相同上下限保存为固定预算。创作阶段只保存名称和顺序，旧版 `percent` 字段会被忽略。

企划列表、本人企划、详情及邀请摘要响应均返回 `budgetMin`、`budgetMax` 和兼容字段 `budget`。历史企划经 `20260825_project_budget_range.sql` 回填为相同上下限；已确认原始发布区间的本地企划可按真实下限单独校正。

`mode=0` 为公开企划；`mode=1` 和 `invitePainterId` 在发布企划事务中创建唯一定向关系，不再通过独立接口追加受邀画师。发布成功会同时生成邀请记录和 `INVITATION_CREATED` 系统通知；待回应期间不允许企划方撤回、下架或删除。

企划不再维护独立招募截止字段，数据库中的历史 `recruit_deadline` 已由 `20260825_project_deadline_unification.sql` 回填并删除。`deadline` 在企划层只控制大厅展示、新应征和待处理邀请接受；它不取消已有应征，不删除会话，也不参与订单接单、交付、验收、完成、结算、评价或售后状态机。订单创建时会把当时的企划截稿日期写入 `projectSnapshot.deadline`，作为准时交稿率的稳定统计基准，后续编辑企划不会改写历史订单。

本人企划的展示口径为：`status=4` 显示“已下架”；`status=0` 且 `deadline < 当前日期` 显示“已过期”；其余正常上架企划显示“招募中”。自然过期不修改持久状态。主动下架后重新上架、以及被拒绝的定向企划改为公开企划，都必须选择至少当前日期 +2 天的新截稿日期；保存后若其他治理条件正常，企划重新进入大厅。

公开大厅固定排除 `mode=1`。数字 ID 详情按创建者、唯一受邀画师、管理员和后续合法业务关联方校验；运行态接口已确认无关企划方被拒绝。完整双账号演示仍建议在发布前使用专用数据回归。

企划面板接口只允许发布者读取。`contentEditable=true` 表示查询时不存在未删除的有效应征、待处理/已接受邀请及任何状态的未删除关联订单。完整编辑 DTO 可提交标题、描述、预算、标签、类型、题材、图片、稿件要求和阶段；服务端在事务内再次检查，但与并发建单/应征尚缺统一锁协议（CR-007）。日期、上下架、删除各用专门接口；定向被拒后只可通过 `publish-public` 转公开，不提供任意修改合作模式或更换邀请目标接口。

公开企划邀请创建请求：

```json
{
  "projectId": 12,
  "painterId": 2,
  "invitationType": 2,
  "offeredPrice": 500,
  "message": "希望按此价格邀请您参与"
}
```

`invitationType` 只允许 `1` 邀请报价或 `2` 带价邀请。邀请报价不得携带价格；带价邀请的 `offeredPrice` 必须不低于 50，暂不要求位于企划预算区间。`message` 选填且最多 500 字。企划必须属于当前账号、`mode=0`、正常上架、未被治理下架且截稿日期未过；目标必须是正常的已认证画师且不能是本人。目标画师已有该企划的当前有效应征时禁止再邀请。

接受请求按类型使用：

```json
{
  "quote": 500
}
```

- 定向邀请：`quote` 必填。
- 邀请报价：`quote` 必填，成功后按画师本次报价形成应征。
- 带价邀请：请求体可为 `{}`，价格只读取邀请记录的 `offeredPrice`；客户端报价不会覆盖邀请价格，生成的 `quoteSource=1` 应征禁止改价。

三类邀请接受均不接收画师填写的 `intro`。服务端会按邀请类型写入固定的内部来源说明（定向邀请、邀请报价、带价邀请），用于保持应征记录可追溯。普通大厅应征接口仍要求真实 `intro` 和 `quote`，不受此规则影响。

拒绝请求：

```json
{
  "reason": "近期档期无法配合"
}
```

`reason` 必填，最多 500 字。当前列表和按企划查询返回 `InvitationProjectSummary`，包含：

```json
{
  "invitationId": 3,
  "projectId": 12,
  "cover": "/uploads/reference.png",
  "projectTitle": "公开角色企划",
  "category": "立绘",
  "projectDescription": "角色立绘需求说明",
  "budget": 800,
  "invitationType": 2,
  "offeredPrice": 500,
  "message": "希望按此价格邀请您参与",
  "status": 0,
  "rejectReason": null,
  "applicationId": null,
  "createdAt": "2026-08-26T10:00:00",
  "respondedAt": null,
  "projectAvailable": true
}
```

`invitationType` 为 `0` 定向邀请、`1` 邀请报价、`2` 带价邀请。`status` 为 `0` 待处理、`1` 已接受、`2` 已拒绝、`3` 已失效；筛选只允许这四个值。

省略 `status` 时，服务端按 `0 → 1 → 2 → 3` 排序，同状态按 `created_at DESC`；指定状态时只返回该状态并按 `created_at DESC`。列表始终排除 `painter_hidden=1` 的提醒，但按企划查询和响应接口不受提醒隐藏影响。逻辑删除企划的提醒继续返回，`projectAvailable=false`，客户端禁用详情入口。

定向邀请创建入口仍为 `POST /api/v1/projects` 的 `mode=1 + invitePainterId`；公开企划邀请只使用本节新增创建接口。注册主身份 `role=1/2` 不参与画师认证权限判断。

当前副作用：

- 创建：定向企划写入 `INVITATION_CREATED`；公开邀请按类型写入 `PUBLIC_QUOTE_INVITATION_CREATED` 或 `PUBLIC_PRICED_INVITATION_CREATED`。首次通知不创建应征、会话或订单。
- 接受：创建/恢复有效应征并写入 `application_id`，建立或复用双方项目会话；分别生成会话系统提示和独立系统通知，正文相同。公开邀请接受不额外发送同义的 `APPLICATION_CREATED`。
- 大厅自主应征：如果同企划、同画师存在待处理公开邀请，则全部同步为已接受并关联同一应征，同时建立或复用会话。
- 拒绝：写入 `reject_reason / responded_at` 并通知企划方。只有定向邀请自动下架企划；公开企划继续招募。
- 失效：企划过期、主动下架、管理员下架或逻辑删除后，待处理公开邀请变为 `status=3`，不可接受或拒绝，只能查看提醒和隐藏。已接受/已拒绝结果不覆盖，延长截稿日期也不恢复失效邀请。
- 被拒绝定向企划可由作者调用 `PUT /projects/{id}/publish-public?deadline=YYYY-MM-DD` 转为公开招募；原邀请记录作为历史保留。
- 隐藏提醒：只把当前邀请的 `painter_hidden` 设为 `1` 并记录时间；不修改 `status`、`application_id`、企划、消息、会话和订单。重复隐藏幂等返回成功。
- 待处理定向邀请仍禁止企划方撤回、下架或删除；公开企划可以正常下架或删除，并使待处理公开邀请失效。重复接受或拒绝由状态条件拦截。

使用约束：

1. 客户端不能提交受邀画师以外的身份、邀请状态、应征 ID 或消息正文。
2. 接受成功的业务证据包括邀请、应征、会话系统提示和独立系统消息，不能只检查 `invitation.status`。
3. 清理旧邀请或企划数据前必须备份并检查关联应征和消息。
4. 接受不自动创建订单；后续选定和发单继续使用第 7 节接口。
5. 客户端不得把 `DELETE /invitations/{id}` 解释为拒绝邀请或删除业务数据；其唯一语义是当前画师隐藏提醒。
6. `quoteSource=1` 是服务端锁价依据；前端隐藏“更改应征”不能替代服务端校验。

- `afterSale`：仅返回正在争议/售后处理中的订单（状态 `5`）；已经取消、退款完成或售后处理完成的订单不会返回。

默认排序口径：

1. 进行中、待验收、争议中及其他未结束交易（状态 `1 / 2 / 5`）。
2. 待接单（状态 `0`）。
3. 已完成及交易关闭（状态 `3 / 4`）。

同一优先级按 `created_at DESC` 排序，时间相同再按 `id DESC`。该排序由服务端完成，前端不得重新按状态或时间打乱。

订单状态：

| 值 | 状态 |
| --- | --- |
| 0 | 待接单 |
| 1 | 进行中 |
| 2 | 待验收 |
| 3 | 已完成 |
| 4 | 已取消 |
| 5 | 争议中 |

状态 `4` 是资金已经退回下单用户后的统一终态值。企划方界面显示“已退款”，画师界面显示“交易关闭”；状态 `3` 双方均显示“已完成”。接口原始值不因查看者角色变化。

阶段提交：

```json
{
  "content": "初稿说明",
  "images": [
    "/uploads/original-1.png",
    "/uploads/original-2.png"
  ]
}
```

`images` 必须包含 1–9 个本站 `/uploads/` 路径，按数组顺序保存。服务端逐张生成最长边不超过 1080px、带 `ARTIV PREVIEW` 水印的验收预览；`order_stage.attachments` 与 `originals` 均按相同顺序使用逗号分隔存储。交易完成前企划方响应中的全部原图地址会被清空；最后阶段通过或执行 `complete` 后结算并开放当前确认版本的全部原图。旧客户端的单值 `image` 字段暂时保留兼容，新代码不得继续使用。

这里的原图限制发生在详情响应层；文件仍位于公开 `/uploads/**`，知道 URL 即可直接读取（CR-002）。`getDetail` 还会为历史提交补水印并更新记录，因此该 GET 目前不是纯只读（CR-020）。订单完成后服务端不再清空各历史提交的原图字段，页面主下载入口展示当前版本，不应把页面行为当作更严格的接口字段过滤。

阶段验收：

```json
{
  "action": "approve",
  "remark": ""
}
```

`action` 支持：

- `approve`：通过并进入下一阶段；若已是最后阶段则完成
- `revise`：要求修改，`remark` 应填写修改意见
- `complete`：跳过剩余阶段并直接完成、结算、开放原图

争议请求：

```json
{
  "reason": "当前交付与确认需求不一致",
  "images": ["/uploads/evidence-a.png", "/uploads/evidence-b.png"],
  "description": "图片中标出了差异位置"
}
```

争议只允许从进行中或待验收状态发起。创建后订单进入 `5=争议中`，普通交易操作暂停，等待管理员执行全额退款企划方或全额结算画师。

| 方法 | 路径 | 当前状态 | 权限 | 说明 |
| --- | --- | --- | --- | --- |
| GET | `/api/v1/users/{userId}/reviews?role=painter&page=1&size=10` | 已实现 | 匿名 | 按 `painter` / `employer` 主页身份分页查询收到的公开评价 |
| POST | `/api/v1/orders/{orderId}/reviews` | 已实现 | 订单参与方 | 提交当前用户对交易另一方的评价；评价对象由服务端推导 |
| POST | `/api/v1/reviews/{reviewId}/appeals` | 已实现 | 收到评价的画师 | 对本人以画师身份收到的评价申请删除 |
| GET | `/api/v1/reviews/{reviewId}/appeal` | 已实现 | 申诉画师本人 | 查看本人针对该评价提交的申诉及处理状态 |

评价请求：

```json
{
  "score": 5,
  "content": "沟通顺畅，交付符合预期。",
  "images": ["/uploads/example-review.jpg"]
}
```

`score` 为 1–5，`content` 最多 500 字，`images` 最多 6 张且必须是本站 `/uploads/` 路径。请求不接受 `toId`；客户端不能指定、伪造或切换评价对象。

业务规则：

- 只有 `status=3` 且未删除、`completed_at` 存在的完成订单可以评价；企划方和画师从完成时刻起分别拥有 7×24 小时评价期。
- 每位参与方对同一订单最多评价一次，双方互不影响；数据库唯一约束与事务行锁共同防止并发重复。
- 7 天内未评价不生成默认评价，不计入平均分；期限内成功提交的评价长期公开。
- `reviewStatus` 为 `NOT_AVAILABLE`、`PENDING`、`SUBMITTED` 或 `EXPIRED`。订单列表的 `review` 筛选只返回当前用户仍可评价的订单。
- 公开响应包含评价人昵称/头像/身份、来源类型与标题、星级、正文、图片和时间；只有评价人头像可打开对应公开主页。
- 公开主页评分按订单中的画师/企划方身份分别统计，只统计 `deleted=0` 的评价。无评价时 `averageScore=null`、`reviewCount=0`。

申诉请求：

```json
{
  "reason": "评价包含与本次交易无关的内容"
}
```

首期只允许评价对应订单的画师申诉，一条评价最多一笔申诉。申诉处理中评价继续公开；管理员批准后只做逻辑隐藏并立即退出公开列表与评分统计，驳回则保持公开。提交、批准和驳回会产生系统通知，终态处理同时写入管理员审计日志。详细口径见[《评价系统设计计划书》](开发计划/评价系统设计计划书.md)。

成交价格分层接口只统计 `status=3`、`project_id` 非空、实际成交金额大于 0 的企划订单，并按 `completed_at` 归入所选日期范围。`category` 不传表示全部类型；传值时只允许平台统一的 10 项企划类型。类型优先读取订单 `project_snapshot.category`，旧订单快照缺失时回退关联企划类型，避免企划后续编辑改写已有快照统计。

响应提供 `sampleSize`、`distinctPriceCount`、均价、中位价、最低/最高价和五档 `buckets`。五档目标比例为 `10 / 20 / 40 / 20 / 10`，价格边界按当前样本动态计算；每档同时返回真实 `orderCount`、`actualRate` 和 `gmv`。无数据、少于 10 笔或价格过度集中时接口仍成功，并分别返回 `NO_DATA`、`INSUFFICIENT_SAMPLE`、`PRICE_CONCENTRATED`，由前端显示对应空状态。

用户封禁请求：

```json
{
  "status": 1,
  "reason": "多次发布违规内容",
  "bannedUntil": "2026-09-01T00:00:00"
}
```

`bannedUntil` 为空表示永久封禁。封禁用户仍能登录、浏览和查看历史，但不能发布企划、应征、创建橱窗、购买橱窗或按应征发送新订单；封禁事务会锁定并终止其全部未结束订单，向下单用户全额退款，并恢复橱窗库存。限时封禁由定时任务与请求时惰性检查自动解除。

仲裁请求：

```json
{
  "result": "REFUND_EMPLOYER",
  "reason": "根据双方证据认定应全额退款"
}
```

`result` 首期只接受 `REFUND_EMPLOYER` 和 `SETTLE_PAINTER`。`PARTIAL_REFUND` 为后续扩展预留值，当前会明确返回状态流转错误。所有认证、封禁、企划治理、仲裁和自动解封都会写入 `admin_action_log`。

接口未传日期时默认近 7 天；管理端页面首次进入时默认选择平台数据起始日 `2026-08-10` 至今天，并提供近 7 天、近 30 天和全部历史快捷选项。允许范围为 `2026-08-10` 至今天，单次查询为 1–366 天，前后端都会拒绝越界日期。

总用户数是当前未删除用户快照；新增用户和新增订单分别按 `user.created_at`、`order_info.created_at` 统计真实事件数；完成订单与成交额按 `order_info.completed_at` 统计，且只包含当前状态为已完成的订单。需求分析以所选日期内发布的企划为一个批次：`publishedProjects` 是新增企划数，`projectsWithOrders` 是该批企划中至少产生过一笔订单的去重企划数，前端显示为“生成订单企划”，不能把它解释为新增订单笔数。需求趋势中的新增应征则独立按 `application.created_at` 统计所选日期内发生的应征事件，不受企划发布时间限制。

需求统计中的 `categories` 是所选日期内发布企划的类型分布；`supplyDemandGap[].activeStalls` 是查询时点当前在售橱窗的供给快照；`funnel` 以所选日期内发布的企划为批次并按企划去重，前端展示各阶段数量和相邻阶段转化率。完成订单成交价格分层按 `completed_at` 落在范围内的已完成企划订单实际成交价统计，类型优先使用订单中的企划快照。

`/api/v1/admin/stats` 与 `/api/v1/admin/stats/demand` 会根据查询跨度返回 `granularity`：1–31 天为 `DAY`，32–90 天为 `WEEK`，91–366 天为 `MONTH`。趋势数组中的每个时间桶统一包含 `date`（兼容字段，等同桶开始日期）、`startDate`、`endDate`、`label`、`value`，双序列趋势额外包含 `secondary`。周桶从查询开始日期起每 7 天分组，月桶按自然月分组；首尾不完整周期使用实际覆盖范围，没有数据的桶也返回 0。

需求趋势中的 `value` 是按 `project.created_at` 统计的新增企划数，`secondary` 是按 `application.created_at` 独立统计的平台新增应征数。后者不要求对应企划也在当前日期范围内发布；后来取消、结束或因屏蔽终止的应征仍保留其创建时发生的历史新增量。平台运营趋势沿用相同时间桶格式，分别用于新增用户、新增订单与完成订单。

## 16. 错误码

| code | 含义 |
| --- | --- |
| 200 | 操作成功 |
| 400 | 参数错误 |
| 401 | 未登录或登录过期 |
| 403 | 无权操作该资源 |
| 404 | HTTP 资源不存在 |
| 500 | 服务器内部错误 |
| 1001 | 用户名已存在 |
| 1002 | 用户名或密码错误 |
| 1003 | Token 无效或已过期 |
| 1004 | 昵称已存在 |
| 2001 | 参数校验失败 |
| 2002 | 业务资源不存在 |
| 2003 | 无权操作该业务资源 |
| 3001 | 状态流转不合法 |
| 3002 | 预算或余额不足 |
| 4001 | 上传文件类型或大小不合法 |

> 当前响应语义（按 `GlobalExceptionHandler`）：仅业务码 `403/2003` 映射为 HTTP 403。未登录或无效 JWT 抛出的 `BusinessException(401)` 当前返回 **HTTP 200 + body.code=401**；其他业务异常也为 HTTP 200。DTO 校验异常返回 body.code=2001，通用异常返回 body.code=500，二者同样没有设置非 200 状态。前端同时处理 envelope 与 HTTP 状态；完整状态码治理属于 CR-015。旧“真实 HTTP 401”描述不适用于当前异常处理实现，框架未进入此处理器的响应另论。
