# 艺绘（Artiv）沟通与消息设计（F9）

> 版本：v1.1 ｜ 最近更新：2026-08-13 ｜ 性质：设计与当前实现记录
> 定位：订单开发前置模块（F9）。本文第 1–9 节保留目标设计，第 13 节为当前 `main` 的生效实现与边界；若内容冲突，以第 13 节为准。

## 1. 功能范围

- 站内信：系统通知 / 应征通知 / 订单变化 / 验收结果
- 私信：用户间 1v1 私聊（应征沟通、议价前沟通）
- 订单内聊天：订单双方在订单详情内的消息（含接单前议价）
- WebSocket 实时推送：新消息即时到达 + 未读红点
- 消息已读 / 全部已读

## 2. 数据模型（message 表）

现状（已有）：

| 字段 | 说明 |
| --- | --- |
| id / from_id / to_id / order_id | 基本消息结构 |
| type | 0 系统、1 应征、2 订单、3 私信 |
| content / read_at / deleted | 内容、已读时间、逻辑删除 |

需要补充：

- `project_id`（可选）：私信关联企划（应征沟通按企划聚合会话）
- `conversation_key`（推荐）：`from_to` 归一化（min:max）便于取双方会话，如 `1_2`

## 3. WebSocket 架构

当前 `MessageWebSocketHandler` 为骨架，需完善：

1. **连接鉴权**：`ws://localhost:8080/ws?token=<jwt>`，握手时用 JwtUtil 解析 userId，失败拒绝连接
2. **会话管理**：`userId → WebSocketSession`（已有 ConcurrentHashMap 骨架），支持多端（一个用户多连接）
3. **断线重连**：前端心跳（ping/pong）+ 断线指数退避重连；重连后拉取未读消息补差
4. **消息格式**：

```json
{
  "type": "NEW_MESSAGE",
  "data": { "id": 100, "fromId": 2, "toId": 1, "orderId": null, "content": "...", "createdAt": "2026-08-12 12:00" }
}
```

事件类型：`NEW_MESSAGE`、`ORDER_UPDATE`、`APPLICATION`、`SYSTEM`

## 4. 接口设计

### 4.1 已有接口（保持）

- `GET /api/v1/messages`：我的消息列表
- `PUT /api/v1/messages/{id}/read`：单条已读
- `PUT /api/v1/messages/read-all`：全部已读

### 4.2 新增接口

| 方法 | 路径 | 说明 | 权限 |
| --- | --- | --- | --- |
| POST | `/api/v1/messages/private` | 发送私信（from 当前用户，body 含 toId/content/projectId?） | 登录 |
| GET | `/api/v1/messages/conversation?withUserId=` | 我与某用户的会话消息（分页） | 双方 |
| POST | `/api/v1/orders/{id}/messages` | 已取消的独立订单聊天规划，不提供 | - |
| GET | `/api/v1/orders/{id}/messages` | 已取消的独立订单聊天规划，不提供 | - |

## 5. 事件推送清单

| 事件 | 触发时机 | 推送对象 |
| --- | --- | --- |
| APPLICATION | 画师应征企划 | 企划方 |
| ORDER_UPDATE | 订单创建 / 接单 / 状态变化 | 订单双方 |
| ORDER_STAGE | 阶段提交 / 验收结果 | 订单双方 |
| SYSTEM | 系统通知（认证结果、封禁等） | 相关用户 |

推送流程：业务操作 → 写 message 落库 → WebSocket pushToUser → 前端未读 +1 / 红点。

## 6. 前端结构

- 独立消息中心（`/messages`）：我的消息 + 系统消息 + 会话切换；旧 `/dashboard/messages`、`/painter/messages` 仅作兼容跳转
- 私聊窗口：应征列表 / 画师主页发起，1v1 聊天（气泡样式）
- 订单详情聊天框：订单内消息（接单前议价 + 进行中沟通）
- WebSocket 客户端（`src/utils/ws.js`）：连接、心跳、重连、事件分发、未读计数

## 6.1 私聊入口与交互设计

### 入口位置（4 类场景）

| 场景 | 入口 | 说明 |
| --- | --- | --- |
| ① 应征沟通（下单前核心） | 应征管理列表每条记录右侧「沟通」按钮 | 企划方与应征画师 1v1；画师侧「我的应征」有对应入口 |
| ② 发现画师 | 画师列表 / 画师主页「私聊」按钮 | 已认证画师可被私聊 |
| ③ 订单沟通 | 订单详情底部聊天框 | 接单前议价 + 进行中沟通 |
| ④ 消息中心 | 顶栏铃铛 → 消息中心会话列表 | 私信 / 订单消息 / 系统通知统一入口 |

### 触发与使用流程

```
点击「沟通 / 私聊」按钮
    ↓
打开私聊窗口（1v1，气泡样式，仅双方可见）
    ↓
发送消息 → 落库（conversation_key 聚合会话）→ WebSocket 推送给对方
    ↓
对方顶栏铃铛红点 +1 → 消息中心出现新会话 → 点击回复
    ↓
达成一致 → 企划方在应征列表「选定」该画师 → 创建订单
```

### 交互细节

- 应征列表「沟通」按钮与「选定」按钮并列，先沟通后选定
- 私聊窗口支持：发送文字、查看历史消息（分页加载）、消息时间分组
- 消息中心会话按最近消息时间排序，未读加粗 / 红点
- 订单详情聊天框：待接单时用于议价（配合画师报价 / 企划方确认金额按钮），接单后用于过程沟通

### 10.1 本轮新增的后端能力

#### 消息数据与迁移

- `message` 表新增 `project_id`：应征场景下让私信关联具体企划。
- `message` 表新增 `subtype`：细分消息业务语义，当前使用 `PRIVATE_CHAT`、`APPLICATION_CREATED`。
- `message` 表新增 `conversation_key`：服务端按较小用户 ID + `_` + 较大用户 ID 生成，例如用户 2 与用户 15 固定为 `2_15`。
- 新增增量迁移脚本：`backend/sql/migrations/20260812_f9_messaging.sql`，用于已有数据库补字段和索引；`init.sql` 也已同步新结构。

#### 私信与会话接口（已实现）

| 方法 | 路径 | 实际功能 |
| --- | --- | --- |
| POST | `/api/v1/messages/private` | 发送 1v1 私信；发送者从 JWT 获取，不接收前端 `fromId`。 |
| GET | `/api/v1/messages/conversation` | 分页查看我与指定用户的私信历史；支持可选 `projectId`。 |
| GET | `/api/v1/messages/conversations` | 获取会话摘要列表：对方信息、最后消息、最近时间、该会话未读数。 |
| GET | `/api/v1/messages/unread-count` | 获取当前用户总未读数。 |

私信服务端校验：不能给自己发消息；内容不能为空且最多 500 字；接收方必须存在、未删除、未封禁；若关联企划，则仅企划发布者与该企划的应征画师可以进入该企划私聊。

#### 应征通知（已实现）

- 画师提交应征成功后，后端会为企划方写入一条 `type=1`、`subtype=APPLICATION_CREATED` 的站内通知。
- 通知内容包含应征画师展示名和企划标题；展示名优先昵称、其次登录名，只有两者均缺失时才回退内部 ID。
- 消息先写数据库，再尝试实时推送；推送失败不会让应征操作回滚。

#### WebSocket（已实现的部分）

- `/ws?token=<jwt>` 会解析 JWT；缺 token 或无效 token 会拒绝连接。
- 会话管理从“一个用户一个连接”改为“一个用户多个连接”，同账号多标签页可同时收到推送。
- 私信落库后向接收者推送 `NEW_MESSAGE`；应征通知落库后推送 `APPLICATION`；其他系统通知使用 `SYSTEM`。
- 前端 `src/utils/ws.js` 具备断线指数退避重连（1 秒、2 秒、4 秒……最高 15 秒）。

## 11. C2C 下单—沟通最小闭环（2026-08-12）

> 当前规则：本节保留 F9 历史记录。与第 12 节冲突的旧表述均不再生效：企划作者可对待处理或已选定应征者主动建立会话；画师不可主动建立，只能在已有会话内回复；选定应征本身不会自动创建项目会话。

### 11.1 本轮目标与边界

本轮把 F9 收敛为 C2C 双方对接所需的最小闭环，而不是完整订单系统：

- 消息中心只保留两个一级入口：**我的消息**（1v1 私聊、应征沟通、橱窗交易沟通）和**系统通知**。
- 画师应征企划后，企划方收到应征通知；企划方可自行选择待处理或已选定画师，并主动建立该企划的沟通会话。
- 用户购买橱窗时不经过支付；后端仅创建一条用于关联沟通的最小订单记录，买家与画师各收到一条系统通知，并自动获得独立交易会话。
- 本轮不做支付、托管、接单/拒单、订单阶段、验收、退款、库存扣减/回滚、订单详情页或完整订单状态流转。

“自动开启对话”在本项目中的定义为：后端自动写入首条引导消息，前端将该会话置入“我的消息”；橱窗页面下单成功、应征管理页选定成功会直接跳转至对应会话，不强制在对方浏览器弹窗。

### 11.2 已实现的服务端行为

#### 橱窗下单

`POST /api/v1/stalls/{id}/purchase` 改为由 `OrderService.createStallPurchase` 统一完成：

1. 校验橱窗存在、未删除、上架、有库存，且购买者不是橱窗所属画师；校验画师账号可用。
2. 创建 `order_info` 最小关联记录：`stall_id`、买家、画师、橱窗价格、`status=0`。该记录仅用于会话关联，不代表支付、接单或订单已进入履约状态。
3. 创建两条 `message.type=0` 系统通知：`STALL_PURCHASED` 给买家，`STALL_PURCHASE_RECEIVED` 给画师。
4. 创建一条 `message.type=3`、`order_id=<订单ID>`、`conversation_key=<双方归一化ID>` 的首条交易会话消息；后续聊天必须携带同一 `orderId`。
5. 本轮**不修改 `stall.stock`**，避免在没有取消、拒绝和库存回滚机制时错误占用库存。

#### 应征选定

- 新增 `PUT /api/v1/applications/{id}/select`；仅企划所属者可以选定状态为待处理的应征。
- 成功后将该应征置为 `status=1`，向画师写入 `APPLICATION_SELECTED` 通知，并创建一条带 `project_id` 的首条应征沟通消息。
- 该接口不创建正式订单、不自动拒绝其他应征者、不修改企划状态；这些属于后续完整订单/企划流程。

#### 会话与通知

- `PrivateMessageRequest` 新增可选 `orderId`；私聊、应征会话和交易会话互斥使用 `projectId` 或 `orderId`。
- 会话读取、发送时会校验请求者是否为关联订单的买卖双方，防止第三方进入交易会话。
- 会话摘要按“双方 + projectId + orderId”聚合，交易会话不会和同一双方的普通私聊或应征会话串在一起。
- 新增 `GET /api/v1/messages/notifications`，仅返回非私聊类型的系统/应征通知。
- 新增 `PUT /api/v1/messages/notifications/read-all`，只标记非私聊通知为已读；不会清除 C2C 会话未读。
- WebSocket 继续遵循“先落库，再推送”；新增通知和首条会话消息都会调用已有推送路径。

### 11.3 已实现的前端行为

## 18. 定向邀请消息规则（2026-08-25）

定向邀请复用现有“双方合并私聊 + 独立系统消息”模型，不新增邀请专属聊天室。

- 创建邀请：只向受邀画师写一条 `type=0`、`subtype=INVITATION_CREATED` 的系统消息，不提前建立会话。系统消息与邀请记录正文相同，并携带 `projectId`。
- 接受邀请：自动建立或复用双方合并私聊，写一条 `type=3`、`subtype=INVITATION_ACCEPTED` 的会话系统提示；同时向企划方另写一条 `type=0`、同 `subtype` 的独立系统消息。
- 接受邀请的两条消息正文必须完全一致：`画师「名字」接受了您的企划「企划标题」的邀请，双方已建立会话，您可以开始与画师沟通后续合作内容。`
- 拒绝邀请：只向企划方写 `type=0`、`subtype=INVITATION_REJECTED` 的系统消息，不建立或启动邀请会话。正文包含画师、企划标题和必填拒绝理由。
- 三类消息都使用 `projectId` 进入企划详情；系统消息标题分别为“收到定向邀请”“邀请已被接受”“邀请已被婉拒”。
- 接受和拒绝只能从待处理状态执行一次；重复请求不能生成重复消息。WebSocket 仍遵循事务提交后推送，断线时依靠已有 REST 补拉。
